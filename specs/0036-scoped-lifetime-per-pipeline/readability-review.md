# Review
## All

- [ ] The mermaid diagrams have added real clarity and are an excellent addition. Use more diagrams when they add clarity, including class diagrams and sequence diagrams.
- [ ] Scope: too hard to read as a narrative. Instead, structure it as a statement of scope: a bullet list of FR/NFR covered, along with other scope not explicitly tagged via FR/NFR; and out-of-scope items that might not be clear with reference to ADRs that do cover.
- [ ] Use [Simplified Technical English](https://www.asd-europe.org/standards-specifications/simplified-technical-english/) to aid non-native speakers and ensure precise usage of language. Sentences are often long and have a tendency to “run on.”
- [ ] Prefer a slightly longer document than terseness, for clarity. See the review item under 71 beginning “AC-33 is that rule's regression guard” as an example of clarity where the cross-references are hard to read without moving back and forth and mainly useful for a reviewer to cross-check. Start with a discussion of the functional requirements to be fulfilled, then bullet-point a list of FRs and ACs this requirement supports. This allows the bullet point to be skimmed in reading for the design, but cross-checked when accuracy is desired. We should balance both these needs.
- [ ] In many places, bold has been used for emphasis to draw out the key parts of the text. Better to rewrite so that these key ideas are not lost in the detail, rather than overusing a typographic convention to pick them out.
- [ ] Be aware that some of these might have shifted from the last set of edits, as this manual review was done at the same time.
- [ ] The Key Components tables work well, but the column names are a little off:
    - [ ] The column headed stereotype is actually a classifier for the responsibility. A stereotype would be something like “Information Holder”, “Structurer”, or “Controller”. The responsibility classifier is the useful call here; the stereotype, less so. So just change the column name.
    - [ ] A component might have several responsibilities, i.e., both knowing and doing
    - [ ] Its role is a collection of those responsibilities, expressed as “what this does”. Expressing the role lets us determine if something has “too many responsibilities” because we find it hard to express it as one role. (RDD really restates the “single responsibility principle” as the “single role principle.”
- [ ] Collaborators might also be useful to truly support RDD
- [ ] A review and fix technique that corrects individual statements needs occasional re-read of the whole document as statements become contradictory or unnecessary in context

72. Adopting an ambient DI scope — the resolution-source hand-off

- [ ] A side note: producer transformer/mapper pipelines may well inherit an ambient scope, as they may run with an ASP.NET controller or similar. But consumer transformer/mapper pipelines will run within a Dispatcher context and thus share the scope of the dispatcher pipeline but never be ambient because a Dispatcher is not hosted inside an ASP.NET scope.
- [ ] ScopeAffinityPolicy — who computes the affinity (new, DI package, internal). The usage is unclear. I know this belongs to these factories and seems to have something to do with our lifetime policy, but I struggle to understand its role in relation to the parent in the text. Hard to parse.

73. ASP.NET Core's request scope as Brighter's ambient scope — a package of its own, and one line to opt in
- [ ] “A pump thread is taken to carry no usable ambient HttpContext, yet IHttpContextAccessor is AsyncLocal-backed, so a Dispatcher started from inside a live request inherits one: the context is non-null, its RequestServices is that request's scope, ADR 0072's usability probe passes, and the ask lands on ladder row 10 — borrowed.” A Dispatcher is never started from within a live request. That would be an erroneous use of the library. A producer may be called from within a live request; a consumer might be (request-reply), but not a Dispatcher. The next paragraph makes this statement, so this one becomes very unclear preceding it.

74. Where the scope-configuration rules are evaluated

Questions:  Registration: Brighter’s builders register required services with the host DI provider; the only implementation provided is for Microsoft DI. These services need to be resolvable from the scopes used by the pipelines. In many cases, they are factory functions for that reason. We should review registration to ensure that it will continue to work as expected, particularly with an ambient scope borrowed from a non-Brighter parent.  74. Where the scope-configuration rules are evaluated
- [ ] => Why the rules are not ISpecification<T> families inside the core validator. The design can implement an extension to ask loaded assemblies whether they add rules for evaluation through reflection. So we could have an interface like IAmAValidationProvider that exposes an IEnumerable<ISpecification<T>> with rules that use types from that assembly. This avoids the problem of needing to take the dependencies across assemblies.
