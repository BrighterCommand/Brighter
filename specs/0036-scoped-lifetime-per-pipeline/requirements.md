# Requirements

> **Note**: This document captures user requirements and needs. Technical design decisions and implementation details should be documented in an Architecture Decision Record (ADR) in `docs/adr/`.

**Linked Issue**: #4256

**Revision**: 27 — see [Revision history](#revision-history) at the end of this document. Decisions are cited by number throughout (**D0**–**D19**); they are listed in [Decisions](#decisions-d0d19).

## Problem Statement

**As** a developer using Brighter's command dispatcher from an ASP.NET controller or Minimal API route handler, and from within a Brighter message pump (Reactor and Proactor), with Microsoft's DI container, **I want** a handler, mapper or transform whose **lifetime** is `Scoped` to resolve its dependencies from the **DI scope the host already owns** — under ASP.NET, the request's DI scope — rather than from a fresh one; and, where the host owns no such DI scope (a message pump, a worker, a console application), for Brighter to begin exactly one DI scope for the pipeline, **so that** the handler, mapper or transform is released at the end of the pipeline that used it rather than at process exit, and everything it resolved is reclaimed when that DI scope is disposed — meaning a key dependency such as an EF Core `DbContext` has **one identity for the whole pipeline** instead of a fresh instance per resolution.

`Transient` and `Singleton` do not change meaning as a result of this work (C-6, OOS-7). Nor does the message pump acquire a DI scope of its own to offer: it publishes none, and a pipeline running under it begins its own exactly as it does today (**D0b**, OOS-1, FR-19).

Three concrete defects sit behind that story, on two axes. All are departures from a lifetime model that is otherwise coherent, so the model is stated first — **The Lifetime Model** below — and the departures from it after, under **Where the Implementation Has Drifted**.

## The Lifetime Model

This section is the frame for everything that follows: what Brighter's lifetime settings mean, how they use Microsoft's DI scopes, and what unit of work a DI scope is meant to correspond to.

The three `ServiceLifetime` values already mean three different **get/release cycles** for objects Brighter creates from a container-backed factory. **This specification does not change that model.** It changes only which DI scope `Scoped` binds to, and adds an opt-in for where that DI scope comes from. So what follows is the model **as it is already meant to work** — and the section after it records the three places where today's implementation does not honour it.

### Terms used in this document

Brighter and Microsoft's DI container both use the word *scope*, for related but distinct things. This document keeps them apart with two words, used consistently and never for each other:

- **DI scope** always means Microsoft's `IServiceScope` — the container's unit of resolution and disposal.
- **lifetime** always means Brighter's `Transient`/`Scoped`/`Singleton` setting (formally the *configured lifetime*, below).

Every other scope term below names a **DI scope seen from some angle**: the qualifier says *which* DI scope, and who owns it. "Lifetime scope" is deliberately **not** used, because `HandlerLifetimeScope`, `ServiceProviderLifetimeScope` and `IAmALifetime` already exist in the codebase and mean something else again — NFR-8 requires those to be kept distinct from `IAmAScope`.

Every requirement and Acceptance Criterion in this document should be read with these meanings.

| Term | Meaning |
| --- | --- |
| **pipeline** | One decorated handler sequence, or one mapper-plus-its-transforms sequence, executed for one request. The unit of work, and — per D0 — the unit a DI scope corresponds to. This is the codebase's own noun: `PipelineBuilder.Build` returns `Pipelines<TRequest>` (`PipelineBuilder.cs:167`), a `Send` is exactly one pipeline (`AssertValidSendPipeline`, `CommandProcessor.cs:1502`) and a `Publish` to N subscribers is N. A pipeline nested inside another — a `Send` issued from inside a handler — is a **new** pipeline, never part of its parent (OOS-14). *(The decorator sequence within one pipeline is the classic chain of responsibility; this document does not use "chain" as a term of art, because in the code `handlerChain` names the whole `Pipelines<TRequest>` collection, not one member of it.)* |
| **handler pipeline** | The decorated sequence of handlers built for one `Send`/`SendAsync`, or for **one subscriber** of one `Publish`/`PublishAsync` — one member of the `Pipelines<TRequest>` that `PipelineBuilder.Build` returns. |
| **transform pipeline** | One message mapper plus its wrap or unwrap transforms, built for one message (consumer) or one `Post`/`DepositPost` (producer). Built by `TransformPipelineBuilder`/`TransformPipelineBuilderAsync`. |
| **bound** | The outer limit within which pipelines live and die. On a consumer the message is the bound, not the DI scope: every pipeline created while handling a message is torn down before the pump takes the next message. |
| **DI scope** | Microsoft's `IServiceScope`. A container-`Scoped` service is one instance per DI scope and is disposed when that DI scope is disposed; that is the only mechanism by which dependencies are shared or reclaimed. Brighter does not implement it and does not change it. |
| **ambient scope** | A **DI scope** owned by **the calling application** and discoverable by Brighter without the caller passing it — under ASP.NET, the DI scope behind `HttpContext.RequestServices`. Never a DI scope Brighter created. |
| **pipeline scope** | The **DI scope** a pipeline resolves from, whether adopted or created. Says nothing about ownership. |
| **owned pipeline scope** | A pipeline scope Brighter created — i.e. a DI scope Brighter called `CreateScope()` for and is therefore responsible for releasing. Used wherever ownership is meant; an adopted scope is never an owned pipeline scope. |
| **adopt** / **borrow** | A pipeline resolves its dependencies from an existing ambient scope instead of creating a DI scope of its own. A borrowed scope belongs to the caller. |
| **own** | A pipeline created its scope and is responsible for releasing it. |
| **suppress** | For the duration of a `Publish` subscriber's pipeline, the ambient is made undiscoverable to that pipeline **and to any pipeline nested inside it**, so nested pipelines also create their own scopes (FR-8, FR-9, **D6**). Suppression is a property of *being a subscriber*, not of declining to adopt: a pipeline that creates its own pipeline scope for any other reason does not suppress (FR-27.3). |
| **artefact** | An object Brighter creates from the container through one of its factories: a message mapper, a message transform, or a request handler. Each has a **configured lifetime** — see the next row. |
| **configured lifetime** | The value of `HandlerLifetime`, `MapperLifetime` or `TransformerLifetime`. Its *type* is `ServiceLifetime`, but it is **Brighter's** setting, and it is **not** the `ServiceLifetime` the artefact type is registered into the service collection with: whatever the configured lifetime, Brighter always registers handler, mapper and transform types as `ServiceLifetime.Transient` (C-17). Where this document says "lifetime" unqualified, it means the configured lifetime. |
| **lifetime triple** | The three configured lifetimes taken together, written `{HandlerLifetime, MapperLifetime, TransformerLifetime}` — e.g. `{Scoped, Scoped, Scoped}`. FR-22.2 makes them a joint choice, so Acceptance Criteria state all three. |
| **participating factory** | The factories that serve a pipeline, determined **structurally** by the kind of pipeline and not by whether a given factory happens to resolve anything for it (**D12**): the handler factory for a handler pipeline; the mapper factory **and** the transformer factory for a transform pipeline (C-19) — **whether or not that mapper declares any `[WrapWith]`/`[UnwrapWith]` transform**. Every participating factory has **Create/Release** semantics, and the `Release` half is what makes "released at the end of the pipeline" expressible at all (ADR 0066) — the two families release differently, which C-19 records. Used by FR-27. |
| **scope provider** / **ambient source** | `IAmAScopeProvider` — the extension point through which an application publishes an **ambient** for pipelines to adopt. Its single member is the **ambient query**: `IAmAScope? GetAmbient(ScopeAffinity affinity)` (the member name is a working name — C-11; its contract is fixed by FR-10 and **D17**). It is called exactly once by each pipeline that takes a pipeline scope, carries that pipeline's affinity, and returns an ambient the pipeline may adopt or nothing. Per **D11** it is *not* the source of Brighter's own scopes: the container package always creates and owns those. Registering one adds adoption; it never adds or removes pipeline scopes. |
| **scope affinity** | Whether a pipeline may adopt an ambient (`ScopeAffinity.JoinAmbient`) or must always create its own and suppress the ambient beneath it (`ScopeAffinity.AlwaysNew`). |

### How Brighter creates the objects it needs

Brighter never constructs a user-defined handler, mapper or transform itself. It asks a **factory**, and every factory call is a `Create` matched by a `Release`:

| Factory (in `Paramore.Brighter`) | Create | Release |
| --- | --- | --- |
| `IAmAHandlerFactorySync` / `IAmAHandlerFactoryAsync` | `Create(Type handlerType, IAmALifetime lifetime)` | `Release(handler, IAmALifetime lifetime)` |
| `IAmAMessageMapperFactory` / `IAmAMessageMapperFactoryAsync` | `Create(Type) → Lease<T>?` | `Release(Lease<T>?)` |
| `IAmAMessageTransformerFactory` / `IAmAMessageTransformerFactoryAsync` | `Create(Type) → Lease<T>?` | `Release(Lease<T>?)` |

Those six interfaces know nothing about any container — NFR-1 keeps it that way, and ADR 0066 is why the mapper and transformer pairs hand back an opaque `Lease` rather than the instance. The **application supplies the implementation**, and in the case this specification is about that implementation is backed by **Microsoft's DI container**: `ServiceProviderHandlerFactory`, `ServiceProviderMapperFactory` and `ServiceProviderTransformerFactory[Async]` in `Paramore.Brighter.Extensions.DependencyInjection`, all delegating to `ServiceProviderLifetimeScope.GetOrCreate` (`:126`), which switches on the configured lifetime (`:132-142`). A different container would supply its own (OOS-3, NFR-7).

That leaves exactly two questions, and **this specification is about nothing else**:

1. **When is `Create` called, and when is what it returned reclaimed?**
2. **Where do the *dependencies* of the created object come from** — the `DbContext`, the transaction, the unit of work the user injected into their own handler?

The second is the one users actually feel. A handler is usually cheap to construct; the `DbContext` it takes is not, and whether it is *the same* `DbContext` the controller is already using is the whole point of this work.

**`Release` means two different things to the two factory families, and that difference *is* Defect 1.** The handler factory keys its DI scope **per pipeline** and disposes it on `Release`. The mapper and transformer factories key **one DI scope for the whole factory** and release per *resolution* — which, for `Scoped`, means never.

| | Handler factory | Mapper & transformer factories |
| --- | --- | --- |
| **Its DI scope is keyed per** | **pipeline** — one `ServiceProviderLifetimeScope` per `IAmALifetime` (`ServiceProviderHandlerFactory.cs:127-131`) | **factory** — one built in the constructor and kept for the factory's life (`ServiceProviderMapperFactory.cs:46`) |
| **Does `Release` carry a token?** | **No.** `Create` uses the token-*discarding* `GetOrCreate<T>(Type)` overload (`ServiceProviderLifetimeScope.cs:110`); `Release` takes the handler and its `IAmALifetime` | **Yes.** `Create` takes the token-*carrying* overload and the token rides in the `Lease` (`ServiceProviderMapperFactory.cs:55-59`) |
| `Transient` **is reclaimed by** | `Release` — disposes that pipeline's whole scope (`:102-107`, `:133-137`) | `Release(Lease)` — drains just that one resolution's DI scope (`:68-73` → `ServiceProviderLifetimeScope.cs:346-350`) |
| `Scoped` **is reclaimed by** | the same `Release` — the handler and everything resolved alongside it go with the pipeline's scope. **This is the model that already works.** | **nothing.** The token is `null` for `Scoped` (`ServiceProviderLifetimeScope.cs:136`, documented at `:118-123`), so `Release` is a no-op and the object lives until the factory is disposed at **shutdown** (`ServiceProviderMapperFactory.cs:78`; its own remarks say so at `:61-65`). **This is Defect 1.** |
| `Singleton` **is reclaimed by** | nothing — `Release` returns immediately (`:104`) | nothing — no token is issued |

That is why Defect 1 is confined to mappers and transforms, and it tells the ADR what shape the fix has: **make the mapper and transformer factories scope the way the handler factory already does** — one DI scope per pipeline, disposed when the pipeline ends — with the added requirement that the two must share *one* such scope per transform pipeline rather than each keeping its own (C-19, FR-3).

### What a lifetime setting actually selects

Every artefact Brighter builds — a message mapper, a message transform, a request handler — raises two separate questions:

1. **Artefact identity.** How many `Create` calls actually produce a new object, and how long is it kept before it is reclaimed?
2. **Dependency identity.** Where do that object's constructor dependencies come from, and which of them does it share with the other artefacts working on the same piece of work?

One setting answers both, and that is the source of most of the confusion this specification exists to remove.

**A lifetime is not a registration.** Whatever the lifetime is set to, Brighter always registers the handler, mapper and transform types into the container as `ServiceLifetime.Transient` (C-17). Setting `MapperLifetime = ServiceLifetime.Scoped` does not make the mapper a container-scoped service, and nothing in the service collection records that you set it. What the lifetime selects is

- **which DI scope Brighter resolves the artefact through** — which decides *dependency* identity, because a container-`Scoped` service is one instance per DI scope and is disposed with it; and
- **whether Brighter caches the resulting object** for the life of that DI scope — which decides *artefact* identity, through Brighter's own per-type cache (`ServiceProviderLifetimeScope.GetOrCreateScoped`, `:163-178`), not through the container.

So the lifetime is best read as a sentence about a DI scope: *which* one this artefact and its dependencies come out of, and *how long* Brighter holds the artefact it got.

| Lifetime | What `Create` returns | Dependencies come from | Verified at |
| --- | --- | --- | --- |
| `Transient` | a **new object every call** | a **fresh** DI scope per `Create`, owned by that resolution. `IsolateTransientHandlerScope = false` restores the older behaviour of one shared DI scope per pipeline. | `GetTransient` `:259-261`; `GetOrCreate` `:139-140`; `BrighterOptions.cs:37`; ADR 0067 |
| `Scoped` | **the same object for every call on one pipeline**, from Brighter's own per-type cache — except under `JoinAmbient`, where identity follows the **borrowed** DI scope, so one object may span several pipelines in one request (FR-16a, **D7**) | the pipeline's single DI scope, owned by the **pipeline**. A `Publish` is multiple pipelines, so it is multiple DI scopes. | `GetOrCreateScoped` `:163-178`; `GetOrCreate` `:135-137`; `ServiceProviderHandlerFactory.cs:127`; `PipelineBuilder.cs:528`, `:539`; ADR 0039 |
| `Singleton` | **the same object for the whole process** | the **root** provider, owned by the application | `GetOrCreateSingleton` `:152-157`; `GetOrCreate` `:132-134` |

**What *reclaims* the object is deliberately not a column here.** It is not a property of the lifetime alone — it depends on the factory family as well, and the two disagree precisely where it matters. That is the matrix in *How Brighter creates the objects it needs* above.

Stated as one rule, **and it is a rule about `Scoped`**: **dependency identity always follows the DI scope; artefact identity follows the pipeline under `AlwaysNew`, and the borrowed DI scope under `JoinAmbient`.** The other two lifetimes sit outside it, which is why the rule does not mention them: `Transient` gives a **new artefact per resolution**, from a DI scope of its own by default or from one shared per pipeline under `IsolateTransientHandlerScope = false` — either way artefact identity there is per *resolution*, not per pipeline, under either affinity — and `Singleton` gives one artefact per process from the root provider.

That is why one consequence runs through the whole document: **artefact identity and dependency identity can come apart.** Resolving from a caller's DI scope gives dependency sharing for free, but sharing the *artefact* across pipelines in that DI scope is a separate thing Brighter must arrange (D7, FR-16, C-17) — which is why FR-26 has to bound what Brighter retains against a DI scope it does not own.

The other consequence is about which lifetime this work touches at all. `Transient` makes and discards its own DI scope per resolution and `Singleton` resolves from the root provider, so a host-owned DI scope is meaningful to `Scoped` alone.

**Adoption is a property of `Scoped` alone** (FR-21). `Transient` and `Singleton` are untouched by this work, so the affinity opt-in has no effect on them. Because all three lifetimes **default to `Transient`** (`BrighterOptions.cs:20`, `:52`, `:69`), opting into adoption without also selecting `Scoped` is inert — and is therefore validated rather than silently ignored (FR-22, **D5**).

### The scope unit is the pipeline

The **pipeline** is the unit: one `Send`, one subscriber of one `Publish`, one transform pipeline for one message or one `Post`. A `Publish` to three subscribers is three pipelines, and therefore three DI scopes.

**Why the pipeline and not the message.** A pipeline is a unit of work: under CQRS each subscriber of a `Publish` is its own unit of work (ADR 0039), and the handler pipeline is also the transactional boundary — the outbox transaction begins and ends inside it. The message is the *bound*, not the DI scope: on a consumer every pipeline created while handling a message is torn down before the pump takes the next, and that bound falls out of pipeline scoping without needing separate enforcement.

### Where a pipeline's DI scope comes from, and what adopting means

Today every DI scope Brighter uses is one it made itself. `IAmACommandProcessor` is a singleton (ADR 0033) whose factories capture the **root** provider, so a `Scoped` pipeline's DI scope is always a fresh child of root. In a worker, a console application or a consumer that is the only available answer — there is nothing else to resolve from. In an ASP.NET application it is not: the request already owns a DI scope, holding the `DbContext`, transaction and middleware-populated state the caller is working with.

An **ambient** scope is a DI scope the calling application owns and Brighter can discover without the caller passing it — under ASP.NET, the DI scope behind `HttpContext.RequestServices`. **Adopting** it means the pipeline resolves from that DI scope instead of creating one. Because Microsoft's DI scopes do not nest (C-1), adoption can only mean resolving *directly* from the caller's provider: there is no way to create a child DI scope that still sees the request's `DbContext`. Ownership travels with the DI scope — Brighter disposes what it created and never disposes what it borrowed (C-7).

Two things are deliberately outside adoption. `Publish` subscribers never adopt, because ADR 0039 makes each subscriber its own unit of work, and that isolation propagates to pipelines nested inside them (D6); the consequence is that an in-process subscriber cannot join a transaction the caller opened, and the answer to that requirement remains the outbox (C-4). And adoption is **off by default** — it is an opt-in the application makes once, at registration (FR-17), and it applies to `Scoped` only.

### Why the three settings must be chosen together

**Why `Transient`/`Scoped` may not be mixed, and why `Singleton` may (D8).** The three factories resolve independently, each through its own `ServiceProviderLifetimeScope`, and each lifetime takes its container-`Scoped` dependencies from a different DI scope: `Singleton` from the **root** provider (`:151-155`), `Scoped` from the pipeline's single DI scope, `Transient` from a **fresh** DI scope per resolution (`:259-261`). Only `Scoped` adopts (FR-21). So under `JoinAmbient` a `{Scoped handler, Transient mapper}` pipeline has the handler joining the caller's request scope while the mapper resolves from a throwaway DI scope off root — half the pipeline in the caller's transaction, half not, silently. `Singleton` is orthogonal: it resolves from root whatever the other two are set to, so mixing it changes nothing about them, and FR-20 actively prescribes it as the migration path.

## Where the Implementation Has Drifted

The model above is not what the code does, in three places on two axes. All three concern the `Scoped` lifetime. The axes are its two halves: **artefact identity** — the artefact is held too long — and **dependency identity** — the artefact's dependencies come from the wrong DI scope. **Defect 1** breaks the first. **Defect 1b** and **Defect 2** each break the second: Defect 1b *within* a single transform pipeline, Defect 2 *between* Brighter and its caller. They are referred to by those names throughout.

**Defect 1 — `MapperLifetime.Scoped` silently means process lifetime** (artefact identity). `ServiceProviderMapperFactory` creates exactly one `ServiceProviderLifetimeScope` in its constructor (`ServiceProviderMapperFactory.cs:46`), and under `Scoped` that scope caches every mapper by type for the factory's whole life (`ServiceProviderLifetimeScope.cs:167`). Those factories are constructed once for the singleton `Dispatcher` and once for the singleton `OutboxProducerMediator`. The same applies to `ServiceProviderTransformerFactory[Async]`. So a `Scoped` mapper that holds per-message state, or that owns an `IDisposable`, holds it from first use until host shutdown, and message N+1 sees message N's state. Handlers are already correct — `CommandProcessor` brackets every call with `using var builder = new PipelineBuilder<T>(...)` and `PipelineBuilder.Dispose()` disposes every instance scope it created, and, more to the point, `ServiceProviderHandlerFactory` keys its `ServiceProviderLifetimeScope` **per pipeline** and disposes it on `Release` (`:127-131`, `:133-137`) rather than holding one for its own lifetime. So the defect is confined to mappers and transforms, and the fix is to give their factories the scoping the handler factory already has (see *How Brighter creates the objects it needs*).

**Defect 1b — the mapper and transformer factories do not share a DI scope** (dependency identity, within one pipeline). Fixing Defect 1 is necessary for FR-3 but not sufficient. `ServiceProviderMapperFactory` and `ServiceProviderTransformerFactory[Async]` each construct their **own** `ServiceProviderLifetimeScope` (`ServiceProviderMapperFactory.cs:46`, `ServiceProviderTransformerFactory.cs:46`), so one transform pipeline has **two** DI scopes even when both factories are configured `Scoped`. A container-`Scoped` dependency shared by a mapper and its `[UnwrapWith]` transform is therefore two instances rather than one, and giving each factory per-pipeline scoping *independently* would leave it that way. FR-3 requires the two factories to be handed the **same** pipeline scope for a given transform pipeline. How that is threaded is design work (C-13); that it is required is recorded in **C-19**, and it is a constraint the ADR must not discover late.

**Defect 2 — no pipeline ever adopts a caller-owned scope** (dependency identity, between Brighter and its caller). `IAmACommandProcessor` is registered as a singleton whose handler factory captures the **root** provider, and `Scoped` resolution calls `CreateScope()` on that root. In an ASP.NET application a `Scoped` handler is therefore resolved from a fresh child of root, never from `HttpContext.RequestServices`. Middleware-populated scoped services are re-constructed empty and a controller-owned `DbContext` or transaction cannot be joined. This was a deliberate consequence of ADR 0033 (`0033-lifetime-of-command-processor-and-mediator`, the `CommandProcessor` is a singleton), but it is surprising: the `WebAPI_EFCore` sample configures Darker with `QueryProcessorLifetime = Scoped` (`samples/WebAPI/WebAPI_EFCore/GreetingsWeb/Startup.cs:132`), so in the same application queries run in the request's DI scope while commands do not.
Closing that gap pays off beyond consistency. Once a `Scoped` pipeline adopts the request's DI scope, a Brighter handler reached by `Send` and a Darker query handler invoked from the *same* controller action or route handler resolve the **same** `DbContext`, because both now resolve from `HttpContext.RequestServices`. That needs no change to Darker, which stays out of scope (OOS-11) — the sharing is a consequence of Brighter joining the DI scope Darker already uses.

## Proposed Solution

Name the unit a DI scope corresponds to explicitly — **the pipeline** — and make every factory honour it, then let an application opt in to `Scoped` pipelines adopting the DI scope it already owns.

From a user's point of view:

- **`Scoped` means per pipeline, everywhere.** A `Scoped` mapper and its transforms share their scoped dependencies for the message (or the `Post`) being mapped, and are released when that mapping finishes. A `Scoped` handler pipeline behaves as it already does — one scope per `Send`, one per subscriber of a `Publish` — and is released when the pipeline completes, which for a `Publish` subscriber means when the **publish** completes rather than when that subscriber finishes (FR-9's release-timing clause: today's behaviour, deliberately unchanged).
- **Opting in is one gesture, and it is checked.** An ASP.NET application installs a new, small package (working name `Paramore.Brighter.Extensions.AspNetCore`) and calls its registration extension. There is **no middleware to register** and no per-request call site to remember. Because adoption applies only to `Scoped`, opting in while every lifetime is still `Transient` would do nothing — so `ValidatePipelines()` reports it rather than leaving the user to wonder. It also enforces that you **pick one lifetime for handlers, mappers and transforms** rather than mixing `Transient` and `Scoped`, since a mixed pipeline joins the caller's scope on one side and not the other. `Singleton` sits outside that rule and stays freely mixable — it is what FR-20 tells you to migrate to.
- **Where there is no ambient, nothing changes.** In a worker, a console app, a consumer, or on a background thread with no `HttpContext`, Brighter creates and owns the pipeline's DI scope, exactly as it does today.
- **`Publish` is the one exception, all the way down.** A fan-out always gives each subscriber its own new DI scope, even under an ambient — and that isolation propagates: a `Send` nested inside a subscriber also creates its own DI scope rather than rejoining the request. Each subscriber is its own unit of work (ADR 0039). In-process subscribers therefore cannot join a transaction the caller opened; the answer to that requirement remains the outbox.
- **Brighter never disposes what it borrowed.** A DI scope Brighter created, Brighter disposes; an adopted DI scope is the caller's.
- **One behavioural break, deliberately.** `MapperLifetime.Scoped` stops caching across messages. Anyone who relied on that — deliberately or accidentally — moves to `Singleton`. There is no compatibility flag.

### Functional Requirements

#### Group A — `Scoped` means per pipeline

- **FR-1 — A `Scoped` mapper is per transform pipeline, not per process.** With `MapperLifetime = ServiceLifetime.Scoped`, the mapper instance resolved while building a transform pipeline must be distinct from the instance resolved for any other transform pipeline **that does not share the same adopted scope**, and its pipeline scope must be released when that pipeline is released. The exception is adoption: under `JoinAmbient`, pipelines that borrow one request scope share one mapper instance, because the borrowed scope owns the artefact (FR-16a, **D7**). Where no scope is adopted — every consumer pipeline, and every producer pipeline under `AlwaysNew` — the rule is unqualified.
  *Example (consumer):* a `Scoped` mapper `OrderPlacedMapper` records `Guid.NewGuid()` in a field on construction. Consuming message N and then message N+1 yields two different `Guid` values; the instance used for N has been disposed (its `Dispose` observed) before the instance for N+1 is constructed.
  *Derives from:* D0, and the defect at `ServiceProviderMapperFactory.cs:46` / `ServiceProviderLifetimeScope.cs:167`.

- **FR-2 — A `Scoped` transform is per transform pipeline, not per process.** With `TransformerLifetime = ServiceLifetime.Scoped`, FR-1 holds identically — **including its adoption qualifier** — for `IAmAMessageTransform` and `IAmAMessageTransformAsync` instances, in both the sync (`TransformPipelineBuilder`) and async (`TransformPipelineBuilderAsync`) builders.
  *Example:* a `Scoped` `CompressPayloadTransform` used for message N is not the instance used for message N+1, and is disposed at the end of N.

- **FR-3 — Within one transform pipeline, mapper and transforms share scoped dependencies.** With `MapperLifetime` and `TransformerLifetime` both `Scoped`, a container-registered `Scoped` dependency injected into the mapper and into each of its transforms must be **one** instance for that pipeline.
  *Example:* `IOrderContext` is registered `AddScoped`. `OrderPlacedMapper` and its `[UnwrapWith]` transform both take an `IOrderContext`. For one message, `ReferenceEquals(mapper.Context, transform.Context)` is `true`; for the next message it is a different instance.

- **FR-4 — Producer transform pipelines scope per `Post`/`DepositPost`.** The behaviour required by FR-1, FR-2 and FR-3 must apply to the wrap pipeline built and disposed per `Post`/`DepositPost` on the producer side, not only to the consumer's unwrap pipeline.
  *Example:* two separate `Post` calls made from a console application (no ambient) resolve two distinct `Scoped` mapper instances, the first disposed before the second is constructed.

- **FR-5 — A failed pipeline build releases the *owned* pipeline scope.** When building a transform pipeline throws (the `CleanUpAfterFailedBuild` path, `TransformPipelineBuilderAsync.cs:122` and `:163`), the **owned pipeline scope for that pipeline, if any**, must be released before the `ConfigurationException` propagates, so a repeatedly-failing build leaks no scopes. Where the pipeline adopted an ambient there is no owned scope and nothing is released — releasing the caller's scope would violate FR-12.
  *Example:* a `Scoped` mapper whose constructor requires an unregistered service is used for 1,000 `Post` attempts, each throwing `ConfigurationException`. The number of live, undisposed scopes attributable to Brighter at the end is zero, and the `ConfigurationException` (with the original inner exception) is still what the caller sees — a release failure must not mask it. Under `JoinAmbient` the same 1,000 failures dispose nothing the caller owns (AC-38).

- **FR-6 — A pipeline scope is released exactly once, on every exit path.** A pipeline scope Brighter owns must be released when the pipeline completes, whether it completes normally or by exception, and releasing the same pipeline scope a second time must be a no-op rather than an error or a double dispose. For a `Publish` subscriber the completing unit is the **publish**, not the individual subscriber — see FR-9's release-timing clause, which preserves today's behaviour.
  *Example:* a handler throws `InvalidOperationException` from `HandleAsync`; the handler pipeline's scope is disposed exactly once, and the exception reaches the caller unchanged.

- **FR-7 — Handler pipeline scoping is preserved.** One `Send`/`SendAsync` takes one handler pipeline scope, released when the pipeline completes. This is today's behaviour and must be regression-guarded, not re-implemented differently.
  *Example:* with all three lifetimes `Scoped` (FR-22.2 makes that choice joint), a handler's `Scoped` dependency is disposed by the time `Send` returns; two sequential `Send` calls with no ambient resolve two distinct instances of it.

- **FR-8 — A `Publish` subscriber never adopts, and suppresses the ambient beneath it.** Every subscriber of a `Publish`/`PublishAsync` whose pipeline takes a pipeline scope at all takes a **distinct, newly created** one, and does so **even when an ambient scope exists and the application has opted in**. A subscriber's pipeline never adopts an ambient. Whether a subscriber's pipeline takes a scope is FR-27.1's question — a subscriber with no `Scoped` participating factory takes none — but **suppression is unconditional**: every subscriber suppresses the ambient beneath it whether or not it took a pipeline scope of its own (FR-27.3). Further (**D6**), for the duration of a subscriber's execution the ambient must be suppressed, so that any pipeline **nested inside** that subscriber — a `Send`, a `Post`, a further `Publish` — also creates its own scope rather than adopting the caller's. Subscriber isolation is not one level deep. (ADR 0039 `0039-scoping-dependencies-inline-with-lifetime-scope`; D0c; D6.)
  *Example:* three handlers are registered for `OrderPlaced`, each taking a `Scoped` `IUnitOfWork`. `PublishAsync` from a controller in an opted-in ASP.NET application yields three `IUnitOfWork` instances, none of them the request's instance. A `SendAsync` issued from inside the first handler resolves a fourth instance — neither the request's nor the first handler's.

- **FR-9 — A `Publish` subscriber needs **two** brackets: one around its resolution, one around its execution.** **Both** `Publish` and `PublishAsync` **fully resolve** every subscriber's pipeline before running any of them, and then run the subscribers **concurrently**: the sync path builds at `CommandProcessor.cs:474` and dispatches via `Parallel.ForEach` at `:481`; the async path builds at `:581`, starts at `:591-599` and awaits together at `:601`. "Build" is not metadata work — `PipelineBuilder.Build` creates a per-subscriber instance scope, resolves the handler through the handler factory, and resolves every attribute-driven decorator, once per subscriber, inside the caller's own flow (`PipelineBuilder.cs:183` scope, `:184` handler, `:187` decorators; async twin `:228` scope, `:229` handler, `:230-231` decorators). Two brackets are therefore required, and **neither substitutes for the other** (**D10**):
  (a) **Resolution-time bracket — per subscriber, inside the build loop.** The pipeline scope, and the ambient suppression FR-8 requires, must be established around **each subscriber's own iteration** of the build, because that is where the subscriber's artefacts and their container-`Scoped` dependencies are resolved. Establishing them around the *whole* build loop is wrong (it would give all subscribers one pipeline scope); establishing them only at dispatch is wrong (the artefacts already exist, resolved from the caller's unsuppressed ambient — under `JoinAmbient` every subscriber would get the request's instance, defeating FR-8 and falsifying AC-10 and AC-11).
  (b) **Execution-time bracket — around that subscriber's own invocation.** Suppression must additionally be live around the subscriber's own `Handle`/`HandleAsync` — inside its `Parallel.ForEach` body or around its task — because pipelines **nested inside** a subscriber (a `Send`, a `Post`, a further `Publish`) are created at dispatch time and must not see the ambient. It must be restored on every exit path of that invocation: normal return, exception, cancellation.
  No subscriber may observe another subscriber's pipeline scope or suppression state, and the caller's own flow must be unsuppressed once the publish returns.
  **Release timing is unchanged from today.** Per-subscriber scopes are created during the build but drained together when the `PipelineBuilder` is disposed at the end of the publish (`using var builder`, `CommandProcessor.cs:472`/`:575`). This work does **not** tighten release to end-of-subscriber, because end-of-publish release is today's behaviour, AC-10 regression-guards it, and tightening it is out of scope for this specification. **C-2 is not the reason** and must not be cited as one: C-2 and OOS-5 cover `Reactor`, `Proactor`, `Dispatcher`, `DispatchBuilder` and `ConsumerFactory` only, not `PipelineBuilder` — which FR-9(a) requires to change in any case, since the resolution-time bracket sits inside its per-subscriber build loop. So for a `Publish`, "released when the pipeline completes" (FR-6, NFR-6) means *when the publish completes*, and that is the behaviour AC-10 asserts.
  *Example:* subscribers A and B each `await` a gate so their execution provably overlaps. A calls `SendAsync(new InnerCommand())` from inside `HandleAsync`. `InnerCommand`'s handler resolves an `IUnitOfWork` that is neither the request's instance, nor A's, nor B's; and B's own resolution is unaffected by A's suppression.
  **The synchronous path requires an explicit restore, and one of its two consequences is observable.** `Parallel.ForEach` partitions the source and gives each worker task a **range** of items; the worker then invokes the body in a loop. `ExecutionContext` is captured and restored per **worker task**, not per body invocation — so an `AsyncLocal` write inside the body for subscriber 1 is **still current when the same worker calls the body for subscriber 2**. With a handful of cheap subscribers, one worker taking several of them is the ordinary case, not an exotic one. Two consequences follow, and they are not of equal standing:
  (i) *Mechanism, not a detectable failure.* Without an explicit restore, subscriber 1's suppression is still set when subscriber 2's body runs on that worker. This is **not observable**: under FR-8 subscriber 2 must be suppressed anyway, so a leaked flag is indistinguishable from its own correct one, and OOS-14 forecloses the only alternative reading by denying that a nested pipeline ever re-enters its parent subscriber's scope. No Acceptance Criterion can or should assert against it — it is stated here because it is *why* the restore must be explicit rather than inherited from `ExecutionContext`.
  (ii) *The observable failure mode.* Establishing suppression **around** the loop in the caller's own flow leaves the caller suppressed after `Publish` returns. That is detectable, and AC-39's leak clauses detect it: a `Send` and a `Post` issued by the controller after the publish must resolve from the request scope. **Setting it inside a body and never restoring it does *not* reach the caller** — although `Parallel.ForEach` may inline bodies on the **calling** thread, the runtime captures and restores `ExecutionContext` per **replica**, including the replica it inlines there, so a body-level write is confined to the worker and shows up only as (i)'s unobservable cross-body leak. That is why the caller-flow failure mode is the bracket's *placement* and not a missing restore inside it. The same reasoning applies to the resolution-time bracket (a): the build loop runs entirely on the caller's thread, so a suppression set for one subscriber's build persists into the next subscriber's build unless it is explicitly restored.
  *Note (no ordering, no guaranteed overlap):* `Parallel.ForEach` neither orders the bodies nor guarantees that two of them overlap — one worker may run every body sequentially. No requirement or Acceptance Criterion on the sync path may depend on subscriber ordering, and none may require overlap in order to pass (contrast the async path, where AC-12 does assert overlap).
  *Note:* this FR deliberately makes **no** claim that a nested pipeline re-enters its parent subscriber's scope. Per the lifetime model, `Scoped` is owned by the pipeline, and a nested `Send` is a new pipeline.

#### Group B — the seam

- **FR-10 — A container-agnostic scope seam exists in `Paramore.Brighter`.** Brighter core must express "a unit of work begins here and ends here" through the types `IAmAScope`, `IAmAScopeProvider` and `ScopeAffinity` (values `JoinAmbient` and `AlwaysNew`) — these exact names (D4). Core must never see or expose a service provider, and the ambient must remain private to the packages **outside** `Paramore.Brighter` — it is not private to the container package, because under FR-17 and NFR-2 the ASP.NET ambient lives in its own package and under NFR-7/AC-35 a third party may supply one from any assembly.
  **Division of labour (D11).** The container package **always creates and owns the `IServiceScope`** a `Scoped` pipeline resolves from. `IAmAScopeProvider` is the **ambient source**: it answers "is there an ambient here that this pipeline may adopt?" and nothing more. It is therefore never required for a pipeline to have a pipeline scope — the unregistered case (FR-11), the null-returning case (FR-24.2) and the stale-ambient case (FR-23) all collapse onto one path: *the container package creates and owns one*. No default `IAmAScopeProvider` is registered, so registering the ASP.NET one never produces a duplicate (FR-24.3).
  **The ambient query (D17).** `IAmAScopeProvider`'s single member is the ambient query, working signature `IAmAScope? GetAmbient(ScopeAffinity affinity)` — the *member name* is a working name (C-11), its *contract* is not. It is called **exactly once** by every pipeline that takes a pipeline scope (FR-27.1), it carries **that pipeline's** affinity, and it returns either an ambient the pipeline may adopt or nothing. `ScopeAffinity.AlwaysNew` means exactly one thing — *do not adopt an ambient*: a `GetAmbient(AlwaysNew)` call must neither consult nor adopt an ambient and must return nothing, and the container package creates and owns the pipeline's DI scope exactly as it does in every other case. **That obligation is stated on the provider and enforced on Brighter's side.** `IAmAScopeProvider` is a public extension point implementable by anyone (NFR-7, OOS-3), so Brighter must not depend on a provider honouring it: an ambient returned for an `AlwaysNew` ask must be **ignored**, and the container package creates and owns the pipeline scope regardless. Both halves are required — without the provider obligation "must not consult" has no contract, and without Brighter's guard a third-party provider could defeat FR-8's per-subscriber isolation. The ignore half is specified as a provider failure mode in **FR-24.4** and discharged by AC-11. **The call is still made (D16)**, so that a pipeline's adoption decision, and the affinity it carried, are observable — which is what AC-13 and AC-46 assert. Skipping the call for `AlwaysNew` pipelines would leave FR-27.2's decline-to-adopt rule with no observable at all.
  **The adopted case's hand-off.** Under C-1, adopting can only mean *resolving directly from the caller's provider*, and NFR-1 forbids `IServiceProvider` on any `Paramore.Brighter` interface — so `IAmAScope` cannot carry one. The division is therefore: the container package resolves the pipeline's artefacts and dependencies from the ambient the provider offered, and the contract by which an ambient exposes a resolution source to it is a **non-core** type. Fixing that contract's shape is design work (C-13); what is required here is that it exist outside core and be implementable by any assembly, so the ASP.NET package (FR-17) and a test or third-party provider (AC-35, NFR-7) participate on the same terms.
  Ambient **suppression** is a separate property, required for `Publish` subscriber pipelines only and required there irrespective of their lifetimes, including subscribers whose pipelines take no pipeline scope at all (FR-8, FR-27.3) — so it cannot be expressed as an argument to, or a return value of, the ambient query. How suppression is expressed is design work (C-13); what is fixed here is the observable rule that registering an `IAmAScopeProvider` adds adoption and changes nothing else.
  *Example:* a test double implementing `IAmAScopeProvider` in a test assembly that does not reference `Microsoft.Extensions.DependencyInjection` can record every `GetAmbient` call — the `ScopeAffinity` each pipeline asked with, and whether an ambient was offered — and can be used to assert FR-8's per-subscriber `AlwaysNew` and FR-27's rules. It does not supply the resolution scope; the container package does.

- **FR-11 — With no scope provider registered, no pipeline adopts, but every pipeline still gets a real scope.** Two distinct requirements:
  (a) **No adoption.** With no `IAmAScopeProvider` registered, no pipeline consults or joins any ambient; the affinity option is irrelevant. Adoption behaviour is exactly as before this change.
  (b) **A real owned pipeline scope is still created.** Per D11 this is the container package's job in every case, not the provider's: it must create and own a genuine `IServiceScope` for every pipeline that has a `Scoped` participating factory (FR-27.1 fixes which pipelines those are), because FR-1, FR-2 and FR-3 apply unconditionally under D3 and cannot be satisfied without one — a container-`Scoped` dependency resolved from the root provider is either a process-wide captive instance or, with `ValidateScopes` on, an `InvalidOperationException`. "No-op scope" describes only the *adoption decision*, never the absence of a DI scope — every `Scoped` pipeline gets a real one.
  This FR governs adoption only; it does **not** preserve the pre-change caching of `Scoped` mappers, which FR-1 and FR-20 change unconditionally under D3.
  *Example:* an application that uses `AddBrighter(...)` alone, with no new registration and no options change, resolves `Send`, `Publish`, `Post` and consumption from Brighter-created scopes exactly as today — while a `Scoped` mapper is now per pipeline rather than per process, and a `Scoped` dependency shared by a mapper and its transforms is one instance for that pipeline (FR-3).

- **FR-12 — Brighter never disposes a borrowed scope.** When a pipeline adopts an ambient scope, Brighter must not dispose it, must not dispose any instance resolved from it, and must leave it usable after the pipeline completes.
  *Example:* opted in, a controller action calls `Send`, then — after `Send` returns — resolves a `Scoped` service from `HttpContext.RequestServices` and uses it successfully; the request's `DbContext` is not disposed, and the same `DbContext` instance the handler saw is still live.

- **FR-13 — Brighter disposes every scope it created.** When a pipeline creates its own pipeline scope — not opted in, or opted in with no ambient available, or a `Publish` subscriber that has a `Scoped` participating factory (FR-27.1), or a pipeline nested inside one — Brighter must release that scope when the pipeline completes, subject to FR-9's release-timing clause for `Publish` subscribers, and must therefore dispose the container-`Scoped` instances resolved from it.
  **Disposal failure on a pipeline that succeeded.** Where releasing an **owned** pipeline scope throws — `IAmAScope.Dispose()`/`DisposeAsync()`, or the underlying container scope's disposal, on a pipeline whose work otherwise completed normally — the failure must be logged at `Error` and swallowed, and the caller's result returned unchanged. The failure must not be latched: a subsequent pipeline behaves normally. (The failed-*build* case is FR-5; a borrowed scope is never disposed at all, FR-12.) This rule lives here rather than among the scope-provider failure modes (FR-24) because, per **D11** and **D17**, the only scope Brighter ever disposes is one the container package created and owns — the provider supplies no disposable scope, so its disposal cannot be a provider failure mode. Discharged by AC-33.
  *Example:* not opted in, a `Send` whose handler takes a `Scoped` `IDisposable` dependency; that dependency's `Dispose` has been called by the time `Send` returns.

- **FR-24 — Scope provider failure modes are defined.** `IAmAScopeProvider` is a public extension point (NFR-7, OOS-3), so its failure modes are reachable from user code and must be specified:
  1. **The ambient query throws.** `GetAmbient(...)` (FR-10, D17) throws — the exception must propagate to the caller of `Send`/`Publish`/`Post` unwrapped; a misconfigured container is a startup-class error and must not be silently degraded to "no ambient".
  2. **The provider offers no ambient**, including by returning `null` from `GetAmbient(...)` — treated exactly as the unregistered case (FR-11(a)): no adoption, and the container package creates and owns the pipeline scope as it always does (FR-10, D11). Logged once at `Warning` **per Brighter container per provider implementation type**, per the diagnostic model below. **This mode is evaluated on `JoinAmbient` asks only.** An `AlwaysNew` ask that returns nothing is FR-10-*conforming* behaviour — it is what a correct provider must do (and what the built-in ASP.NET provider does under `AddBrighterRequestScope(ScopeAffinity.AlwaysNew)`, the gesture FR-25.11 prescribes for registering the ambient source without opting in) — and is **never** logged. Without this carve-out the default affinity (`AlwaysNew`, FR-14) would make correct operation warn on every ask. The mode is nonetheless **not** confined to faulty providers, and the heading of FR-24 should not be read as saying it is: a conforming provider with nothing to offer reports here too — the ASP.NET provider on a `JoinAmbient` ask made where there is no current `HttpContext` (**FR-18**) is the ordinary instance of it, and from Brighter's side that is indistinguishable from a provider that should have offered something. So the entry is **diagnostic rather than a fault report**: it records that the host opted in and no ambient was found, it is latched once per Brighter container per provider implementation type like the other two (**D19**), and it never rises above `Warning`. "Unusable" is deliberately not this mode's word — an ambient that *was* offered and then fails its usability probe is FR-23's, per the exclusivity rule below.
  3. **More than one ambient source is registered.** Brighter itself registers none (D11), so this can only arise from two application registrations — the ASP.NET package plus a hand-rolled provider, or two hand-rolled ones. So that a duplicate is both *visible to validation* and *resolved predictably*, `IAmAScopeProvider` must be registered with a plain `services.AddSingleton<IAmAScopeProvider, T>()` on **every** registration path, including FR-17's extension — **not** `TryAddSingleton`. Two consequences follow, and both are required:
     - **Resolution.** Multiple descriptors for the service type coexist, and MS DI resolves `IAmAScopeProvider` to the **last unkeyed** descriptor registered. The last unkeyed registration wins; a keyed descriptor for the service type is resolved only by an explicit keyed request, which Brighter never makes, so it is never the effective provider and does not enter this rule's distinctness set. (`TryAdd` would make the first win but would also leave the second descriptor — and therefore the duplicate — absent from the collection entirely, so nothing could be reported. The two clauses of this rule need the same mechanism, and this is it.)
     - **Reporting.** When the service collection holds unkeyed descriptors for `IAmAScopeProvider` with **more than one distinct implementation type**, `ValidatePipelines()` must report a warning that names every registered implementation type, identifies the last-registered unkeyed one as the effective provider, and names `docs/guides/lifetimes-and-scoping.md` (the same obligation FR-22 imposes on its own messages). Registering the *same* implementation type more than once is idempotent in effect and is **not** a finding. Where a descriptor was registered by factory delegate or instance and has no statically known implementation type, the message names its registration position and the runtime type where one is available.
     Detection is evaluated against the service collection **as it stands when `ValidatePipelines()` is called**, which snapshots its inputs at that point (`BrighterPipelineValidationExtensions.cs:47-52`, `:64-69`). A provider registered *after* that call is therefore not seen; that limitation is recorded in C-15 and the guidance remains "call `ValidatePipelines()` last".
  4. **The provider ignores the affinity.** A provider returns an ambient for an `AlwaysNew` ask, contrary to FR-10. Brighter must **ignore** the returned ambient and create and own the pipeline scope as it does for any `AlwaysNew` pipeline; the pipeline must not adopt. No exception is thrown and no validation error is raised — the guard is a fail-safe, not a validation, because the condition is only observable at run time — but it is logged once at `Warning` per Brighter container per provider implementation type (**D19**), naming that provider's implementation type, since it is a defect in that provider. This mode exists because `IAmAScopeProvider` is a public extension point and FR-8's per-subscriber isolation (ADR 0039, **D6**) must not be defeasible by a third-party implementation. Discharged by AC-11.
  **The diagnostic model for these modes.** Three rules in this document require a latched `Warning` naming a provider implementation type — FR-23 (an ambient offered but unusable, whether stale or the root provider), FR-24.2 (no ambient offered) and FR-24.4 (an ambient offered for an `AlwaysNew` ask and ignored). They are **three distinct diagnostics, not one**, and the following is required of all three so that an implementation and a test can tell them apart:
     - **Each is latched independently**, per (condition, provider implementation type), and each latch is scoped to the **Brighter container** — the host's root service provider — rather than to the process (**D19**). A provider that both returns nothing on some asks and violates the affinity on others produces one `Warning` for each condition, not one in total. Container scoping is what every counting Acceptance Criterion relies on: an application builds one host, so it is indistinguishable there from once per process; a test process builds several, and each host latches afresh, so a count asserted by one AC — or by one branch of one AC — is never silenced by an AC that ran before it. A latch static to the process would make AC-31's `AlwaysNew` branch vacuous and AC-11's third branch unsatisfiable by a *correct* implementation, since each re-uses one provider implementation type across the branches that assert a count.
     - **Each message must name the condition it reports**, in terms a capturing `ILoggerProvider` can discriminate on: *no ambient offered*, *ambient offered but unusable* and *ambient offered for an `AlwaysNew` ask and ignored* respectively. Naming only the provider type is not sufficient, because all three do that.
     - **The conditions are mutually exclusive on a given ask.** In particular a stale ambient is reported under **FR-23 only** and is *not* also reported under FR-24.2. The overlap is real and survives FR-24.2's retitling, but it is not the word "unusable" that creates it: FR-23 instructs that a failed usability probe be **treated exactly as "no ambient"**, which is FR-24.2's condition verbatim. That treatment governs *adoption and scope creation only* and does not extend to the diagnostic, where FR-23 is the more specific rule and it wins. This is what makes **AC-29's** "exactly one `LogLevel.Warning`" satisfiable at all: without it a stale ambient would be reported twice, under FR-23 *and* under FR-24.2, and AC-29's "no entry naming either of FR-24's other two conditions" would be false. AC-31 needs no tiebreak — a `null` return is unambiguously FR-24.2's condition and no other rule competes for it. The remaining pair is settled the same way: an ambient returned for an `AlwaysNew` ask is **ignored before it is probed for usability**, so **FR-24.4 wins over FR-23** on such an ask — a provider that violates FR-10 by returning a *stale* ambient for an `AlwaysNew` ask is reported under FR-24.4 only, and never additionally under FR-23. The evaluation order this fixes is **FR-24.4, then FR-23, then FR-24.2**, and it settles all three pairs; FR-24.2 against FR-24.4 needs no rule at all, being exclusive by construction, since either something was returned or nothing was.
  **Not a provider failure mode: disposal.** Per **D11** and **D17** the provider supplies no disposable scope — every scope Brighter disposes was created and is owned by the container package — so a throwing `IAmAScope.Dispose()`/`DisposeAsync()` on a pipeline that otherwise succeeded is specified in **FR-13**, not here, and is discharged by AC-33. (The failed-build case is FR-5; a borrowed scope is never disposed, FR-12.)

- **FR-27 — Where a pipeline's factories have different lifetimes, the seam's behaviour is determined.** A pipeline may be served by more than one **participating factory** — a transform pipeline by both the mapper factory and the transformer factory (C-19) — and those factories may have different configured lifetimes. Three rules make the single per-pipeline ambient query (FR-10, NFR-6) determined in **every** configuration, including the ones FR-22.2 would reject but that were never validated because `ValidatePipelines()` was not called (C-15):
  1. **When a pipeline takes a pipeline scope, and therefore makes an adoption decision.** A pipeline takes exactly one pipeline scope, and asks the ambient source — FR-10's `GetAmbient(ScopeAffinity)` — **exactly once**, when **at least one** of its participating factories has the configured lifetime `Scoped`.
     **The ask is unconditional for such a pipeline (D16).** It is made even when the pipeline's affinity is `AlwaysNew`, whether because the affinity option says so, because the pipeline is a `Publish` subscriber (FR-8), or because rule 2 below declined to adopt. An `AlwaysNew` ask must neither consult nor adopt the ambient and returns nothing (FR-10); its purpose is that the decision, and the affinity it carried, are **observable**. Without it, rule 2's decline-to-adopt behaviour would have no observable of its own and two conforming implementations could differ in what a recording provider sees — which is precisely what AC-13 and AC-46 pin.
     A pipeline none of whose participating factories is `Scoped` takes no pipeline scope and asks nothing — `Transient`'s per-resolution scope (ADR 0067) and `Singleton`'s root resolution do not pass through the seam and are unchanged by this work (C-6, OOS-7). The seam expresses pipeline scoping for `Scoped`, which is the lifetime FR-1 to FR-3 govern. (This governs the *pipeline scope*; suppression is separate and unconditional for subscribers — rule 3.)
  2. **Which affinity that decision carries.** A pipeline's adoption decision is `JoinAmbient` **if and only if** the affinity option is `JoinAmbient`, at least one participating factory is `Scoped`, and **no** participating factory is `Transient`. A pipeline mixing `Scoped` with `Transient` therefore does **not** adopt: adopting for only part of a pipeline — half of it in the caller's transaction and half not — is the failure mode D8 exists to prevent, so the fail-safe is to create its own pipeline scope. `Singleton` participants are ignored by this test, exactly as FR-22.2 ignores them. A `Publish` subscriber's pipeline is always `AlwaysNew` regardless (FR-8).
  3. **Suppression is a subscriber property, not a consequence of affinity.** Ambient suppression (FR-8, D6) is required for, and only for, a `Publish` subscriber's pipeline and everything nested inside it. A non-subscriber pipeline that creates its own scope — because it is not opted in, because no usable ambient exists (FR-18, FR-23), or because rule 2 declined to adopt — does **not** suppress the ambient for pipelines nested inside it; each such nested pipeline consults the ambient on its own terms. Conversely, a subscriber's pipeline must suppress **irrespective of its own lifetimes**: a subscriber pipeline with no `Scoped` participant takes no pipeline scope under rule 1 yet must still suppress, because a pipeline nested inside it may be `Scoped`. This is why suppression cannot be expressed as a property of the ambient query (FR-10, C-13), and why FR-9 requires it at both the resolution-time and the execution-time bracket.
  *Example (rule 2):* opted in with `MapperLifetime = Scoped` and `TransformerLifetime = Transient`, a `Post` from a controller resolves its mapper from a Brighter-created scope, not the request scope — and per D12 that holds even if the mapper declares no transforms at all. `ValidatePipelines()` would reject that configuration (FR-22.2); this rule fixes what happens when it was never called.
  *Example (rule 3):* opted in, a `Send` whose handler issues a nested `Post` — the nested transform pipeline may adopt the request scope, because a `Send` is not a subscriber. The same nested `Post` inside a `Publish` subscriber may not (FR-8).
  *Derives from:* FR-8, FR-21 and C-19; it closes the gap those three leave open when the three lifetimes differ.

#### Group C — the opt-in

- **FR-14 — One flag governs scope affinity for both pipeline kinds.** A single option on `IBrighterOptions`/`BrighterOptions` selects the default scope affinity for **both** handler pipelines and transform pipelines. The uniform rule is: "`Scoped` means per pipeline; when opted in, a `Scoped` pipeline joins the ambient scope if one exists." Working name and shape for the FRs and ACs below (**provisional — see C-9**):
  `ScopeAffinity DefaultScopeAffinity { get; set; } = ScopeAffinity.AlwaysNew;`
  *Example:* setting the option to `JoinAmbient` changes the resolution source of both a `Send`'s handler pipeline and a `Post`'s transform pipeline; there is no way to opt one in and the other out.
  *Derives from:* D2.

- **FR-15 — Default is `AlwaysNew`, and behaviour under it is identical to today.** With the option left at its default, no pipeline adopts any ambient, whether or not an `IAmAScopeProvider` is registered.
  *Example:* an ASP.NET application that adds the new package's **PackageReference but does not call its registration extension** sees a `Send` from a controller resolve a `Scoped` handler dependency that is **not** the request's instance — exactly as before this change. (An application that *does* call the extension is opted in by FR-17 unless it passes `ScopeAffinity.AlwaysNew` to the extension, which is AC-18.)

- **FR-16 — Pipelines in one HTTP request share the request scope when opted in.** Opted in, with a request-scope ambient available and **every participating factory of each pipeline concerned configured `Scoped`** — for a transform pipeline that means both `MapperLifetime` and `TransformerLifetime`, per FR-27.2 and D12; for a handler pipeline, `HandlerLifetime`. (A single `Transient` among them makes the pipeline decline to adopt, and the clauses below would then be false.)
  (a) two `Post` calls made within a single HTTP request resolve **one** `Scoped` mapper instance across both; and
  (b) a `Scoped` dependency injected into both a mapper and a handler reached by `Send` in the same request is **one** instance, because both pipelines resolve from the same borrowed request scope. This requires all three of `HandlerLifetime`, `MapperLifetime` and `TransformerLifetime` to be `Scoped`: the `Send`'s handler pipeline and the `Post`'s transform pipeline must *both* adopt, and the transform pipeline will not adopt while `TransformerLifetime` is `Transient`.
  (c) a `Scoped` dependency the **caller** has already resolved — the controller's own `DbContext`, say — is the **same** instance a handler reached by `Send` resolves, so work the handler does through it is work in the caller's transaction. This is clause (b) extended across the call boundary rather than a second mechanism: (b) shares an instance between two Brighter pipelines, (c) shares it between the caller and a Brighter pipeline, and both hold for the one reason that the pipeline's scope *is* the request scope. It is stated separately because it is the clause applications depend on and the only one whose failure is **silent** (**C-21**).
  Clause (b) is the opted-in producer exception to C-3, which otherwise holds.
  *Example:* a controller action calls `Post(commandA)` then `Post(commandB)`, both mapped by `Scoped` mappers of the same type; the two mapper instances are reference-equal, and neither is disposed when the action returns (the request scope owns them — FR-12).
  *Example (clause c):* a controller writes an entity through its own `Scoped` `DbContext`, opens a transaction on it, and calls `Send(command)`; the handler injects a transaction provider over that same `DbContext` and calls `DepositPost(event, provider)`. The outbox row and the entity are written on one connection inside one transaction, and commit or roll back together. Under `AlwaysNew` they are two `DbContext` instances and two transactions, and nothing reports it (**C-21**, **AC-52**).
  *Derives from:* D2 and **D7** — under adoption the borrowed scope, not the pipeline, owns the artefact. This is the faithful reading of the lifetime model: if the pipeline's scope *is* the request scope, the request owns the instance. Brighter's own per-type instance identity must therefore be associated with the borrowed scope, which is what FR-26 bounds.

- **FR-17 — The ASP.NET ambient ships in a new package and registration is the only wiring.** A new package (working name `Paramore.Brighter.Extensions.AspNetCore`) supplies an `IAmAScopeProvider` backed by `IHttpContextAccessor` that resolves from `HttpContext.RequestServices`. Calling that package's registration extension registers the provider and selects the default affinity. **The extension takes the affinity as an explicit argument** (**D13**), defaulting to `JoinAmbient`: `AddBrighterRequestScope()` opts in, `AddBrighterRequestScope(ScopeAffinity.AlwaysNew)` registers the ambient source without opting in. The exact member name is a working name (C-11); that the affinity is an argument is not. **No middleware component may be required**, and no per-request call site may be required. The extension does **not** alter any lifetime (FR-21, FR-22 — an inert combination is reported, not silently corrected). **There is no ordering rule, and that is the point** (closing C-10). Ordering cannot be made to work: only `AddBrighter(Action<BrighterOptions>)` runs an `IOptions` pipeline, `AddConsumers(Action<ConsumersOptions>)` has already invoked the application's delegate by the time it returns (`ServiceActivator.Extensions.DependencyInjection/ServiceCollectionExtensions.cs:36-38`), and both `Func` overloads defer to first resolution — so "later" is not a registration-order concept on three of the four paths, and without a sentinel those paths cannot tell "the application chose `AlwaysNew`" from "the application left the default". Taking the affinity as an argument removes the question entirely. No tri-state or "was it explicitly set" sentinel is required, and none may be introduced — the option stays a plain non-nullable value as FR-14 specifies. **The extension's argument is the value, and the extension wins (D18).** Because the argument must reach the object `IBrighterOptions` resolves to on **all four** registration paths — three of which run no `IOptions` pipeline at all — the write necessarily lands *after* every application-supplied options delegate has run. The extension therefore wins unconditionally, in every registration order and on every path. **One thing defeats that, and it is reported rather than silent**: an application that registers `IBrighterOptions` **itself** — *before* Brighter, winning the `TryAddSingleton`, or *after*, winning resolution as the last unkeyed descriptor — makes the object the factories read one Brighter never produced, so the write-through never runs and the extension's argument is lost, on every path and in either ordering, including the extension-before-`AddBrighter` ordering **AC-48** requires to work. That is an error under **FR-22.4**, not an accepted silence. An application that *also* assigns the affinity option in its own configuration while calling the extension gets the **extension's** value, and that combination is a **configuration error**: the way to select an affinity while using the extension is to pass it to the extension. This is **documented rather than validated**, and deliberately so — with no sentinel (banned above), an implementation cannot distinguish "the application explicitly assigned `AlwaysNew`" from "the application left the property at its `AlwaysNew` default", so any rule comparing the pre-extension value with the argument would fire falsely on the ordinary opt-in (`AddBrighterRequestScope()` on a default host). The guidance page states the rule (FR-25.11); AC-48 pins the behaviour in both directions.
  **Calling the extension more than once is determined, and reported.** A repeated call is a configuration error the extension must not throw on. The **last** call's affinity argument is the effective one, matching FR-24.3's last-registration-wins rule for the provider, so both halves of a repeated gesture resolve the same way: a host cannot end up carrying one call's affinity and another call's provider. So that a repeat is *visible to validation* as well as determined, whatever mechanism carries the affinity must leave **every** call's descriptor in the collection — the same obligation, imposed for the same reason, that FR-24.3 places on `IAmAScopeProvider`, and for the same reason a first-wins registration is banned there: it would resolve predictably but leave nothing to report. Where the collection holds affinity-carrying descriptors with **more than one distinct affinity value**, `ValidatePipelines()` must report a warning that names every affinity registered, identifies the last-registered unkeyed one as effective, and names `docs/guides/lifetimes-and-scoping.md` (the same obligation FR-22 and FR-24.3 impose on their own messages). Repeated calls carrying the **same** affinity are idempotent in effect and are **not** a finding — the exclusion FR-24.3 makes for a repeated identical provider registration, made here for the identical reason. Detection is evaluated against the service collection as it stands when `ValidatePipelines()` is called, which snapshots its inputs at that point (C-15), exactly as FR-24.3's is. This is the one FR-17 configuration error that *is* validated, and it is validated precisely because it needs no sentinel: two differing affinity values are distinguishable from a default without knowing whether either was explicitly assigned, which is what makes the conflict in the paragraph above undetectable and this one detectable. Discharged by **AC-49**.
  **An override whose value cannot be read is reported as such, so the rule above cannot be defeated silently.** The rule above reads affinity values off descriptors without resolving anything, so it can only see a descriptor that supplies an `ImplementationInstance`. An override registered by factory delegate supplies none: it still takes effect, because the write-through resolves it, but it contributes nothing to the distinctness set and a conflicting repeat carrying it goes unreported. Where the collection holds an affinity-carrying descriptor that supplies no instance, `ValidatePipelines()` must therefore report a **warning** that states that an affinity override is registered by factory delegate, that its value cannot be read without resolving so a conflicting repeat carrying it cannot be reported, and that the remedy is to register the override as a constructed instance — and it must name `docs/guides/lifetimes-and-scoping.md`, as every message these rules produce does. It is a warning rather than an error because nothing about such a host is broken: the affinity the registrar passed is the affinity the factories read, and what is lost is a diagnostic rather than the opt-in. The condition is a property of the *registration shape*, which is readable, rather than of the value, which is not — the same division FR-22.4 draws for the same reason. Discharged by **AC-53**.

  **The opt-in must reach the object the factories read, on all four registration paths.** Brighter's factories read `IBrighterOptions` (`ServiceProviderMapperFactory.cs:44`), and only **one** of the four entry points routes that object through the `IOptions` pipeline: `AddBrighter(Action<BrighterOptions>)` calls `services.AddOptions<BrighterOptions>()` + `services.Configure(configure)` (`ServiceCollectionExtensions.cs:69-71`) and binds `IBrighterOptions` to `IOptions<BrighterOptions>.Value` (`:74-75`). The other three bind `IBrighterOptions` directly and run no configuration pipeline at all: `AddBrighter(Func<IServiceProvider, BrighterOptions>)` (`:97`), `AddConsumers(Action<ConsumersOptions>)` (a pre-built instance, `ServiceActivator.Extensions.DependencyInjection/ServiceCollectionExtensions.cs:38`) and `AddConsumers(Func<IServiceProvider, ConsumersOptions>)` (`:88`) — and all four route through `BrighterHandlerBuilder`, so all four are complete Brighter hosts. A bare `services.Configure<BrighterOptions>(…)` contributed by the extension therefore never reaches the options object the factories read on three of the four paths, which would make the opt-in fail **silently and totally** — in every consumer host, and in any producer host using the `Func` overload. It is a requirement of this work that the affinity **passed to the extension** takes effect on the object the factories read, on **all four** paths (AC-45) — save where the application registered that object itself, the one case FR-22.4 reports rather than serves. *How* — bringing the other three paths onto `IOptions`, or applying the affinity inside Brighter's own `IBrighterOptions` registration — is design work (C-13); that it must hold on all four is not. What the mechanism may **not** be is a write to whatever object `IBrighterOptions` happens to resolve to, whoever registered it: an application's own options object is the application's, and AC-48's before-ordering leaves no descriptor to wrap in any case. That is why an application-registered `IBrighterOptions` defeats the opt-in rather than receiving it, and why FR-22.4 reports it. This is a distinct hazard from C-12's `TryAdd` first-wins, and both are recorded there.
  *Example:* an application adds the package reference, sets all three of `HandlerLifetime`, `MapperLifetime` and `TransformerLifetime` to `ServiceLifetime.Scoped` (FR-22.2 makes that choice joint), and adds one registration call in `Program.cs`; a `Send` from a controller then resolves the handler's `Scoped` `DbContext` as the same instance the controller holds. Passing `ScopeAffinity.AlwaysNew` to that same call instead registers the ambient source but adopts nothing — in any registration order, on any of the four entry points.
  *Derives from:* D1.

- **FR-18 — No `HttpContext` means fall back to a new, Brighter-owned scope.** When the ASP.NET provider is registered but there is no current `HttpContext` — a hosted service, a background thread, application startup — a pipeline must create and own a new pipeline scope, exactly as if not opted in. This must not throw, must not log at `Error` or above, and must not resolve from the root provider directly. Where the ask carried `JoinAmbient`, the provider was asked and offered nothing, which **is** FR-24.2's condition: **one `Warning` per Brighter container per provider implementation type is emitted** (**D19**), and it is a diagnostic recording that the host opted in and no ambient was found rather than a report of a fault — it is the only observable difference from the not-opted-in case, and resolution, identity and disposal are unaffected. Under `AlwaysNew` the ask is carved out of FR-24.2 and nothing is logged at all.
  *Example:* an `IHostedService` in the same ASP.NET application calls `Send`; the handler's `Scoped` dependency is a fresh instance, disposed when `Send` returns.

- **FR-23 — A present-but-unusable ambient falls back, and says so.** A provider may offer a resolution source that is non-null but whose DI scope has already been disposed. A provider that **captures** a scope rather than reading it afresh on every ask is the general case: an `AsyncLocal`-backed provider for non-ASP.NET hosts (NFR-7, AC-35), a provider that stores `HttpContext.RequestServices` at construction, or a custom `IHttpContextAccessor` that does not clear itself at end of request. (ASP.NET Core's **built-in** `HttpContextAccessor` is not one of them: it holds an `AsyncLocal` over a shared holder object and clears that holder when the request ends, so a flow that outlives the response — a fire-and-forget `Task.Run`, or a `Dispatcher` started from within a request — sees a **null** `HttpContext` and therefore no ambient at all. That case is FR-24.2's *no ambient offered*, not this rule.) **A second shape is unusable for a different reason: a resolution source that *is* the container's own root provider** — what a provider that hands back the `IServiceProvider` it was constructed with offers. Nothing about it is stale, and on a container built without `ValidateScopes` every resolution from it succeeds; what it yields is one process-wide instance of each `Scoped` service, disposed by nothing, defeating FR-1 and FR-2. A resolution source that is **the same object as the root provider the container package holds** must therefore be declined on this rule's terms and with this rule's `Warning`. The obligation is stated over object identity so that it is decidable: other handles onto the root — the object `BuildServiceProvider()` returns, or a wrapper over either — resolve the same way, and this rule does not require an implementation to detect them. A pipeline must **probe the ambient for usability before resolving any pipeline instance from it** — a failed probe is treated exactly as "no ambient" **for the purposes of adoption and scope creation; the diagnostic remains this rule's** — then create and own a new pipeline scope (as FR-18), and log at `Warning` **once per Brighter container per provider implementation type** (**D19**), latched independently of FR-24.2's and FR-24.4's conditions (FR-24's diagnostic model). Like FR-24.2 this mode is evaluated on **`JoinAmbient` asks only** — an `AlwaysNew` ask never probes, because an ambient offered for one is ignored first, so staleness there is reported under FR-24.4 instead. It must not surface `ObjectDisposedException` from Brighter's own resolution to the caller, and must not resolve from the root provider directly. This bounds only Brighter's resolution: a *handler* that itself captures and uses `HttpContext.RequestServices` after the request has ended is outside Brighter's control and may still throw. This is the third case C-7 must accommodate: an ambient was offered and declined.
  *Example:* a host registers a provider that captured the request's `IServiceProvider` and keeps offering it after the request scope has been disposed; a `Send` on that host resolves a fresh `Scoped` dependency, disposes it, and logs one `Warning`. A second such `Send` in the same host logs no further `Warning`.

- **FR-19 — The flag is inert on the consumer side.** Setting the affinity option to `JoinAmbient` must produce **no observable difference in resolution, instance identity or disposal** on the consumer side: every consumer pipeline creates and owns its pipeline scope. There is no permitted difference in log entries either. A consumer pipeline's ask carries `AlwaysNew` however the option is set (C-14), so FR-24.2's *no ambient offered* condition is never reached — that mode is evaluated on `JoinAmbient` asks only, and an `AlwaysNew` ask that returns nothing is never logged — and neither is FR-23's, which is `JoinAmbient`-only for the same reason. A host with a conforming ambient source therefore records nothing at all on the consumer side under either setting, however many messages are consumed, and where no ambient source is registered there is no difference either (FR-11(a)). The one entry a consumer host can record comes from a *non*-conforming provider that returns an ambient for an `AlwaysNew` ask: FR-24.4's once-per-Brighter-container `Warning` (**D19**), which reports that provider's fault rather than a difference the flag makes. This holds because the pump publishes no ambient (D0b) and because the ask is `AlwaysNew` whatever flow the pump was started on, so it holds for a `Dispatcher` started from within a request as well (**AC-55**).
  *Example:* a consumer host with `DefaultScopeAffinity = JoinAmbient` and the ASP.NET package registered (a mixed web+consumer host) consumes 100 messages; each message's transform pipeline and handler pipeline resolve fresh `Scoped` instances, disposed per pipeline, identical to `AlwaysNew`. There is no difference at all over the whole run, in log output as in everything else: the consumer ask carries `AlwaysNew`, so the provider is asked, offers nothing, and nothing is recorded.

- **FR-20 — Clean break on `MapperLifetime.Scoped`, documented as breaking.** No compatibility flag is provided for the old "cache for the life of the process" behaviour. The change must be called out as a **breaking behavioural change** in `release_notes.md`, with the migration stated: applications that relied on cross-pipeline caching under `Scoped` must change to `Singleton`.
  *Example:* documentation states that a `Scoped` mapper holding a warmed lookup table across messages must be re-registered with `MapperLifetime = Singleton`; a `Scoped` mapper holding per-message state needs no change and is now correct.
  *Derives from:* D3.

- **FR-21 — Scope affinity applies to `Scoped` only.** The affinity option has **no effect** on a factory whose configured lifetime is `Transient` or `Singleton`. A `Transient` handler, mapper or transform continues to get its own per-resolution scope (ADR 0067) and a `Singleton` continues to be resolved once for the process, under either affinity setting. Adoption is a property of the `Scoped` lifetime, because only `Scoped` binds its instances to the pipeline's scope.
  *Example:* an opted-in ASP.NET application with `HandlerLifetime = Transient` (the default) sees a `Send` from a controller resolve a `Scoped` dependency that is **not** the controller's instance — identical to `AlwaysNew`. Changing the affinity flag changes nothing until `HandlerLifetime` is `Scoped`.
  *Derives from:* D5, and the lifetime model table above.

- **FR-22 — Unworkable lifetime and opt-in configurations are reported by `ValidatePipelines()`.** Four rules, stated below; rule 1 is the one this requirement began as. Because all three lifetimes default to `Transient` (`BrighterOptions.cs:20`, `:52`, `:69`) and FR-21 makes affinity inert outside `Scoped`, the combination "opted in, nothing `Scoped`" is almost certainly a configuration mistake and must not be silent. Using the existing validation machinery (`BrighterPipelineValidationExtensions.cs:58`), surfaced at host start by **whichever validation host owns validation**: `BrighterValidationHostedService`, or `ServiceActivatorHostedService` when `AddConsumers` has set `ConsumerOwnsValidation = true` (`ServiceCollectionExtensions.cs:60`, `:127`). This distinction is load-bearing: `BrighterValidationHostedService.StartAsync` returns immediately when `ConsumerOwnsValidation` is set (`BrighterValidationHostedService.cs:73`), so in a consumer host it is a no-op — and the `MapperLifetime`/`TransformerLifetime` clauses below are precisely the consumer-relevant ones. The rules must fire under **both** hosts.
  **There is a third case, and it is an accepted gap (D14).** `AddConsumers` sets `ConsumerOwnsValidation = true` (`ServiceCollectionExtensions.cs:60`, `:127`) but does **not** register `ServiceActivatorHostedService` — that type lives in `Paramore.Brighter.ServiceActivator.Extensions.Hosting` and the application registers it. A consumer host that never adds the hosting package therefore has *no* validation host: `BrighterValidationHostedService` defers, and nothing takes over. This work does not change that; it is recorded beside C-15 as a second residual gap in an already opt-in mechanism, and the guidance page must tell consumer applications to register the hosted service (FR-25.10). Every AC that expects a consumer host to validate must register it explicitly (AC-40).
  The rules:
  1. **Error — inert opt-in.** The affinity option is `JoinAmbient` and **none** of `HandlerLifetime`, `MapperLifetime`, `TransformerLifetime` is `Scoped`. The message must name the affinity setting, list all three lifetimes and their values, and state that the opt-in has no effect. (D5)
  2. **Error — mixed `Transient`/`Scoped`.** Taking the three lifetimes and **discarding any that are `Singleton`**, the remainder must all be equal. A remainder containing both `Transient` and `Scoped` is an error **under either affinity setting**. The message must list all three lifetimes and their values and state that the mixed pair do not share pipeline-scoped dependencies. (D8)
     `Singleton` is excluded because the three factories resolve independently and a `Singleton` artefact resolves from the root provider regardless of what the other two are — mixing it changes nothing about the other two. Excluding it is also required for consistency with FR-20, which prescribes `MapperLifetime = Singleton` as the migration for code relying on the old cross-pipeline caching; a rule that forbade `Singleton` alongside `Scoped` would forbid the migration this spec ships.
     *Worked examples:* `{Scoped, Transient, Scoped}` → error. `{Scoped, Singleton, Scoped}` → no finding (discard `Singleton`; remainder `{Scoped, Scoped}`). `{Singleton, Singleton, Singleton}` → no finding (remainder empty). `{Transient, Transient, Transient}` → no finding.
     **Consequence for adopters — the choice is joint.** Because the rule compares all three lifetimes, adopting `Scoped` is not a one-line change: fixing Defect 1 (a per-pipeline `Scoped` mapper) requires setting `HandlerLifetime`, `MapperLifetime` and `TransformerLifetime` **together** — all `Scoped`, or `Scoped` for the kinds that need it and `Singleton` for the kinds that do not. `{Scoped, Scoped, Transient}` is not a valid destination. This consequence must be stated in `release_notes.md` (FR-25.6, FR-25.7) and in the decision guide (FR-25.9), and it is why every Acceptance Criterion in this document states all three lifetimes.
  3. **Warning — captive dependency.** An **artefact** (see Terms) whose configured lifetime is `Singleton` requires a container-`Scoped` service. `GetOrCreateSingleton` resolves from the **root** provider (`ServiceProviderLifetimeScope.cs:151-155`), so that dependency is captive: one instance for the process, or an `InvalidOperationException` when the container's `ValidateScopes` is enabled. The message must name the artefact type and the `Scoped` service it requires. This is a warning, not an error, because a `Singleton` artefact with no `Scoped` dependencies is legitimate and is what FR-20 recommends. (D9)
     **Detection contract.** Fixed here, because each of these choices changes which configurations are reported and two implementations could otherwise both satisfy this rule while disagreeing:
     - **Which constructor** — **the public constructor with the most parameters; where two public constructors have the same parameter count, the type is not inspected.** This is Brighter's own rule, stated in its own terms (**D15**). It deliberately does **not** claim parity with MS DI's selection, which additionally requires the winning constructor's parameter set to be a superset of every other resolvable candidate's, and which treats `IServiceProvider`, `IServiceScopeFactory` and `IEnumerable<T>` as resolvable without a descriptor. The divergence — a warning may be raised against, or missed on, a constructor MS DI would not have chosen — is recorded in C-20.
     - **How deep** — **direct parameters of that constructor only.** A `Singleton` artefact whose `Transient` dependency itself requires a `Scoped` service is equally captive and is deliberately **not** reported. That bounded gap is recorded in **C-20** and pinned by AC-42, so a later implementation cannot widen or narrow it silently.
     - **Which types** — only artefact types **the application supplied**: the mapper, transform and handler types discovered by assembly scanning or registered explicitly. Brighter's own attribute-driven pipeline handlers **and its own transforms** are excluded, and the exclusion must be expressed as a **mechanism, not a list**: any handler type returned by a `RequestHandlerAttribute.GetHandlerType()` (`RequestHandlerAttribute.cs:91`), **or any transform type returned by a `TransformAttribute.GetHandlerType()` (`TransformAttributeBase.cs:17` — the type is `TransformAttribute`; the file name is historic)**, whose defining assembly's **simple name is `Paramore.Brighter`, or begins with `Paramore.Brighter.`**. The trailing dot is part of the rule: a third-party assembly named `Paramore.BrighterExtras` is **not** excluded.
       Both extensions are load-bearing. *Transforms do not go through `RequestHandlerAttribute` at all* — they have their own attribute base — and Brighter ships transforms with constructor dependencies: `ClaimCheckTransformer` (`Transforms/Transformers/ClaimCheckTransformer.cs:62`) takes `IAmAStorageProvider` and `IAmAStorageProviderAsync`, so a host with `TransformerLifetime = Singleton` — an FR-22.2-conformant triple, and one FR-20 actively recommends — and an `AddScoped` storage provider would otherwise be warned against a **Brighter** type, which is exactly the noise the exclusion exists to prevent. *The prefix match rather than an exact assembly name* is load-bearing for the same reason, because Brighter ships transforms outside the core assembly: `JustSayingCompressionTransform` (`Paramore.Brighter.Transformers.JustSaying/JustSayingCompressionTransform.cs:34`, returned by `JustSayingDecompressAttribute.GetHandlerType()` at `:29`) and the MassTransit wrap/unwrap transforms. **Neither half pins the other, and the prefix half cannot be pinned by any Brighter-shipped transform today**: every out-of-core Brighter transform is currently parameterless (`JustSayingCompressionTransform`, `MassTransitTransform`), so it would raise no captive-dependency warning under an exact-name implementation either, and an Acceptance Criterion built on one would pass vacuously. AC-42 therefore pins the transform half with `ClaimCheckTransformer` — in-core, and genuinely dependency-taking — and the prefix half with a transform defined in a `Paramore.Brighter.*`-named **test** assembly, which is the only construction that fails under `== "Paramore.Brighter"` and passes under the prefix rule. The cost of the prefix — an application type living in a `Paramore.Brighter.*` assembly is excluded too — is accepted and recorded in C-20(iii).
       An enumeration would be wrong the day it is written — the sync handlers have async twins (`UseInboxHandlerAsync<>`, `RequestLoggingHandlerAsync<>`, `ExceptionPolicyHandlerAsync<>`, `MonitorHandlerAsync<>`, `FallbackPolicyHandlerRequestHandlerAsync<>`), there are resilience variants (`ResilienceExceptionPolicyHandler<>` and its async twin) and `ValidateRequestHandler<>`/`ValidateRequestHandlerAsync<>`, and more may be added. Brighter's own decorators' dependency graphs are Brighter's responsibility, not the user's, and warning on them would be noise in every async host with `HandlerLifetime = Singleton`.
     - **What is read for each parameter** — the `ServiceLifetime` of the parameter's own descriptor in the snapshot: the **last unkeyed** descriptor for that service type, which is what MS DI resolves, or the last descriptor for that `(service type, key)` pair where the parameter carries `[FromKeyedServices(key)]`, which is what MS DI resolves *there*. Honouring the attribute is load-bearing rather than a refinement: a `Singleton` artefact taking `[FromKeyedServices("k")]` on a parameter whose service type also has an unkeyed `Scoped` registration is correct and builds cleanly, and a rule reading the unkeyed descriptor would report a captive dependency the container never creates. A parameter with no descriptor is not a finding (it is an unresolvable-dependency question, not a captivity one).
     Detection reads the service-collection snapshot and resolves nothing. `ServiceCollectionTransformerResolvabilityProbe` is the precedent for **that technique only** — snapshot the collection and answer questions from it without building a provider — and for nothing more: the whole class is a `HashSet<Type>` of service types plus a `Contains` (`ServiceCollectionTransformerResolvabilityProbe.cs:40-56`), with no constructor and no lifetime inspection. The constructor and lifetime walk this rule needs is new work.
  4. **Error — the opt-in never reached the object the factories read.** An affinity override is registered — FR-17's registration extension was called — and the `IBrighterOptions` the container resolves is **not** the one Brighter's own registration produced, so the write-through FR-17 requires never ran and the affinity the factories read is not the one the extension carried. Brighter registers `IBrighterOptions` with `TryAddSingleton` on all four entry points (`Extensions.DependencyInjection/ServiceCollectionExtensions.cs:74`, `:97`; `ServiceActivator.Extensions.DependencyInjection/ServiceCollectionExtensions.cs:38`, `:88`), so an application or test host that registers its own `IBrighterOptions` **before** Brighter wins that registration; and one that registers it **after**, with a plain `AddSingleton` that does not contest the `TryAdd`, wins *resolution* instead — MS DI resolves a service type to the **last unkeyed** descriptor registered, the same rule FR-24.3 relies on for `IAmAScopeProvider`. Either way the object the factories read is not the one Brighter registered, the override is never applied, and the opt-in is lost **on all four paths, in either ordering of the application's own registration and at any placement of the extension call** — including the extension-before-`AddBrighter` ordering AC-48 requires to work. The message must name the affinity the extension registered, state that the resolved `IBrighterOptions` was supplied by the application rather than by Brighter so the override was never applied, and give the remedy: configure Brighter's options through `AddBrighter`/`AddConsumers` rather than by registering `IBrighterOptions` directly. It is an error rather than a warning because the outcome is the total, silent loss of the opt-in — the failure FR-17's write-through and AC-45 exist to prevent — and because, unlike FR-17's *other* conflict, it is detectable without the sentinel FR-17 bans. (FR-17, FR-14)
     **Detection must not rest on comparing affinity values, and must see both orderings.** An override carrying `AlwaysNew` — the option's own default (FR-14) — is by value indistinguishable from an override that was never applied, so a value comparison would miss exactly the hosts that pass the default and would make the rule's coverage depend on which affinity was chosen. The condition is a property of the *registrations*: an override is present, and the `IBrighterOptions` the container will resolve for Brighter's factories — the **last unkeyed** descriptor for that service type — is not one Brighter registered. It must be the unkeyed descriptor, because Brighter's factories resolve `IBrighterOptions` unkeyed: a rule reading the last descriptor of any kind would raise this error against a host that registered a *keyed* `IBrighterOptions` for its own purposes, whose Brighter registration and write-through both ran correctly. Such a host is not a finding of any kind under this document. Recording the defeat at the point Brighter's own `TryAddSingleton` finds the service already present sees only the *before* ordering and is not on its own sufficient: in the *after* ordering that `TryAdd` succeeds and the defeat is visible only in the collection. Both orderings are readable from the service-collection snapshot the other rules already read (C-15); the mechanism is otherwise design work (C-13), and this document requires only that the condition is evaluated at host start and surfaced through the existing validation result.
  **The four rules are evaluated independently.** Unlike FR-24's three diagnostics, which are mutually exclusive on a given ask, more than one of these rules may fire on one configuration — a host whose application-registered `IBrighterOptions` carries `JoinAmbient` with three `Transient` lifetimes trips rule 1 *and* rule 4 — and each finding is then reported. There is no precedence order among them, and none may be invented.
  **Every message produced by these rules — errors and warnings alike — must name `docs/guides/lifetimes-and-scoping.md`** (FR-25) as the place that explains how to choose a lifetime. A message that tells a user their configuration is wrong without telling them how to make it right is not an acceptable discharge of these rules; per C-18 many affected applications will never have reasoned about lifetime before.
  All errors above are subject to `ThrowOnError` (`BrighterPipelineValidationOptions.cs:47`, default `true`). Where an error is raised with `throwOnError: true` (`BrighterPipelineValidationOptions.cs:47`, default `true`), startup fails with `PipelineValidationException` (thrown by `PipelineValidationResult.ThrowIfInvalid()`, `PipelineValidationResult.cs:52-56`); with `throwOnError: false` the same message is logged at `Error` and startup proceeds.
  **Where these rules are evaluated, and what they read.** The rules require the three lifetimes and the affinity option **as the factories see them** — from the object `IBrighterOptions` resolves to, not from `IOptions<BrighterOptions>.Value`, which FR-17 shows can be a different object on three of the four registration paths. Validation must not pass a configuration the factories will ignore, nor fail one they would have honoured. `PipelineValidator` is constructed today with no access to `IBrighterOptions` (`BrighterPipelineValidationExtensions.cs:88-90`), so that input is new work — but it must **not** be supplied by handing container concepts to core. `PipelineValidator` lives in core (`src/Paramore.Brighter/Validation/PipelineValidator.cs`), whose project references no `Microsoft.Extensions.DependencyInjection*` package and in which `ServiceLifetime` appears nowhere; NFR-1 now forbids changing that. `IAmAPipelineValidator` is already a core interface with a single `PipelineValidationResult Validate()` method (`src/Paramore.Brighter/Validation/IAmAPipelineValidator.cs:38`), so the DI package can contribute a validator — or a validation spec — that knows about `ServiceLifetime` and `IBrighterOptions` while core does not. This document requires only that the rules are **evaluated at host start with those inputs and surfaced through the existing validation result**; which component evaluates them is design work (C-13).
  **Compatibility note.** Rule 2 will fail startup for existing applications that today mix `Transient` and `Scoped` across the three lifetimes *and* call `ValidatePipelines()`. Such configurations work today (with unshared pipeline-scoped dependencies), so this is a second behavioural break beyond FR-20's and must appear in `release_notes.md` alongside it (FR-25.6, C-18).
  Validation is opt-in (`ValidatePipelines()` must be called); this FR does not make it mandatory, and an application that never calls it gets today's silence. That residual gap is accepted and recorded in C-15.
  *Derives from:* D5.

- **FR-26 — Brighter-held state associated with a borrowed scope must not outlive that scope.** FR-16 requires per-type instance identity across pipelines that share one borrowed scope (D7), which means Brighter holds state keyed to a scope it does not own and receives no disposal callback for. That state must be released when the borrowed scope ends, and must not accumulate across requests. Two observable properties are required:
  (a) **Nothing from a completed request stays reachable.** Once a request has completed and a full collection has run, no mapper, transform or handler instance created for that request, and no association Brighter held for that request's scope, is reachable from Brighter.
  (b) **Peak retained state tracks concurrency, not throughput.** The peak number of live Brighter-held per-scope associations observed while serving requests is bounded by a constant multiple of the number of concurrently in-flight requests, and does not grow with the number of requests served.
  AC-37 fixes how both are measured — including a **positive control** — because under the mechanism the *Note* below recommends, a raw "retained count is zero" assertion is true by construction and could never fail.
  *Example:* an opted-in host serves 10,000 sequential requests, each performing two `Post`s with a `Scoped` mapper. A `WeakReference` to the mapper instance used by the first request is dead after those requests and a forced collection, and the peak count of live associations while serving them is the same at 10,000 requests as at 100.
  *Note (implementation, for the ADR — C-13 governs):* the obvious mechanism is to make the per-scope instance cache itself a container-`Scoped` service resolved from the borrowed provider, so the container owns its lifetime and disposes it with the scope; no weak references or eviction logic are then needed, and the same mechanism works unchanged for a Brighter-owned pipeline scope. Note also that MS DI tracks disposable **transient** resolutions against the scope that created them, so the artefact instances themselves are already disposed by the caller at end of scope — which is what AC-17 asserts.
  *Derives from:* D7.

#### Group D — documentation

- **FR-25 — Brighter's lifetime model is documented, with guidance on how to choose.** A lifetimes-and-scoping page must be created at `docs/guides/lifetimes-and-scoping.md`. No such page exists today — the only lifetime prose in the repository is inside ADRs 0066 and 0067 — so this page becomes the canonical reference for all three lifetimes, not merely a changelog for this feature. That matters because FR-22.2 will fail startup for applications that never had to reason about lifetime before: the error tells them they must choose, and this page is what lets them choose correctly. It must contain, at minimum:
  1. the get/release cycle for each of `Transient`, `Scoped`, `Singleton` (the lifetime model table above);
  2. that affinity applies to `Scoped` only (FR-21) and that an inert opt-in is reported (FR-22);
  3. the truth table required by NFR-9;
  4. the distinction between `IAmAScope` and the existing `IAmALifetime` (NFR-8);
  5. that in-process `Publish` subscribers — and pipelines nested inside them — cannot join a transaction the caller opened, and that the outbox is the answer (C-4, FR-8);
  6. the `MapperLifetime.Scoped` break and its migration (FR-20), which must also appear in `release_notes.md` — including the joint consequence stated in FR-22.2: a per-pipeline `Scoped` mapper requires all three lifetimes to be set together, so `{Scoped, Scoped, Transient}` is not a valid destination;
  7. the rule that handlers, mappers and transforms must not mix `Transient` and `Scoped` (FR-22.2), that `Singleton` is excluded from it, that adopting `Scoped` therefore moves all three lifetimes together, and that this is enforced only when `ValidatePipelines()` is called — which must also appear in `release_notes.md` as a compatibility note (C-18);
  8. the captive-dependency hazard for `Singleton` artefacts (FR-22.3), and its interaction with the FR-20 migration: moving a mapper to `Singleton` is safe only if it has no container-`Scoped` dependencies — stating also that Brighter's warning inspects direct constructor parameters only, so the container's own `ValidateScopes` remains the complete check (C-20);
  9. **a decision guide — "which lifetime should I choose?"** — framed as the **joint** choice FR-22.2 makes it, not as nine independent per-kind cells: a guide that answered "when is a `Scoped` mapper right?" on its own would produce configurations that fail startup, which is exactly what NFR-10 forbids. It must contain a table of the configurations that pass validation — `{Transient, Transient, Transient}`, `{Scoped, Scoped, Scoped}`, and either of those with any member replaced by `Singleton` — stating for each what it costs and when it is the right answer; plus a per-kind note for handlers, mappers and transforms saying when *that* kind is the one that should be `Singleton` (stateless, or deliberately caching across pipelines — with the captive-dependency caveat, FR-22.3). It must answer explicitly: when `Scoped` is needed rather than `Transient` (sharing a `DbContext`, transaction or other pipeline-scoped dependency across the pipeline, and adopting the caller's scope — stating that this choice moves all three lifetimes together); when `Singleton` is right; and why `Transient` remains the default. Because those three answers can read as contradictory — FR-1 makes `Scoped` the fix for per-pipeline state, FR-20 prescribes `Singleton` as the migration for cross-pipeline caching, and `Transient` stays the default — the page must state which situation each answer belongs to. Guidance must be prescriptive enough that a reader hitting the FR-22.2 error can pick a conformant **triple** without reading the source;
  10. a statement that validation reaches an application only if it calls `ValidatePipelines()` **and** a validation host runs — naming the consumer case where `AddConsumers` defers to a `ServiceActivatorHostedService` the application must itself register (C-15, D14) — and **a troubleshooting section keyed to each of the seven validation messages** — FR-22's four (inert opt-in, mixed `Transient`/`Scoped`, captive dependency, an opt-in defeated by a pre-existing `IBrighterOptions` registration), FR-24.3's duplicate provider, and FR-17's two (a conflicting repeated opt-in, and an override registered by factory delegate whose value cannot be read) — each entry stating the cause and the remedy. Three are errors (FR-22.1, FR-22.2, FR-22.4) and four are warnings (FR-22.3, FR-24.3, FR-17's two).
  11. the rule that the ASP.NET extension's affinity **argument** is the value (FR-17, **D18**): to select an affinity, pass it to the extension; assigning `DefaultScopeAffinity` in the application's own configuration *while also calling the extension* is a configuration error whose outcome is the extension's value, on every registration path and in any order — and it is **not** reported by validation, because no sentinel exists to distinguish it from the ordinary opt-in. The page must state the correct gesture for each intent: opt in with `AddBrighterRequestScope()`; register the ambient source without opting in with `AddBrighterRequestScope(ScopeAffinity.AlwaysNew)`; opt out entirely by not calling the extension.

### Non-functional Requirements

- **NFR-1 — Core stays container-agnostic.** No `IServiceProvider` may appear on any `Paramore.Brighter` interface. **Nor may core gain a container dependency — and the *source-level* half of that is the load-bearing one.** `Paramore.Brighter` must gain no **direct** `PackageReference` or `ProjectReference` matching `Microsoft.Extensions.DependencyInjection*`; **and** no source file under `src/Paramore.Brighter/` may reference `ServiceLifetime`, `IServiceCollection`, `IServiceProvider` or `ServiceDescriptor`. The second clause carries the weight because `Microsoft.Extensions.DependencyInjection` is **already on core's compile closure transitively**, via `Microsoft.Extensions.Logging` — so those types are compile-visible in core today, and a project-file check alone would pass a change that put them in core's source. So the FR-22 rules, which read container concepts, must be evaluated outside core (FR-22, AC-22.2, AC-22.3). The purpose is ADR 0014's: Brighter offers per-family factory interfaces rather than abstracting an IoC container, so the seam must stay implementable over Autofac or SimpleInjector as readily as over Microsoft's container (NFR-7, OOS-3).

  **What this requirement no longer forbids (withdrawn in revision 14).** Earlier revisions also froze the *signatures* of the six factory interfaces — `IAmAMessageMapperFactory`, `IAmAMessageMapperFactoryAsync`, `IAmAMessageTransformerFactory`, `IAmAMessageTransformerFactoryAsync`, `IAmAHandlerFactorySync` and `IAmAHandlerFactoryAsync` — on the grounds that `netstandard2.0` has no default interface members, so any added member breaks every implementation at compile time. **That freeze is withdrawn.** These interfaces are consumed internally and implemented, in practice, only by the container-backed factories Brighter itself ships; there are no known public implementations to protect, and the cost of the freeze is a design that must reach the factories by some means other than the obvious one. The six interfaces may therefore gain members and change signatures. Three obligations follow, and none is optional. **(a)** Whatever a factory method gains must itself be a container-agnostic `Paramore.Brighter` type: the clauses above are unchanged, so no signature may carry `IServiceProvider`, and the freed parameter is not a licence to hand the container to core. **(b)** Every implementation in this repository moves together — the four container-backed factories, the six core factories (`SimpleMessageMapperFactory[Async]`, `SimpleMessageTransformerFactory[Async]`, `EmptyMessageTransformerFactory[Async]`) and every test double — so the solution compiles with no partial adopters. **(c)** The break is a **source and binary breaking change** for any application that implements one of the six by hand, and must be recorded in `release_notes.md` alongside FR-20's behavioural break, naming each interface whose signature changed and stating the migration (AC-24).
- **NFR-2 — No ASP.NET dependency in the DI package.** `Paramore.Brighter.Extensions.DependencyInjection` must gain no reference to ASP.NET Core (`IHttpContextAccessor`, `Microsoft.AspNetCore.*`). The ASP.NET ambient lives only in the new package (FR-17).
- **NFR-3 — `Paramore.Brighter.ServiceActivator` keeps its current dependency set** — a single project reference to `Paramore.Brighter`. It gains no container dependency.
- **NFR-4 — Thread safety.** Beginning and releasing pipeline scopes, and establishing and clearing ambient suppression, must be safe under concurrent pipelines on different threads and under the concurrent subscriber execution of **both** `PublishAsync` (started at `CommandProcessor.cs:591-599`, awaited together at `:601`) and the synchronous `Publish` (`Parallel.ForEach`, `:481`, whose `ExecutionContext` is restored per worker task, not per body), with no cross-pipeline interference and no torn or shared state between pipelines, and no suppression state left on the caller's flow when either publish returns.
- **NFR-5 — Bounded resource growth.** Steady-state consumption of N messages must leave zero Brighter-created scopes live after the Nth message completes, for `Scoped` and `Transient` mapper/transform/handler lifetimes alike. Memory attributable to Brighter scopes must not grow with message count.
- **NFR-6 — Cost proportional to pipelines, not to resolutions.** Pipeline scoping must add at most one DI scope begin/release per pipeline; it must not add a DI scope per resolved instance within a pipeline.
- **NFR-7 — Extensibility without ASP.NET.** The seam must not preclude a later `AsyncLocal`-based `IAmAScopeProvider` for non-ASP.NET hosts, nor implementations over other containers (SimpleInjector `AsyncScopedLifestyle`, Autofac `ILifetimeScope.BeginLifetimeScope`). Neither is delivered here (see Out of Scope).
- **NFR-8 — Documentation must disambiguate `IAmAScope` from `IAmALifetime`.** The two names are close and the existing `IAmALifetime` (the handler instance-tracking lifetime, `HandlerLifetimeScope`) is not being replaced. Documentation and XML comments must state plainly what each is for and how they relate.
- **NFR-10 — The lifetime documentation is self-sufficient.** A reader who hits any FR-22 message must be able to reach a correct configuration using `docs/guides/lifetimes-and-scoping.md` alone, without reading Brighter's source, the ADRs, or this specification. This is the primary mitigation for C-18 and is the acceptance bar for FR-25.
- **NFR-9 — Diagnosability.** It must be possible for a user to determine, from documentation, which of the sources a pipeline's dependencies came from — an adopted ambient, a Brighter-created pipeline scope, or the no-provider no-op path — for each of `Send`, `Publish` (subscriber, and nested inside a subscriber), `Post` and consume; for each setting of the affinity flag; and for each of `Transient`/`Scoped`/`Singleton`. A truth table in `docs/guides/lifetimes-and-scoping.md` satisfies this.

### Constraints and Assumptions

- **C-1 — Microsoft's DI scopes do not nest** (verified by spike, recorded in the design narrative). `IServiceScopeFactory` resolved from a scoped provider is the *same instance* as the one resolved from root, and creating a scope from it yields a fresh **root-parented** scope. Therefore "adopt the ambient" can only mean *resolve directly from the caller's provider*; there is no way to create a child scope that still sees the request's `DbContext`, and no way to nest a per-subscriber scope inside a per-message one. This constraint is why the scope unit must be the pipeline (D0).
- **C-2 — The message pump is untouched.** `Reactor`, `Proactor`, `Dispatcher`, `DispatchBuilder` and `ConsumerFactory` require no change and must not be changed by this work (D0b).
- **C-3 — On the consumer, a transform pipeline's scope ends before the handler pipeline begins.** `TranslateMessage` runs its `finally` — releasing the transform pipeline — before `InvokeDispatchRequest` is called (`Proactor.cs:239` then `:241`). **When both pipelines own their scopes** — the consumer path always, and the producer path under `AlwaysNew` — a `Scoped` dependency used by an unwrap transform and by the handler is therefore **two instances**, and the transform's is already disposed by the time the handler runs. This is intended and is not a defect. The single exception is FR-16(b): under `JoinAmbient` on the producer side, both pipelines borrow the same request scope and therefore share one instance. State that must cross the consumer boundary travels in `RequestContext.Bag`, as `ChannelName` and `RequestStart` already do.
- **C-4 — In-process `Publish` subscribers cannot join a caller's transaction**, and under D6 neither can pipelines nested inside them. This follows from FR-8 and ADR 0039. The answer is the outbox. Discharged by FR-25(5).
- **C-5 — ADR 0033 is not reopened.** The `CommandProcessor` remains a singleton.
- **C-6 — `Transient` and `Singleton` are untouched.** Since #4254 (ADR 0067) `Transient` already gets a per-resolution scope released per message. This work concerns `Scoped` only (FR-21), and must not regress ADR 0067's behaviour or `IsolateTransientHandlerScope` (`BrighterOptions.cs:37`).
- **C-7 — Ownership travels with the scope.** Created ⇒ Brighter disposes (FR-13). Adopted ⇒ the caller's, never disposed by Brighter (FR-12). An ambient that is offered but unusable is declined and a new scope created (FR-23), and so is one offered for an `AlwaysNew` ask and therefore ignored (FR-24.4) — both are the created case, not further ownership rules, and in neither does Brighter dispose the ambient it declined to adopt.
- **C-8 — Assumed home for the seam types.** `IAmAScope`, `IAmAScopeProvider` and `ScopeAffinity` are assumed to live in the `Paramore.Brighter` namespace/assembly, alongside the existing `IAmALifetime`. The ADR should confirm this and settle whether `IAmAScope` implements `IDisposable` only or both `IDisposable` and `IAsyncDisposable`.
- **C-9 — OPEN ITEM (for the ADR to settle): the exact name and shape of the opt-in property on `IBrighterOptions`/`BrighterOptions`.** The FRs and ACs here are written against the working name `ScopeAffinity DefaultScopeAffinity { get; set; } = ScopeAffinity.AlwaysNew;` purely so they are testable. The alternative shape is a `bool` (e.g. `AdoptAmbientScope`). Whichever is chosen, the *behaviour* required by FR-14 through FR-23 is unchanged; only the property's name, type and default expression are open. Note that unlike `IsolateTransientHandlerScope` (`BrighterOptions.cs:37`), this is **not** a compatibility flag (D3).
- **C-10 — CLOSED: the extension's argument is the value.** There is no *ordering* rule between the extension and an affinity assignment, because the extension takes the affinity as an **argument** (FR-17, **D13**) and that argument wins unconditionally (**D18**) — it must reach `IBrighterOptions` on the three paths that run no `IOptions` pipeline, so it necessarily lands after every application options delegate. It wins over an affinity the application assigns on the options object; it does not win against an application that registers `IBrighterOptions` **itself**, which defeats the opt-in altogether rather than out-ranking it, and which FR-22.4 reports. Ordering could not have been made to work: three of the four registration entry points run no `IOptions` pipeline and cannot distinguish an explicit `AlwaysNew` from the default without a sentinel, which FR-17 forbids (C-12a). Assigning the option alongside the extension is therefore a **configuration error**, not a precedence question — and it is documented, not validated: without the sentinel FR-17 bans, "the application assigned `AlwaysNew`" is indistinguishable from "the application left the default", so any value-comparison rule would fire falsely on the ordinary opt-in. AC-18 asserts the two argument values from a non-default starting point; AC-45 asserts the argument reaching `IBrighterOptions` on all four paths; AC-48 asserts extension-wins in both directions. The extension never alters a lifetime.
- **C-11 — Naming is settled** as `IAmAScope`, `IAmAScopeProvider`, `ScopeAffinity{JoinAmbient, AlwaysNew}` (D4). `IAmAChainScope`, `IAmAPipelineScope` and `IAmAUnitOfWorkScope` were considered and rejected. Two names remain **working names**, and for each the *contract* is fixed while the spelling is not: the package name `Paramore.Brighter.Extensions.AspNetCore`; and the ambient-query member `IAmAScope? GetAmbient(ScopeAffinity affinity)` on `IAmAScopeProvider`, whose contract is fixed by FR-10 (**D17**). The ADR may confirm or change either spelling; it may not change the contracts. A third was a working name and is now **settled**: the registration extension is `AddBrighterRequestScope(...)`, chosen by the ADR that decides the ASP.NET package, superseding the working name `AddBrighterAspNetCoreScopes(...)` recorded here. Its contract — that it takes the affinity as an argument, and that the argument is the value — was fixed by FR-17 throughout (**D13**, **D18**) and the naming call did not touch it.
- **C-12a — Only one registration path runs the `IOptions` pipeline.** `AddOptions<BrighterOptions>()` is called on exactly one entry point, `AddBrighter(Action<BrighterOptions>)` (`Paramore.Brighter.Extensions.DependencyInjection/ServiceCollectionExtensions.cs:69`); the other three bind `IBrighterOptions` directly — `AddBrighter(Func<IServiceProvider, BrighterOptions>)` (`:97`), `AddConsumers(Action<ConsumersOptions>)` (`ServiceActivator.Extensions.DependencyInjection/ServiceCollectionExtensions.cs:38`) and `AddConsumers(Func<…>)` (`:88`). A `services.Configure<BrighterOptions>(…)` contributed by a later extension therefore reaches the object the factories read on that one path only. This is a *different* hazard from C-12's `TryAdd` first-wins — it bites even when `AddBrighter` wins the `TryAdd` — and FR-17 requires the opt-in to work on all four paths regardless (AC-45), save for FR-22.4's case.
- **C-12 — `IBrighterOptions` is registered `TryAdd`, so the first registration wins.** Both `AddBrighter` (`Paramore.Brighter.Extensions.DependencyInjection/ServiceCollectionExtensions.cs:74`) and **`AddConsumers`** (`Paramore.Brighter.ServiceActivator.Extensions.DependencyInjection/ServiceCollectionExtensions.cs:88`) call `TryAddSingleton<IBrighterOptions>`. There is no `AddServiceActivator` method — the name survives only in three stale doc comments and must not be used in this spec. In a mixed producer+consumer host the options object Brighter reads is therefore **whichever side registered first**, not necessarily the one the user configured most recently. **The same first-wins behaviour lets an *application's own* `IBrighterOptions` registration defeat the affinity opt-in entirely** — Brighter's registration never runs, so the extension's argument is never applied — and a later plain `AddSingleton` does the same by winning resolution as the last unkeyed descriptor. That is not an accepted silence: it is diagnosed by **FR-22.4** and pinned by **AC-50**. Any AC that sets the affinity flag in a mixed host must state which registration call carries it, **which `AddConsumers` overload is used**, and in what order the `Add*` calls are made — because the two overloads behave differently:
  - `AddConsumers(Func<IServiceProvider, ConsumersOptions>)` (`:78`) registers `IAmConsumerOptions` as a cast of the resolved `IBrighterOptions` (`:89-90`). With `AddBrighter` first, that resolves a plain `BrighterOptions`, which does **not** implement `IAmConsumerOptions` — so every resolution of `IAmConsumerOptions` throws `InvalidCastException` at resolve time. This is a **pre-existing hazard**, not one this spec introduces, but a mixed-host AC must avoid walking into it.
  - `AddConsumers(Action<ConsumersOptions>)` (`:29`) registers the `ConsumersOptions` instance directly for `IAmConsumerOptions` (`:38-39`), so no cast and no throw — but `IBrighterOptions` and `IAmConsumerOptions` then resolve to *different* objects, so subscriptions come from the consumer's options while lifetimes and the affinity flag come from whichever object won the `TryAdd`.
- **C-19 — FR-3 requires the mapper and transformer factories to share one pipeline scope.** `ServiceProviderMapperFactory` and `ServiceProviderTransformerFactory[Async]` each construct their **own** `ServiceProviderLifetimeScope` (`ServiceProviderMapperFactory.cs:46`, `ServiceProviderTransformerFactory.cs:46`), so each creates its own `IServiceScope` — today they do **not** share one even when both are configured `Scoped`. FR-3's requirement that a container-`Scoped` dependency be one instance across the mapper and its transforms therefore cannot be met by per-pipeline scoping alone: the two factories must be handed the *same* pipeline scope for a given transform pipeline. How that is threaded is design work (C-13), but that it is required is a constraint the ADR must not discover late. It is named **Defect 1b** in *Where the Implementation Has Drifted*, so that the enumeration of drift there is complete.
  **The two factory families release differently, and only one is handed a per-pipeline object — which bounds the solution.** The handler factories are `IHandleRequests? Create(Type handlerType, IAmALifetime lifetime)` and `void Release(IHandleRequests handler, IAmALifetime lifetime)` (`IAmAHandlerFactorySync.cs:44`, `:51`; async twin `IAmAHandlerFactoryAsync.cs:44`, `:51`), so a per-pipeline object already travels on every call, and `ServiceProviderHandlerFactory` keys its `ServiceProviderLifetimeScope` on exactly that (`:127`). The mapper and transformer factories do **not**: they are `Lease<T>? Create(Type)` and `void Release(Lease<T>?)` — a type in, an opaque lease out (ADR 0066), carrying nothing that identifies the pipeline (`IAmAMessageMapperFactory.cs:45`, `:60`; `IAmAMessageMapperFactoryAsync.cs:46`, `:62`; `IAmAMessageTransformerFactory.cs:44`, `:50`; `IAmAMessageTransformerFactoryAsync.cs:45`, `:54`). Since revision 14, NFR-1 no longer freezes those signatures, so the handler family's own mechanism — a per-pipeline object travelling on every call — is available to the mapper and transformer factories too, at the cost of a compile break for any hand-rolled implementation (NFR-1(c), AC-24). Whether the shared pipeline DI scope is threaded as a parameter, through construction, or through something the factory reads is design work (C-13). What this constraint fixes is not the mechanism but the outcome: the two factories must end up resolving from the *same* scope for a given transform pipeline, and anything added to a signature must be a container-agnostic core type (NFR-1(a)).
- **C-18 — Rule 2 of FR-22 is a compatibility break for validating applications.** An application that today sets, say, `HandlerLifetime = Scoped` with `MapperLifetime = Transient` works — the two simply do not share pipeline-scoped dependencies — and will now fail startup if it calls `ValidatePipelines()`. The blast radius is bounded by validation being opt-in (C-15), but it is a second break beyond FR-20's and belongs in the release notes with it. This asymmetry is not new; adoption is what makes it consequential, because under `JoinAmbient` the mixed pair means half the pipeline joins the caller's transaction and half does not.
- **C-17 — `Scoped` identity is Brighter's, not the container's.** Every mapper, transform and handler type is registered into the service collection as `ServiceLifetime.Transient` (`ServiceCollectionMessageMapperRegistryBuilder.cs:80`, `:99`, `:116-117`, `:127`, `:137`; `ServiceCollectionTransformerRegistry.cs:56`; `ServiceCollectionSubscriberRegistry.cs:63`, `:76`, `:90`, `:116`, `:130`, `:146`, `:160`). `MapperLifetime.Scoped` is implemented by Brighter's own per-type cache in `ServiceProviderLifetimeScope.GetOrCreateScoped` (`:163-178`), not by the container: the `IServiceScope` supplies dependency identity and disposal, while the `_scopedInstances` dictionary supplies artefact identity. Two consequences shape this spec. First, adopting a borrowed provider gives dependency sharing for free but **not** artefact identity across pipelines — that requires FR-16's per-scope association, which FR-26 bounds. Second, FR-11(b) cannot be satisfied without a real `IServiceScope`, because the dependency half comes only from the container.
- **C-20 — Captive-dependency detection is bounded in two ways, both deliberate.** *(i) Constructor selection is Brighter's own rule* (**D15**) — most parameters, ties not inspected — and does not reproduce MS DI's superset requirement or its always-resolvable services (`IServiceProvider`, `IServiceScopeFactory`, `IEnumerable<T>`), so the rule may inspect a constructor MS DI would not select. *(ii) Depth is direct parameters only.* FR-22.3 inspects the direct parameters of the selected constructor. Transitive captivity — a `Singleton` artefact taking a `Transient` dependency that itself takes a `Scoped` one — is **not** reported, and neither is captivity reachable only through a descriptor registered by factory delegate or instance, whose implementation type is not statically known. *(iii) The exclusion's assembly-name prefix over-excludes.* Because FR-22.3 excludes any attribute-returned type whose defining assembly's simple name is `Paramore.Brighter` or begins with `Paramore.Brighter.`, an **application's** handler or transform that happens to live in an assembly the application named `Paramore.Brighter.Something` is excluded too, and a captive dependency on it is not reported. Accepted: the alternative is an exact-name match, which would warn against Brighter's own out-of-core transforms, and an assembly-identity or strong-name test is more machinery than the noise it removes. AC-42's prefix case relies on exactly this over-exclusion. *(iv) Mappers are unreachable by the exclusion mechanism.* It keys off `RequestHandlerAttribute.GetHandlerType()` and `TransformAttribute.GetHandlerType()`, and no mapper is returned by an attribute — so no Brighter-shipped mapper can be excluded by it. Brighter ships no mapper with constructor dependencies today, so the gap is latent rather than live; were one added it would be warned against as if it were the user's, and the mechanism would need a third clause. All four are accepted gaps for this spec, and the container's own `ValidateScopes` remains the complete check, which the guidance page must say (FR-25.8). AC-42 pins each as intended behaviour so a later implementation cannot change any of them silently: (i) by its two-constructor and equal-count cases, (ii) by its transitive case, (iii) by its `Paramore.Brighter.Extensions.Tests` transform case, and (iv) by the `Paramore.Brighter.Extensions.Tests` **mapper** case, which asserts the *opposite* outcome from the transform case in the same assembly and so pins the gap as a deliberate asymmetry rather than an oversight.
- **C-13 — How** pipeline scoping, adoption, suppression and the seam are implemented — where the ambient query is called from, the shape of the non-core contract by which an ambient exposes a resolution source (FR-10), how the pipeline scope is keyed and threaded to the factories, and how suppression is expressed — is a design/ADR concern. This document constrains observable behaviour only.
- **C-14 — A consumer pipeline never adopts, whatever flow its pump was started on.** This was an assumption — that a consumer pump thread carries no usable ambient `HttpContext` — and the requirements could not make it good: `IHttpContextAccessor` is `AsyncLocal`-backed, a `Dispatcher` started from within a request does inherit one, and the context that flows in is *live* rather than stale, so FR-23 would not govern it. The design closes the case at the ask instead: a consumer pipeline's ask carries `AlwaysNew` however the affinity option is set, so a conforming ambient source offers it nothing (FR-19, **AC-55**). Starting a `Dispatcher` from inside a live request remains erroneous use of the library; what is guaranteed is that it fails toward isolation, not that it is supported.
- **C-15 — `ValidatePipelines()` is opt-in, and snapshots its inputs.** FR-22's error and warnings only reach an application that calls it; an application that opts into adoption, leaves every lifetime `Transient`, and never validates gets no signal. Further, `ValidatePipelines()` snapshots the service collection at the point it is called (`BrighterPipelineValidationExtensions.cs:47-52`, `:64-69`), so FR-24.3's duplicate-provider check covers only providers registered before that call. Third, per **D14**, a consumer host that sets `ConsumerOwnsValidation` but never registers `ServiceActivatorHostedService` (it lives in `Paramore.Brighter.ServiceActivator.Extensions.Hosting`, and `AddConsumers` does not register it) has no validation host at all, so no FR-22 message is surfaced however the configuration is wrong. All three residual gaps are accepted for this spec; the documented guidance remains "call `ValidatePipelines()` last in the builder pipeline", and — for consumers — "register the consumer hosted service".
- **C-21 — A transaction provider's transaction is decided by the scope that resolved it, and today that scope is never the caller's.** Brighter's relational transaction providers wrap a `DbContext` taken by constructor injection (`MsSql.EntityFrameworkCore/MsSqlEntityFrameworkCoreTransactionProvider.cs:18`, and the same shape in the MySql, Sqlite, PostgreSql and MongoDb providers). The provider is registered `Transient` by default (`Extensions.DependencyInjection/ServiceCollectionExtensions.cs:250`, `:386`) and the `DbContext` is `Scoped`, so **which** transaction the provider hands out is fixed entirely by which scope resolved the pair. Every non-`Singleton` handler resolution is made from a scope Brighter created (`ServiceProviderHandlerFactory.cs:67-68`, `:85-86`), so under `AlwaysNew` a handler's `DbContext` is never the caller's, and a handler that deposits to the outbox writes on a different connection and inside a different transaction from the caller's own writes. **Nothing detects it**: the deposit succeeds, the row is written, and only the atomicity is lost. This is the mechanism FR-16(c) exists to fix and **AC-52** measures, and it bounds the fix in three ways. *(i)* The fix is the scope, not the outbox: `IAmAnOutbox` and `IAmAnOutboxProducerMediator` are `Singleton`s (`ServiceCollectionExtensions.cs:484`), so they are built in the root scope and never borrow; adoption changes the provider instance **the handler holds** and nothing the mediator does. *(ii)* The three `sp.GetService<IAmABoxTransactionProvider>()` sites (`:431`, `:487`, `:648` — the last inside a scope created for the purpose at `:646`) are **type discovery** only; Brighter resolves no transaction provider from the container at dispatch time. *(iii)* `DepositPost` without an explicit provider passes `null` (`CommandProcessor.cs:795`), so adoption does not make an outbox write transactional on its own — the caller must still pass the provider. Under FR-8 a `Publish` subscriber is suppressed and so is excluded from all of this, which is **C-4**.
- **C-16 — ADRs are cited by slug.** ADR 0033 = `0033-lifetime-of-command-processor-and-mediator`; ADR 0039 = `0039-scoping-dependencies-inline-with-lifetime-scope` (the repo also has `0039-opentelemetry-builder-extension`, `0039-redis-dlq-brighter-managed` and `0039-transport-scheduler-wiring`); ADR 0064 = `0064-pipeline-cache-type-key` (the repo also has `0064-validate-pipeline-assembly-and-provider-registration`); ADR 0066 = `0066-release-factory-instances-on-an-opaque-lease`; ADR 0067 = `0067-per-resolution-di-scope-for-transient-factory-instances`. Note that ADR 0033 and ADR 0039 are both status **Proposed**, not Accepted, though this document treats their decisions as settled.

### Out of Scope

- **OOS-1 — A per-message ambient published by the pump.** Decided against (D0b, issue comment 2). Each pipeline stands alone.
- **OOS-2 — A general `AsyncLocal`-based `IAmAScopeProvider` for non-ASP.NET hosts** — i.e. an ambient *source* that lets an arbitrary caller publish a scope for Brighter to adopt. Out of scope; the seam must not preclude it (NFR-7). **Partially amended by D6**: an `AsyncLocal` **suppression** flag, scoped to a `Publish` subscriber's execution and carrying no service provider, *is* in scope, because FR-8 requires it. Suppression is not adoption and does not deliver OOS-2's capability.
- **OOS-3 — Implementations of the seam for other containers** (Autofac, SimpleInjector, Lamar…). The seam must permit them; none ship here.
- **OOS-4 — Any `UseBrighterScope()`-style middleware.** Rejected in favour of the provider (D1, FR-17).
- **OOS-5 — Changes to `Reactor`, `Proactor`, `Dispatcher`, `DispatchBuilder`, `ConsumerFactory`** (C-2).
- **OOS-6 — Reopening the `CommandProcessor` singleton decision** (ADR 0033) or the per-subscriber scope decision (ADR 0039).
- **OOS-7 — Changes to `Transient` or `Singleton` lifetimes**, and to `IsolateTransientHandlerScope` (C-6, FR-21).
- **OOS-8 — A compatibility flag restoring the old cross-message `MapperLifetime.Scoped` caching** (D3, FR-20).
- **OOS-9 — Sharing a resolved `Scoped` instance between an unwrap transform and a handler on the consumer** (C-3). `RequestContext.Bag` remains the carrier. The opted-in producer case is FR-16(b) and is in scope.
- **OOS-10 — Letting a `Publish` subscriber, or a pipeline nested inside one, adopt an ambient scope** (FR-8, D6), and letting in-process subscribers join a caller's transaction (C-4).
- **OOS-11 — Darker's `QueryProcessorLifetime`** and any change to Darker's scoping. Cited only as evidence of the current asymmetry.
- **OOS-12 — Shutdown-hygiene disposal of the consumer factories by the `Dispatcher`** (the alternative suggested on #4254). Superseded by per-pipeline scoping.
- **OOS-13 — Making `ValidatePipelines()` mandatory or on by default** (C-15).
- **OOS-14 — A nested pipeline re-entering its parent subscriber's scope.** Per the lifetime model, `Scoped` is owned by the pipeline and a nested `Send` is a new pipeline (FR-9).

## Acceptance Criteria

Each AC names the FR(s) or NFR(s) it discharges. Every FR and NFR is covered.

**How to read the lifetime configuration in a Given.** Every AC whose behaviour depends on a pipeline taking a pipeline scope — which, under FR-27.1, means every AC that exercises adoption, scope creation, scope release or the scope provider, not merely those that *set* a lifetime — states **all three** of `HandlerLifetime`, `MapperLifetime` and `TransformerLifetime`, and states a triple that is conformant with **both** FR-22.1 (not an inert opt-in) and FR-22.2 (no `Transient`/`Scoped` mixing), so that a host built for one AC can be reused as a fixture by another without tripping validation. The exceptions are the ACs whose subject *is* the configuration itself — AC-26, AC-27, AC-28, AC-41, AC-42, AC-46 and AC-47 — which state their triples explicitly and, where a triple is deliberately non-conformant, say so and say that `ValidatePipelines()` is not called. Where an AC says "the AC-15 setup" it inherits that AC's triple unchanged.

**How to read a `Warning` count in a Then.** Every AC that asserts a count of `Warning` entries — AC-11, AC-19, AC-20, AC-29, AC-31, AC-54 and AC-55 — builds its **own host**, and so does every branch that **changes the configuration** — a different provider, a different provider behaviour, or a different affinity. A clause that merely **repeats an operation** within a Then — "a second `PublishAsync`" (AC-11), "a second deferred `Send`" (AC-29) — runs in the **same** host, and asserts *no further* entry precisely because the latch is per container. Under **D19** the three diagnostic latches are scoped to the Brighter container, so such a count is unaffected by any AC or branch that ran earlier in the same process, and two branches may re-use a single `IAmAScopeProvider` implementation type without one silencing the other — which AC-11's and AC-31's branches deliberately do. An implementation that latches statically for the process fails these ACs, which is intended.

**Per-pipeline scoping — mappers and transforms**

- **AC-1 (FR-1, NFR-5) — A `Scoped` mapper is not reused across messages.**
  **Given** all three of `HandlerLifetime`, `MapperLifetime` and `TransformerLifetime` set to `Scoped` (an FR-22.2-conformant triple) and a mapper type registered `AddScoped` that records its construction identity and its disposal,
  **When** the consumer processes message N and then message N+1,
  **Then** two distinct mapper instances were constructed, and the instance used for N was disposed before the instance for N+1 was constructed.

- **AC-2 (FR-2) — A `Scoped` transform is not reused across messages.**
  **Given** all three of `HandlerLifetime`, `MapperLifetime` and `TransformerLifetime` set to `Scoped` (an FR-22.2-conformant triple) and an unwrap transform registered `AddScoped`,
  **When** the consumer processes two messages,
  **Then** two distinct transform instances were constructed and the first was disposed before the second was constructed — asserted for both `TransformPipelineBuilder` (sync/Reactor) and `TransformPipelineBuilderAsync` (async/Proactor).

- **AC-3 (FR-3) — One `Scoped` dependency across mapper and transforms within a pipeline.**
  **Given** all three of `HandlerLifetime`, `MapperLifetime` and `TransformerLifetime` set to `Scoped` (an FR-22.2-conformant triple), and `IMarker` registered `AddScoped` and injected into both the mapper and its `[UnwrapWith]` transform,
  **When** one message is mapped,
  **Then** the mapper's `IMarker` and the transform's `IMarker` are reference-equal;
  **And when** a second message is mapped,
  **Then** both see a second, different `IMarker` instance, and the first `IMarker` was disposed at the end of the first pipeline.

- **AC-4 (FR-4) — Producer transform pipelines scope per `Post`.**
  **Given** a console host (no ambient, no provider registered) with all three of `HandlerLifetime`, `MapperLifetime` and `TransformerLifetime` set to `Scoped` (an FR-22.2-conformant triple),
  **When** `Post(commandA)` completes and then `Post(commandB)` is called,
  **Then** the two calls used distinct mapper instances and the first was disposed before the second was constructed.

**Error and boundary paths**

- **AC-5 (FR-5, NFR-5) — Failed build releases the pipeline scope and preserves the error.**
  **Given** all three of `HandlerLifetime`, `MapperLifetime` and `TransformerLifetime` set to `Scoped` (an FR-22.2-conformant triple), and a mapper whose constructor depends on an unregistered service, so pipeline build throws,
  **When** 1,000 `Post` attempts are made, each failing,
  **Then** each call throws `ConfigurationException` whose inner exception is the original resolution failure,
  **And** the count of Brighter-created scopes begun equals the count released — zero live at the end.

- **AC-6 (FR-5) — A release failure does not mask the configuration error.**
  **Given** all three lifetimes `Scoped`, and a failing pipeline build where releasing the pipeline scope itself throws,
  **When** the build is attempted,
  **Then** the caller receives the `ConfigurationException` for the build failure, and a capturing `ILoggerProvider` registered for `Paramore.Brighter.*` records the disposal failure at `LogLevel.Error`.

- **AC-7 (FR-6) — A throwing handler still releases the pipeline scope, exactly once.**
  **Given** not opted in, all three of `HandlerLifetime`, `MapperLifetime` and `TransformerLifetime` set to `Scoped` (an FR-22.2-conformant triple), and a handler with a `Scoped` `IDisposable` dependency whose `HandleAsync` throws `InvalidOperationException`,
  **When** `SendAsync` is called,
  **Then** the caller observes `InvalidOperationException`, and the dependency's `Dispose` was called exactly once.

- **AC-8 (FR-6) — Disposing a pipeline scope twice is a no-op and does not affect a concurrently live pipeline.**
  **Given** all three lifetimes `Scoped` — so both pipelines take a pipeline scope (FR-27.1) — two concurrently live pipelines, X and Y, each holding a Brighter-created `IAmAScope`, and X's scope already disposed,
  **When** `IAmAScope.Dispose()` — and separately `DisposeAsync()` — is invoked a second time on X's scope instance,
  **Then** no exception is raised, and Y's scope and the instances resolved from it remain undisposed and usable.

**Handler pipelines and `Publish`**

- **AC-9 (FR-7) — A handler pipeline scope is torn down at the end of `Send`.**
  **Given** not opted in, all three of `HandlerLifetime`, `MapperLifetime` and `TransformerLifetime` set to `Scoped` (an FR-22.2-conformant triple), and a handler with a `Scoped` `IDisposable` dependency,
  **When** `Send` returns,
  **Then** that dependency has been disposed; **and** a second `Send` resolves a different instance.

- **AC-10 (FR-8) — Each `Publish` subscriber gets a distinct scope (ADR 0039 regression guard).**
  **Given** all three of `HandlerLifetime`, `MapperLifetime` and `TransformerLifetime` set to `Scoped` (an FR-22.2-conformant triple), three handlers registered for `OrderPlaced` each taking a `Scoped` `IUnitOfWork`, not opted in,
  **When** `PublishAsync(orderPlaced)` completes,
  **Then** three distinct `IUnitOfWork` instances were resolved, and all three were disposed by the time `PublishAsync` returns — released together at end of publish, which is today's behaviour and what FR-9's release-timing clause preserves.

- **AC-11 (FR-8, FR-10, FR-24) — `Publish` subscribers do not adopt the ambient even when opted in, and a provider that ignores the affinity cannot change that.**
  **Given** an opted-in ASP.NET application with all three of `HandlerLifetime`, `MapperLifetime` and `TransformerLifetime` set to `Scoped` (an FR-22.2-conformant triple) and a request scope containing `IUnitOfWork` instance `R`, and two subscribers for `OrderPlaced` each taking `IUnitOfWork`,
  **When** a controller action calls `PublishAsync(orderPlaced)`,
  **Then** neither subscriber resolved `R`, the two subscribers resolved two distinct instances, both were disposed when the publish completed, and `R` was **not** disposed.
  **And given** the same application except that its ambient source is a hand-rolled `IAmAScopeProvider` reading the same request ambient — registered as the **only** `IAmAScopeProvider` descriptor, in place of the ASP.NET one, with the affinity option `JoinAmbient` so no extension call is involved (FR-17, D18) — which **violates FR-10** by returning that ambient for *every* ask including `AlwaysNew` ones, and with a capturing `ILoggerProvider` registered for `Paramore.Brighter.*`,
  **Then** the outcome is unchanged — neither subscriber resolved `R`, the two resolved distinct instances, and `R` was not disposed — because Brighter ignores an ambient returned for an `AlwaysNew` ask rather than trusting the provider to withhold it (FR-10, **FR-24.4**);
  **And** the capturing provider records exactly one `LogLevel.Warning` naming the **ambient offered for an `AlwaysNew` ask and ignored** condition and that provider's implementation type, and records no further one for a second `PublishAsync` in the same host — FR-24.4's once-per-Brighter-container-per-provider-implementation-type entry (**D19**), latched independently of FR-23's and FR-24.2's conditions (FR-24's diagnostic model). This provider never returns nothing, so FR-24.2 does not fire and the count is unambiguous — which is exactly the variable the next branch changes;
  **And given** a **second host of the same shape** — a fresh Brighter container, so all three latches start unlatched (**D19**, and the reading note above) — registering the **same** hand-rolled `IAmAScopeProvider` implementation type as the previous branch, configured to vary in one respect: it returns the request ambient for `AlwaysNew` asks, still violating FR-10, but `null` for `JoinAmbient` asks,
  **When** a controller action calls `Send` (one ask carrying `JoinAmbient`, FR-27.2) and then `PublishAsync(orderPlaced)` to the same two subscribers (two asks carrying `AlwaysNew`, FR-8),
  **Then** the capturing provider records **exactly two** `LogLevel.Warning` entries — one naming the **no ambient offered** condition and one naming the **ambient offered for an `AlwaysNew` ask and ignored** condition, both naming the same provider implementation type — and repeating both operations in the same host records no further entry.
  This branch is what pins **independent latching** (FR-24's diagnostic model), and it is the only case in this document that does: a single latch shared across the three conditions records one entry and fails it, and so does a latch keyed on the provider implementation type alone. Every other `Warning` AC uses a provider that can trip exactly one condition — AC-31's returns `null` on every ask, AC-29's host has only a stale ambient, and this AC's own second branch never returns nothing — so each of them passes under either latching scheme.
  *Why this is a resolution-time assertion:* both subscribers' handlers — and therefore their `IUnitOfWork` dependencies — are resolved inside `BuildAsync`, in the controller's own flow, before either subscriber runs (`PipelineBuilder.cs:228-229`). So this AC fails unless FR-9's **resolution-time** bracket (a) is implemented; an execution-time bracket alone cannot make it pass.

- **AC-12 (FR-8, FR-9, NFR-4) — Suppression propagates into a subscriber and does not leak out of it.**
  **Given** an opted-in ASP.NET application with all three of `HandlerLifetime`, `MapperLifetime` and `TransformerLifetime` set to `Scoped` (an FR-22.2-conformant triple), and request-scope `IUnitOfWork` instance `R`; subscribers A and B for the same event, each holding a `Scoped` `IUnitOfWork`, each signalling entry and awaiting a gate so their executions provably overlap — **every gate bounded by an explicit timeout that fails the test rather than hanging it**, since `PublishAsync` starts every subscriber (`CommandProcessor.cs:591-599`) and then awaits them together at `:601`, so an unbounded gate deadlocks the publish; and A calling `SendAsync(new InnerCommand())` from inside `HandleAsync`,
  **When** `PublishAsync` runs both concurrently,
  **Then** the test asserts both subscribers were in flight simultaneously;
  **And** neither subscriber's own `IUnitOfWork` is `R` — which fails unless suppression was established at the **resolution-time** bracket, since both subscribers' handlers were resolved during `BuildAsync` before either ran (FR-9(a));
  **And** `InnerCommand`'s handler resolved an `IUnitOfWork` that is not `R`, not A's and not B's;
  **And** — the assertions that can actually fail on a leak — after the publish completes, a `Send` **and** a `Post` issued from the controller outside any subscriber both resolve from `R`'s scope, proving suppression was restored on A's and B's exit paths rather than left set on the caller's flow.
  *Note:* an assertion that "B's own `IUnitOfWork` is unaffected by A's suppression" would be vacuous — under FR-8 B is `AlwaysNew` and suppressed regardless, so a leak from A into B is unobservable from B's side. A leak is only visible via a pipeline that *should* adopt, which is why the final clause is written against the post-publish controller calls.

**The seam**

- **AC-13 (FR-10, FR-8, FR-27.1, NFR-6) — Core expresses scoping only through the seam, with the correct affinity mix.**
  **Given** a fake `IAmAScopeProvider` implemented in a test assembly with no reference to `Microsoft.Extensions.DependencyInjection`, recording every `GetAmbient(ScopeAffinity)` call and the affinity it carried, **with the affinity option set to `JoinAmbient`** and all three lifetimes `Scoped`,
  **When** one `Send`, one `Publish` with three subscribers, and one `Post` are executed,
  **Then** the recorder shows **exactly** five adoption decisions: `JoinAmbient` for the `Send`'s handler pipeline, `JoinAmbient` for the `Post`'s transform pipeline (one decision for the pipeline, shared by the mapper and transformer factories — C-19, D12), and `AlwaysNew` for each of the three `Publish` subscribers — the subscribers ask too, and are recorded, because the ask is unconditional for any pipeline that takes a pipeline scope (**D16**, FR-27.1);
  **And** no further decision is recorded for any individual resolution within a pipeline (NFR-6), and none for the `Post`'s transformer factory separately from its mapper factory.
  *Note:* per D11 the fake provider neither supplies nor disposes the resolution scope — the container package does — so this AC characterises **which affinity each pipeline asked with**, and nothing else. It asserts nothing about scope release, which the fake cannot observe and which for the two adopting pipelines does not happen at all (FR-12). AC-15, AC-17 and AC-35 assert resolution source; AC-23 and AC-37 clause 3 carry NFR-6's release-count half, both of which have instruments for it.

- **AC-14 (FR-11, FR-15) — Not opted in ⇒ adoption behaviour identical to today.**
  **Given** an application configured exactly as before this change — no `IAmAScopeProvider` registered and the affinity option left at its default — with an `IHttpContextAccessor` spy registered,
  **When** the existing Brighter test suite for `Send`, `Publish`, `Post`, `DepositPost` and consumption is run,
  **Then** it passes, and the spy records zero accesses;
  **And** the tests excluded from this AC are those whose subject is the pre-change *single-factory* `Scoped` scope, which changes under D3/FR-20 — at minimum, in `tests/Paramore.Brighter.Extensions.Tests/`: `When_releasing_a_scoped_mapper_it_should_stay_usable_for_later_resolutions.cs`, `When_two_threads_first_resolve_a_scoped_mapper_concurrently_it_should_not_leak_a_scope.cs`, and `When_disposing_a_factory_holding_a_scoped_async_disposable_only_mapper_should_dispose_it.cs`. The list is a floor, not a closed enumeration.
  *Explicitly NOT excluded:* `FactoryLifetimeTests.Factory_WithScopedLifetime_ReturnsSameInstanceWithinScope` (`FactoryLifetimeTests.cs:36-55`) and its async twin `AsyncFactory_WithScopedLifetime_ReturnsSameInstanceWithinScope` (`:154`). These assert *within-pipeline* handler identity — two `Create` calls against **the same** `TestLifetimeScope` returning the same instance — which is exactly the behaviour FR-7 requires to be preserved. They must keep passing unchanged, and serve as regression guards for AC-9.

- **AC-30 (FR-24.1) — A throwing provider surfaces to the caller.**
  **Given** all three lifetimes `Scoped` — so both the `Send`'s handler pipeline and the `Post`'s transform pipeline consult the ambient source (FR-27.1) — and an `IAmAScopeProvider` whose `GetAmbient` throws `InvalidOperationException`,
  **When** `Send` is called,
  **Then** the caller observes that `InvalidOperationException` unwrapped, and no pipeline scope is leaked;
  **And when** `Post` is called in the same host,
  **Then** the caller observes that same `InvalidOperationException` unwrapped, and no pipeline scope is leaked. Without this second branch an implementation that leaked the pipeline scope on the transform-pipeline build path would pass, because the two verbs build different pipelines whose builders differ in what they clean up before the fault leaves.

- **AC-31 (FR-24.2) — A null-returning ambient query is treated as "no ambient".**
  **Given** all three lifetimes `Scoped`, **the affinity option `JoinAmbient`**, and an `IAmAScopeProvider` whose `GetAmbient` returns `null`,
  **When** `Send` is called twice,
  **Then** both calls succeed with behaviour identical to the unregistered case (FR-11), and a capturing `ILoggerProvider` records exactly one `LogLevel.Warning` entry naming the **no ambient offered** condition and the provider's implementation type (FR-24's diagnostic model);
  **And given** a **second host of the same shape** — a fresh Brighter container, so FR-24.2's latch starts unlatched (**D19**, and the reading note above) — registering the **same** provider implementation type, with the affinity option **`AlwaysNew`**,
  **Then** the two `Send` calls behave identically but the capturing provider records **no** `Warning` at all — an `AlwaysNew` ask returning nothing is conforming behaviour, not a failure mode (FR-24.2's carve-out). Without this branch an implementation that warns on every `AlwaysNew` ask — on the default affinity, and on FR-25.11's register-without-opting-in gesture — would pass.

- **AC-32 (FR-24.3) — Duplicate providers: the last registration wins, and the duplicate is reported.**
  **Given** two **distinct** `IAmAScopeProvider` implementations, each registered with a plain `services.AddSingleton<IAmAScopeProvider, T>()` in a stated order (FR-24.3 forbids `TryAdd` here precisely so both descriptors exist), with `ValidatePipelines()` called **after both registrations** (per C-15's snapshot semantics), and all three lifetimes `Scoped`,
  **When** the host starts and a `Send` is executed,
  **Then** validation reports exactly one warning that names **both** provider types, identifies the **last**-registered one as the effective provider, and contains the literal string `docs/guides/lifetimes-and-scoping.md`;
  **And** the pipeline resolved via the **last**-registered provider, matching MS DI's resolution of the service type;
  **And given** the *same* implementation type registered twice instead,
  **Then** no warning is reported — repeated registration of one type is idempotent in effect and is not a finding.

- **AC-33 (FR-13) — Disposal failure on a successful pipeline does not affect the result.**
  **Given** all three lifetimes `Scoped` and **not opted in**, so the pipeline scope is one Brighter created and owns (FR-13, D11) — and, as the stated injection point, a container-`Scoped` dependency of the handler whose `Dispose()` throws `InvalidOperationException`: MS DI disposes a scope's tracked disposables when the scope is disposed and does not swallow their exceptions, so releasing the owned pipeline scope throws. (A borrowed scope cannot be used here — Brighter never disposes one, FR-12 — and the provider supplies no disposable scope, D17, which is why this AC discharges FR-13 and not FR-24.)
  **When** `Send` is called and the handler completes normally,
  **Then** the caller observes normal completion and the handler's result unchanged, and a capturing `ILoggerProvider` registered for `Paramore.Brighter.*` records the disposal failure at `LogLevel.Error`;
  **And when** a second `Send` is issued,
  **Then** it succeeds identically — the failure is logged and swallowed, not latched.
- **AC-51 (FR-13, FR-5, FR-6) — A handler-factory `Release` that throws is logged and does not reach the caller.**
  **Given** all three lifetimes `Scoped` and **not opted in**, so the handler pipeline's scope is one Brighter created and owns, and a handler factory whose `Release` throws `InvalidOperationException` — the sibling case to AC-33, which covers the *scope disposal* half of FR-13's teardown rule while this covers the *handler release* half,
  **When** `Send` is called and the handler **completes normally**,
  **Then** the caller observes normal completion and the handler's result unchanged, and a capturing `ILoggerProvider` registered for `Paramore.Brighter.*` records the release failure at `LogLevel.Error`;
  **And given** the same host and a handler whose `Handle` throws `InvalidOperationException`,
  **When** `Send` is called,
  **Then** the caller observes **that** `InvalidOperationException` — not the release failure, and not an `AggregateException` composing the two — and the release failure appears only in the log at `LogLevel.Error`. This is the clause that fails on the natural wrong implementation: a teardown that rethrows replaces the handler's own exception, because the builder is disposed under `using var`, which FR-5 and FR-6 forbid;
  **And given** three tracked handlers whose factory's `Release` throws on the **first**,
  **When** the pipeline is released,
  **Then** the other two are still released, the pipeline scope is still disposed, and exactly one `LogLevel.Error` record names the failing release — a failure must not skip the remaining reclamation, which is the latent defect this rule closes;
  **And when** a second `Send` is issued in the same host,
  **Then** it succeeds identically — the failure is logged and swallowed, not latched.

- **AC-52 (FR-16c, C-21) — A handler's outbox write is in the caller's transaction when opted in, and is not when it is not.**

- **AC-43 (FR-17, FR-22, FR-24.3, FR-25, NFR-10) — Every validation message points at the guidance.**

- **AC-44 (NFR-10) — The guidance is self-sufficient.**
  **Given** the merged `docs/guides/lifetimes-and-scoping.md`,
  **When** a reviewer walks each of the seven messages from AC-43 to the troubleshooting entry it names, and from there to the decision guide,
  **Then** each path yields a concrete correction, of the kind the message calls for:

  - for the unreadable-override warning (FR-17) — a specific corrective **registration** action: that the override is registered as a constructed instance rather than by factory delegate, and what is lost until it is (a conflicting repeat carrying that override cannot be reported, while the affinity itself still takes effect);

  - for the defeated-opt-in error (FR-22.4) — a specific corrective **registration** action: which registration to remove (the application's own `IBrighterOptions`), how to express the same configuration through `AddBrighter`/`AddConsumers` instead, and what the affinity is while the override is defeated — whatever the application's own object carries, which is the option's default `AlwaysNew` unless the application set it;

- **AC-37 (FR-26, NFR-5) — Borrowed-scope state does not accumulate across requests.**
  **Given** an opted-in ASP.NET host (all three lifetimes `Scoped`) whose controller action performs two `Post`s and one `Send`,
  **When** the following three measurements are taken,
  **Then** all three hold:
  1. **Reachability.** A `WeakReference` (not tracking resurrection) is taken to the mapper instance used by request 1. After 10,000 further requests and `GC.Collect(); GC.WaitForPendingFinalizers(); GC.Collect();`, `weakRef.IsAlive` is `false`.
  2. **Positive control, on the production path.** The same harness is run against a host whose Brighter-held per-scope association is deliberately made process-lifetime — registered `Singleton` rather than `Scoped`, or replaced by a test double that never releases — and reports `IsAlive == true`. The control must exercise *Brighter retaining the association*, which is the failure FR-26(a) describes; a test-owned static field holding the mapper would prove only that `WeakReference` and `GC.Collect` behave as documented.
  3. **Steady state.** The peak number of live Brighter-held per-scope associations, sampled while requests are in flight, is measured for concurrency C = 1 and C = 8 over 10,000 requests each; both peaks are bounded by a constant multiple of C, and neither grows with the request count. The instrument is a test-visible count of those associations — incremented when one is created, decremented when it is released. If the ADR adopts FR-26's *Note* mechanism (the association is itself a container-`Scoped` service), the counter is incremented in its constructor and decremented in its `Dispose`, so the clause measures the container actually releasing it rather than being true by construction.

- **AC-38 (FR-5, FR-12) — A failed build under `JoinAmbient` disposes nothing the caller owns.**
  **Given** an opted-in ASP.NET host (all three lifetimes `Scoped`) with a mapper whose constructor depends on an unregistered service, so the transform pipeline build throws,
  **When** a controller action calls `Post` 100 times, each failing,
  **Then** each call throws `ConfigurationException`; **and** the request scope is **not** disposed — the controller can still resolve and use its own `Scoped` `IOrderDbContext` after the failures; **and** no Brighter-owned scope is leaked, because under adoption none was created.

- **AC-39 (FR-8, FR-9, NFR-4) — Synchronous `Publish` isolates each subscriber and leaves the caller's flow unsuppressed.**
  **Given** an opted-in ASP.NET host (all three lifetimes `Scoped`) with request-scope `IUnitOfWork` instance `R`, and three **synchronous** subscribers for `OrderPlaced` each taking a `Scoped` `IUnitOfWork`, **two** of which — identified by their own recorded markers, **not** by execution order — each call `Send(new InnerCommand())` from inside `Handle`,
  **When** a controller action calls `Publish(orderPlaced)` (the sync path, `Handle` not `HandleAsync`, dispatched via `Parallel.ForEach` at `CommandProcessor.cs:481`),
  **Then** all three subscribers resolved distinct `IUnitOfWork` instances, none of them `R`;
  **And** each nested `Send` resolved an `IUnitOfWork` that is neither `R`, nor its own subscriber's, nor the other nesting subscriber's or its nested `Send`'s — which pins D6 and OOS-14 on the sync path (a pipeline nested inside a subscriber neither re-enters its parent subscriber's scope nor shares one with a sibling's). It is **not** a detector of suppression leaking **between** subscribers: per FR-9(i) that leak is unobservable, because under FR-8 every subscriber is suppressed anyway, so a correct implementation and a leaking one produce identical results here;
  **And** — the clauses that actually fail on a leak — after `Publish` returns, a `Send` **and** a `Post` issued from the controller outside any subscriber both resolve from `R`'s scope, which is false if suppression was established around the dispatch loop in the caller's own flow instead of inside each subscriber body (FR-9);
  **And** no assertion depends on which subscriber ran first, and no gate requires two subscriber bodies to overlap in order for the test to pass: `Parallel.ForEach` neither orders nor guarantees overlap and may inline every body on the calling thread (FR-9). Any latch used to observe overlap is bounded by an explicit timeout, and its expiry records "no overlap observed" without failing the test — the concurrency assertion belongs to AC-12 (the async path), not here.

- **AC-45 (FR-17, FR-14) — The opt-in reaches the object the factories read, on all four registration paths.**
  **Given** four hosts, each using exactly one Brighter registration entry point — `AddBrighter(Action<BrighterOptions>)`, `AddBrighter(Func<IServiceProvider, BrighterOptions>)`, `AddConsumers(Action<ConsumersOptions>)` alone, and `AddConsumers(Func<IServiceProvider, ConsumersOptions>)` alone (all four route through `BrighterHandlerBuilder`, so each is a complete host) — each setting all three lifetimes `Scoped` and each calling the new package's registration extension with no affinity argument (so the `JoinAmbient` default applies),
  **When** each host is built and `IBrighterOptions` is resolved,
  **Then** in all four the affinity option on the resolved `IBrighterOptions` — the object the factories read (`ServiceProviderMapperFactory.cs:44`) — is `JoinAmbient`, not the `AlwaysNew` default, even on the three paths that run no `IOptions` pipeline (C-12a);
  **And when** a request-scope ambient is available and a `Send` is issued from within it,
  **Then** in all four the handler resolves the ambient's `Scoped` instance;
  **And when** all four hosts are rebuilt so that each **first** sets `DefaultScopeAffinity = ScopeAffinity.JoinAmbient` by whatever means its entry point supports (the `Action` delegate; the instance the `Func` returns) and **then** calls the extension passing `ScopeAffinity.AlwaysNew`,
  **Then** in all four the resolved `IBrighterOptions` carries `AlwaysNew` and no pipeline adopts. The non-default starting value is what makes this clause falsifiable: `AlwaysNew` is the property's own default (FR-14), so a Then written against a fresh host would also pass on an implementation that dropped the argument entirely — this one cannot. It is simultaneously the four-path form of D18's extension-wins rule (**D13**, **D18**).

- **AC-48 (FR-17, C-10) — The extension's argument wins over an affinity the application assigned itself.**
  **Given** an ASP.NET host with all three lifetimes `Scoped` that sets `DefaultScopeAffinity = ScopeAffinity.AlwaysNew` in its own `AddBrighter(Action<BrighterOptions>)` delegate **and** calls `AddBrighterRequestScope()` with no affinity argument, so the extension's `JoinAmbient` default applies — the conflicting combination FR-17 declares a configuration error,
  **When** the host is built, `IBrighterOptions` is resolved, and a controller action calls `Send`,
  **Then** the resolved `IBrighterOptions` carries **`JoinAmbient`** and the handler resolves the controller's own `Scoped` instance — the extension's argument is the value (**D18**);
  **And** the same holds with the extension call placed **before** `AddBrighter` as well as after it — the rule is not an ordering rule (C-10);
  **And** no validation finding is raised for the conflict, on either ordering — per FR-17 it is documented (FR-25.11), not validated, because without the sentinel FR-17 bans it is indistinguishable from the ordinary opt-in;
  **And given** the mirror configuration — the application's own delegate setting `JoinAmbient` while the extension is passed `ScopeAffinity.AlwaysNew`,
  **Then** the resolved `IBrighterOptions` carries `AlwaysNew` and nothing adopts, so the rule is symmetric and is not "the more permissive value wins".

- **AC-49 (FR-17, FR-25, NFR-10) — A repeated opt-in resolves to the last call, and a conflicting repeat is reported.**
  **Given** an ASP.NET host with all three lifetimes `Scoped` that calls the registration extension **twice** — first passing `ScopeAffinity.AlwaysNew`, then passing `ScopeAffinity.JoinAmbient` — with `ValidatePipelines()` called after both calls (per C-15's snapshot semantics),
  **When** the host is built, `IBrighterOptions` is resolved, and a controller action calls `Send`,
  **Then** the resolved `IBrighterOptions` carries **`JoinAmbient`** — the last call's argument — and the handler resolves the controller's own `Scoped` instance, so the affinity and the provider agree on which call won;
  **And** validation reports exactly one `Warning` for the repeat, naming both `AlwaysNew` and `JoinAmbient`, identifying `JoinAmbient` as the effective value, and containing the literal string `docs/guides/lifetimes-and-scoping.md`;
  **And** no *duplicate-provider* finding is raised alongside it (FR-24.3): both calls register the same provider implementation type, which that rule excludes;
  **And given** a second host of the same shape calling the extension in the reversed order — `JoinAmbient` then `AlwaysNew`,
  **Then** the resolved `IBrighterOptions` carries `AlwaysNew`, nothing adopts, and the same single `Warning` is reported naming both values — so the rule is "last call wins", not "the more permissive value wins";
  **And given** a third host of the same shape calling the extension twice with the **same** affinity,
  **Then** that affinity is effective and validation reports **no** finding for the repeat: a repeated identical opt-in is idempotent in effect, exactly as a repeated identical provider registration is under FR-24.3 (AC-32's second branch).

- **AC-50 (FR-22.4, FR-17, FR-14) — An opt-in defeated by an application's own `IBrighterOptions` registration is reported, not silent.**
  **Given** an ASP.NET host that registers its own options object **before** Brighter — `services.AddSingleton<IBrighterOptions>(new BrighterOptions { HandlerLifetime = ServiceLifetime.Scoped, MapperLifetime = ServiceLifetime.Scoped, TransformerLifetime = ServiceLifetime.Scoped })`, an FR-22.2-conformant triple so that no lifetime rule fires — and then calls `AddBrighter(Action<BrighterOptions>)`, whose delegate sets no lifetime (the triple validation reads is the pre-registered object's, which is the point), and `AddBrighterRequestScope()` with no affinity argument, so the extension's `JoinAmbient` default applies; with `ValidatePipelines()` called last and **`throwOnError: false`**, so that startup proceeds and the runtime clauses below are reachable at all (C-15). The pattern is live in the repository today (`tests/Paramore.Brighter.Core.Tests/CommandProcessors/Pipeline/When_A_Handler_Is_Part_Of_An_Async_Pipeline.cs:23` and its siblings register `IBrighterOptions` themselves),
  **When** the host is built, `IBrighterOptions` is resolved, and a controller action calls `Send`,
  **Then** the resolved `IBrighterOptions` carries **`AlwaysNew`** — the application's own object won the `TryAddSingleton` and Brighter's own registration, the only place the override is applied, never ran — and the handler does **not** resolve the controller's `Scoped` instance;
  **And** validation reports exactly one `Error`, naming the affinity the extension registered, stating that the resolved `IBrighterOptions` did not come from Brighter, and containing the literal string `docs/guides/lifetimes-and-scoping.md` (FR-22.4);
  **And** no *other* finding is raised — the triple is FR-22.2-conformant and, the override having been defeated, the resolved affinity is `AlwaysNew`, so FR-22.1's `JoinAmbient` precondition fails; a rule that reported both would be reporting the same defect twice;
  **And when** the same host is configured with **`throwOnError: true`** (the default),
  **Then** startup fails with `PipelineValidationException` carrying that message and no controller action runs — the same split AC-27 and AC-28 make for the other two errors;
  **And given** the same host with the **application's own registration placed *after* `AddBrighter`** — a plain `services.AddSingleton<IBrighterOptions>(...)`, which does not contest the `TryAdd` but wins resolution as the **last unkeyed** descriptor, the rule FR-24.3 relies on,
  **Then** the same single `Error` is reported: FR-22.4's condition is that the resolved object is not Brighter's, and both orderings satisfy it. This is the branch that fails under a detection mechanism which only records whether Brighter's own `TryAddSingleton` found the service already present;
  **And given** a host in which the extension is passed **`ScopeAffinity.AlwaysNew`** over a pre-registered `IBrighterOptions` that also carries `AlwaysNew` — override and resolved object holding the *same* value,
  **Then** the same single `Error` is still reported. This is the only branch that fails under an implementation detecting the defeat by comparing the override's affinity with the resolved object's, which is why FR-22.4 forbids that mechanism;
  **And given** the same host with the *extension* call placed **before** `AddBrighter` — AC-48's ordering, on which the extension is required to win,
  **Then** the same single `Error` is reported: the defeat is not an ordering failure of the extension, and no placement of the extension call avoids it;
  **And given** a host of the same shape on each of the other three registration entry points — `AddBrighter(Func<IServiceProvider, BrighterOptions>)`, `AddConsumers(Action<ConsumersOptions>)` alone and `AddConsumers(Func<IServiceProvider, ConsumersOptions>)` alone,
  **Then** the same single `Error` is reported on each, so the rule covers all four paths that AC-45 covers positively. **The two consumer hosts must pre-register a `ConsumersOptions` instance as `IBrighterOptions`**, not a bare `BrighterOptions`: the `Func` overload binds `IAmConsumerOptions` by casting whatever `IBrighterOptions` resolves to (`ServiceActivator.Extensions.DependencyInjection/ServiceCollectionExtensions.cs:89-90`), so a bare `BrighterOptions` throws `InvalidCastException` while the dispatcher is constructed — before any validation host starts — and the `Error` this AC asserts would never be reached (**C-12**). Both consumer hosts register `ServiceActivatorHostedService` explicitly, since `AddConsumers` does not (C-15, D14);
  **And given** a control host identical to the first except that the application's registration is removed and the same `{Scoped, Scoped, Scoped}` triple is set in the `AddBrighter(Action<BrighterOptions>)` delegate instead — so that the only difference is *who* registered `IBrighterOptions`,
  **Then** validation reports **no** finding, the resolved `IBrighterOptions` carries `JoinAmbient`, and the handler resolves the controller's own `Scoped` instance — so the `Error` is attributable to the defeated registration and not to the host shape.

- **AC-53 (FR-17) — An affinity override registered by factory delegate is reported, and the repeat it hides is what the report is about.**
  **Given** a host with an FR-22.2-conformant `{Scoped, Scoped, Scoped}` triple that registers an affinity override **by factory delegate** rather than as a constructed instance — the shape a third-party opt-in package can write, since the override type is public in the DI package — with `ValidatePipelines()` called last and `throwOnError: true` (the default, which a warning must not trip),
  **When** the host starts and its validation output is captured,
  **Then** startup **succeeds**, and exactly one `Warning` is reported that states an affinity override is registered by factory delegate, that its value cannot be read without resolving, and that the remedy is to register it as a constructed instance, and that contains the literal string `docs/guides/lifetimes-and-scoping.md`;
  **And** the affinity that override carries **is** the effective one on the resolved `IBrighterOptions` — the finding is about reportability, not about a lost opt-in, and an implementation that treated the delegate registration as a defeat would fail here;
  **And given** a second host of the same shape that registers **two** overrides carrying **different** affinities, one as an instance and one by factory delegate,
  **Then** the unreadable-override `Warning` is reported and FR-17's repeated-opt-in `Warning` is **not** — the delegate-registered descriptor contributes nothing to the distinctness set, so only one distinct value is visible, which is precisely the silence this rule exists to break;
  **And given** a third host of the same shape registering its override as a **constructed instance**, as ADR 0073's extension does,
  **Then** validation reports **no** finding — so the `Warning` is attributable to the registration shape and not to the presence of an override.

- **AC-46 (FR-27.1, FR-27.2) — The ambient query is made only for `Scoped` pipelines, and a pipeline mixing `Scoped` with `Transient` declines to adopt.**
  **Given** the recording `IAmAScopeProvider` of AC-13 with the affinity option `JoinAmbient`, and `ValidatePipelines()` **not** called — the second configuration below is an FR-22.2 violation, and this AC pins what the seam does when validation was never run (C-15),
  **When** a host with `{Transient, Transient, Transient}` executes one `Send`, one `Publish` with three subscribers and one `Post`,
  **Then** the recorder shows **zero** adoption decisions and no pipeline scope taken — `Transient`'s per-resolution scope does not pass through the seam (FR-27.1, C-6, ADR 0067);
  **And when** a host with `{HandlerLifetime = Transient, MapperLifetime = Scoped, TransformerLifetime = Transient}` executes one `Post` from within an available ambient, **using a mapper that declares no `[WrapWith]`/`[UnwrapWith]` transform at all**,
  **Then** the recorder shows exactly one adoption decision for that transform pipeline carrying **`AlwaysNew`** — the ask is made despite the affinity being `AlwaysNew`, which is what makes the decline observable at all (**D16**, FR-27.1) — and the mapper's container-`Scoped` dependency is **not** the ambient's instance — a pipeline mixing `Scoped` with `Transient` creates its own scope rather than adopting for half the pipeline (FR-27.2), and the transformer factory counts as a participating factory even though it resolved nothing (**D12**). This is the boundary case the structural definition exists to settle.

- **AC-47 (FR-27.3, FR-8) — Suppression fires for subscriber pipelines only, and fires even when the subscriber's own pipeline takes no scope.**
  **Given** an opted-in ASP.NET host with `{HandlerLifetime = Transient, MapperLifetime = Scoped, TransformerLifetime = Scoped}` and `ValidatePipelines()` **not** called (FR-22.2 would reject this triple; the AC pins the seam rule — C-15), with request-scope `IMarker` instance `R` injected into the mapper, and a `Send` handler and a `Publish` subscriber that each issue the same `Post`,
  **When** a controller action calls `Send`,
  **Then** the nested `Post`'s mapper resolves `R` — the parent handler pipeline is `Transient`, so it takes no pipeline scope (FR-27.1) and, not being a subscriber, suppresses nothing (FR-27.3);
  **And when** the controller action calls `Publish` instead,
  **Then** the nested `Post`'s mapper resolves an instance that is **not** `R` — a subscriber suppresses the ambient for pipelines nested inside it even though its own pipeline has no `Scoped` participant and took no scope of its own (FR-8, FR-27.3, D6). Suppression here must come from FR-9's **execution-time** bracket, since the nested `Post` is created while the subscriber runs.

### Design notes

**Why the per-message ambient was rejected** (issue comment 2). It was cheap to implement, but it was not uniform — because MS DI scopes do not nest (C-1), a `Publish` subscriber's scope would be a *sibling* of the message scope and would see nothing from it, forcing the rule to be documented as "`Scoped` means per message, except for events, where it means per subscriber". It also extends resource lifetime — today the transform pipeline is released before dispatch begins, whereas under a message-wide scope any connection or `DbContext` the mapper resolved would be held through handling and through the ack.

**Why subscriber isolation propagates (D6).** ADR 0039 makes each subscriber its own unit of work. If isolation stopped at the subscriber boundary, the first `Send` a subscriber issued would rejoin the request scope the subscriber was deliberately isolated from — so a handler could not join the caller's transaction, but anything it called could. Propagating suppression keeps the rule stateable in one sentence and keeps C-4 true all the way down. The cost is an `AsyncLocal` suppression flag, which is why OOS-2 is amended rather than simply upheld.

**What is already correct and must stay correct.** `CommandProcessor` brackets every call with `using var builder = new PipelineBuilder<T>(...)` (`CommandProcessor.cs:317`, `:394`, `:472`, `:575`) and `PipelineBuilder.Dispose()` disposes every instance scope created; each subscriber gets its own `HandlerLifetimeScope` (`PipelineBuilder.cs:528`, `:539`) which `ServiceProviderHandlerFactory` keys a `ServiceProviderLifetimeScope` on (`ServiceProviderHandlerFactory.cs:127`). ADR 0064 (`0064-pipeline-cache-type-key`) memoises reflection-derived pipeline metadata only, never instances. FR-7/AC-9 and FR-8/AC-10 are regression guards over this.

**Residual differences after the change.** Under `AlwaysNew`, a `Scoped` mapper and a `Transient` mapper differ only in that `Scoped` shares its scoped dependencies between the mapper and its transforms within one pipeline, while `Transient` gives each resolution its own scope (ADR 0067). Under `JoinAmbient` there is a second difference: a `Scoped` mapper is additionally shared *across* pipelines within one request (FR-16a), which a `Transient` mapper never is.

**Highest-risk area.** FR-8 / FR-9 / AC-12 / AC-39 — the two brackets and the suppression flag. Both publish paths resolve every subscriber's pipeline before running any of them (sync `CommandProcessor.cs:474` then `:481`; async `:581` then `:591-599` and `:601`), and `PipelineBuilder.Build` resolves handlers and decorators per subscriber inside that build (`PipelineBuilder.cs:183-187`). So the resolution-time bracket and the execution-time bracket sit in different places and fail differently: put the scope only at dispatch and every subscriber resolves from the caller's ambient; put suppression around the whole build loop and all subscribers share one; put it around the dispatch loop and the caller stays suppressed after the publish returns; omit the explicit restore inside the body and — because `Parallel.ForEach` restores `ExecutionContext` per worker task, not per body — one subscriber's flag flows into the next subscriber that worker runs. **The first three are directly detectable and AC-12 and AC-39 between them must detect them.** The fourth is **not detectable at all**: the cross-body leak is unobservable in its own right, because under FR-8 the next subscriber must be suppressed anyway (FR-9(i)), and it does not reach the caller either — `ExecutionContext` is restored per replica, including an inlined one, so a body-level write never escapes the loop. It is the reason the restore must be explicit, not something a test can catch. Neither path may be specified or tested in terms of subscriber ordering. Both should be driven test-first.

**A misnamed existing test.** `tests/Paramore.Brighter.Extensions.Tests/AssemblyResolutionHandlerLifetimeScopedAndMapperLifetimeSingletonTests.cs` does **not** exercise the mixed configuration its name claims: it calls `AddConsumers()` with no options, so all three lifetimes are the `Transient` default, and it asserts `Transient` registrations. It should not be mistaken for existing coverage of FR-22.2, and renaming it is worth a tidy-first task.

**Prior art.** ADR 0033 `0033-lifetime-of-command-processor-and-mediator` (CommandProcessor is a singleton — not reopened), ADR 0039 `0039-scoping-dependencies-inline-with-lifetime-scope` (the per-subscriber `HandlerLifetimeScope` — preserved and extended by D6; note its name is the `IAmALifetime` sense of "lifetime scope", not this document's *lifetime*, which is why NFR-8 exists), ADR 0066 `0066-release-factory-instances-on-an-opaque-lease`, ADR 0067 `0067-per-resolution-di-scope-for-transient-factory-instances` (the fix this builds on). ADRs 0033 and 0039 are status **Proposed**.
