# Requirements

> **Note**: This document captures user requirements and needs. Technical design decisions and implementation details should be documented in an Architecture Decision Record (ADR) in `docs/adr/`.

**Linked Issue**: #4573

## Problem Statement

**As an** operator running a Brighter service that uses `TimedOutboxSweeper`,
**I want** to see when an outbox sweep has hung or keeps failing, and to be told what kind of response it needs,
**so that** I can restart the process, investigate the broker or outbox, or take the instance out of service before unsent messages build up in the outbox (or, with the `InMemoryOutbox`, are lost when the process restarts).

Today a hung sweep cannot be seen:

- `TimedOutboxSweeper` runs its sweeps one after another on a dedicated thread (#4560 / #4562). While one sweep is hung, no later sweep starts. Until the hung sweep ends, the sweeper records no `paramore.brighter.outbox_sweeper.tick.lag`, `paramore.brighter.outbox_sweeper.sweep.duration` or `paramore.brighter.outbox_sweeper.sweeps` measurements at all.
- `lock_unavailable` sweeps appear only on *other* instances that share the distributed lock. With a single instance, or with the in-memory lock, a hang records nothing.
- The only alert available today is on the *absence* of `completed` sweeps (ADR 0081 `0081-timed-outbox-sweeper-health-metrics.md`, called "ADR 0081 (sweeper metrics)" below; docs from #4562). That is indirect and hard to tune.
- A run of failed sweeps shows only as Error log lines and as the `failed` count. Nothing reports the service as unhealthy.

Brighter cannot fix a hang itself. Blocking sync code and sync-over-async deadlocks ignore cancellation, and ADR 0081 (sweeper metrics) deliberately does not cancel a sweep in flight. Brighter can **detect** the hang and **tell an operator**.

A second problem, wider than the sweeper: Brighter's health checks tell an operator *that* something is wrong but not *what to do*. #4555's ADR tells users to map Degraded to HTTP 503 on readiness endpoints. That suits a consumer that cannot receive. It does not suit a hung sweeper. Removing the pod from the load balancer does nothing, because the sweeper serves no traffic. A restart is what clears a hang, and some conditions need neither, only investigation. A run of failed sweeps caused by an outbox or lock fault, and topics circuit-broken during a broker outage, are examples: restarting does not clear either. A single Degraded status, mapped to one HTTP status, cannot carry that distinction.

A third problem is the topic circuit breaker (ADR 0028). When publishing to a topic keeps failing, `IAmAnOutboxCircuitBreaker` trips that topic. The sweeper then leaves the topic's outstanding messages out of each sweep (they are excluded from `OutstandingMessagesAsync`) until the cooldown has run down, then tries again. The sweeper keeps running and records `completed` sweeps, so nothing tells an operator that it is only partly working. A broker outage mostly appears this way, as tripped topics, because a failed send trips the topic and does not make the sweep itself fail. Messages for a tripped topic wait in the outbox, and the lag looks unexplained from outside. ADR 0058 ("Outbox circuit breaker trip logging") adds logs, spans and a metric on each trip and recovery, but nothing reports the *current* set of tripped topics as a state, and a sweeper must not be reported Healthy while it is skipping topics.

## Proposed Solution

1. **A running-time gauge.** When `AddBrighterInstrumentation` is configured, the sweeper publishes how long the current sweep has been running, or 0 when no sweep is running. An operator alerts on `max(paramore.brighter.outbox_sweeper.sweep.running_time) > 3 × TimerInterval`. The alert works on a single instance, with the in-memory lock, and across instances that share a distributed lock.
2. **Opt-in sweeper health checks, one per remedy kind.** An operator who registers them gets a restart check, which is Degraded when the current sweep has run longer than a threshold, and an investigate check, which is Degraded after N consecutive failed sweeps or while an active sweeper has any topic circuit-broken (and when the tripped topics cannot be read). Each carries a tag, so the host can map the restart check to liveness and the investigate check to monitoring. The description says which condition applies, how long the sweep has run, how many sweeps have failed or which topics are tripped, and, for a hung sweep or failed sweeps, the `TimerInterval`.
3. **Tripped topics are surfaced.** While a sweeper that is actively sweeping has one or more topics circuit-broken, the investigate check reports Degraded and names those topics, and a gauge reports how many topics are tripped. Together they tell an operator why messages for some topics lag while others are swept normally.
4. **All signals keep reporting while the sweeper's thread is stuck.** The metrics exporter and the health-check host read them on their own threads.
5. **A Brighter convention for "what to do".** Every Degraded or Unhealthy condition reported by the new Brighter remedy checks tells an operator or orchestrator which kind of response it needs: restart, take out of service, or investigate. The convention covers the new sweeper checks (FR-4) and a new opt-in split of #4555's consumer check into a take-out-of-service check and a restart check (FR-12), and is documented for future checks. The existing consumer check keeps working unchanged and is marked obsolete in favour of the split (FR-10.2). These requirements define what an operator can see and do; the ADR decides the mechanism.

## Requirements

### Definitions

- **Sweeper**: an instance of `TimedOutboxSweeper` (`Paramore.Brighter.Outbox.Hosting`).
- **Sweep**: one pass of the sweeper on its dedicated thread. It **starts** immediately before the sweeper begins to acquire the distributed lock (after tick lag is recorded). It **ends** when the sweeper has its outcome, after any lock release. A sweep always ends with exactly one of the ADR 0081 (sweeper metrics) outcomes:
  - **Completed sweep**: outcome `completed`. The lock was obtained and the outbox sweep returned without throwing.
  - **Failed sweep**: outcome `failed`. Any exception escaped the sweep, whether from lock acquisition, the outbox sweep or lock release.
  - **Lock-unavailable sweep**: outcome `lock_unavailable`. Lock acquisition returned without a lock because another holder has it. This is **not** a failed sweep and **not** a completed sweep.
- **Stopped sweeper**: a sweeper whose stop has been requested (`StopAsync` or `Dispose`). The host does this at shutdown, and a stopped sweeper is not restarted. Stopping is the only way a sweeper stops.
- **Sweep in progress**: a sweep that has started and not yet ended.
- **Running time**: for a sweep in progress, the time from its start to now, measured with the sweeper's `TimeProvider`. **Lock acquisition time is included.** When no sweep is in progress, running time is 0.
- **Hang threshold**: the running time beyond which a sweep is treated as hung. Default: 3 × `TimerInterval`. It can be overridden with a positive duration. The default assumes a healthy sweep ends well within one interval, since a sweep that overruns its interval already shows as tick lag, so a sweep three intervals long is abnormal. A deployment whose healthy sweeps are slower than that (a large `BatchSize`, a slow broker) must raise the override, or the restart check will call a slow sweep hung.
- **Hung sweep**: a sweep in progress whose running time is **strictly greater than** the hang threshold.
- **Consecutive failed sweeps**: the number of failed sweeps since the sweeper started or since the last completed sweep, whichever is later. A completed sweep resets it to 0. A lock-unavailable sweep leaves it unchanged.
- **Failure threshold (N)**: the number of consecutive failed sweeps at which the sweeper is Degraded. Default: 3. It can be overridden with a positive integer.
- **Tripped topic**: a topic that `IAmAnOutboxCircuitBreaker` currently reports in `TrippedTopics`. The sweeper excludes its messages from the sweep until the circuit breaker cools it down and removes it.
- **Circuit breaker in use**: the `IAmAnOutboxCircuitBreaker` registered in the service provider. It is expected to be a singleton shared with the outbox producer mediator (see FR-6A.4). If none is registered, no topic is ever tripped.
- **Active sweeper**: while a sweep is in progress, a sweeper that holds the lock for it (from when `ObtainLockAsync` returns a lock until the sweep ends, so a sweep hung in `ReleaseLockAsync`, or between release and its outcome, is still active); while none is, a sweeper whose most recent ended sweep obtained the lock (outcome completed, or failed after the lock was obtained). A sweep in progress that is still acquiring the lock makes the sweeper not active until the lock is obtained, because it is not cooling anything down while it waits. A sweeper that has not yet obtained the lock for any sweep, or whose most recent ended sweep was lock-unavailable or failed while acquiring the lock, is not active unless it currently holds the lock for a sweep in progress. A sweeper whose stop has been requested is never active, whatever its sweeps did before. Cooldown of the circuit breaker advances only on a sweep that obtained the lock, so only an active sweeper cools its tripped topics down.
- **Remedy kind**: the kind of response a health condition needs. There are three kinds:
  - **restart**: the process should be restarted (a liveness decision).
  - **take out of service**: the instance should stop receiving work (a readiness decision).
  - **investigate**: an operator should look. Automation should neither restart nor remove the instance.
- **Remedy check**: a health check registration that reports only conditions of one remedy kind and carries a tag naming that kind. A host selects remedy checks with the standard `HealthCheckOptions.Predicate`.
- **Restart check** and **investigate check**: the sweeper's remedy checks for the remedy kinds restart and investigate (FR-4). "The check" in a requirement or criterion means the one of these that owns the condition being discussed: the restart check for FR-5, the investigate check for FR-6 and FR-6A.
- **Existing consumer check**: `BrighterServiceActivatorHealthCheck` as registered today by the user with `AddCheck`. It carries no remedy tag.
- **Consumer take-out-of-service check** and **consumer restart check**: the two remedy checks that split the existing consumer check's conditions (FR-12). Together, the **consumer remedy checks**.
- **Condition**: a named state a remedy check reports. The conditions are: hung sweep (FR-5), consecutive failed sweeps (FR-6), tripped topics (FR-6A), tripped topics unreadable (FR-13.2), persistent channel failures and missing consumers (FR-12).
- **Opt in**: an explicit registration call made by the user. No health check is added implicitly.

### Functional Requirements

**FR-1 — Track the sweep in progress.** The sweeper records when each sweep starts, and clears that record when the sweep ends, whatever its outcome. The record covers lock acquisition, so a sweep hung inside lock acquisition is a sweep in progress.
- Example: TimerInterval = 10 s. A sweep starts at t = 0 and lock acquisition blocks. At t = 25 s the running time is 25 s. The lock is then granted, the sweep completes at t = 40 s, and the running time becomes 0.
- Example: the in-memory lock is already held by another sweeper. A sweep starts at t = 0 and lock acquisition returns no lock straight away (lock-unavailable). Running time is 0 once that sweep has ended.
- **FR-1.1 — Stop with a sweep in flight.** If the sweeper is stopped while a sweep is still in progress and stop does not wait for it (ADR 0081 (sweeper metrics)), that sweep remains in progress. Its running time keeps growing and the restart check stays Degraded once it is past the hang threshold, until the sweep ends or the process exits. Example: a sweep has run 25 s when stop is requested and abandoned; at 31 s later the running time reads 56 s.
- **FR-1.2 — Stopped sweeper.** When stop is requested the sweeper becomes inactive (never active again) and keeps everything else it has recorded: the consecutive-failed-sweep count, the last outcome and any sweep in progress are neither reset nor changed by the stop itself. A stopped sweeper therefore reports what it last knew, except that it reports no tripped topics. Example: after 3 failed sweeps and a stop, the investigate check is still Degraded for the failures. Example: after a completed sweep with `orders` tripped and a stop, the tripped-topics gauge reads 0 and the investigate check does not report `orders`.

**FR-2 — Track consecutive failed sweeps and the last outcome.** The sweeper counts consecutive failed sweeps as defined above, and records the outcome of its most recent ended sweep (none before the first sweep ends), whether that sweep obtained the lock, and whether the sweep in progress currently holds the lock. "Active sweeper" is derived from these and from whether stop has been requested.
- Example: the outcomes failed, failed, lock_unavailable, failed give a count of 3. The outcomes failed, failed, completed, failed give a count of 1. Before the first sweep ends, the count is 0 and there is no last outcome (the sweeper is not active). After the outcomes completed, lock_unavailable the sweeper is not active; after lock_unavailable, then a sweep that obtained the lock and failed in the outbox, it is active; after a sweep that failed inside `ObtainLockAsync` it is not active. While a sweep is blocked in `ObtainLockAsync` the sweeper is not active, even if its previous sweep completed; once the lock is obtained it is active again.

**FR-3 — Running-time gauge.** When `AddBrighterInstrumentation` has been called, an observable gauge named `paramore.brighter.outbox_sweeper.sweep.running_time` reports the sweeper's running time in seconds (unit `s`) each time it is observed.
- **FR-3.1 — Value while a sweep is in progress.** It reports the running time at the moment of observation. Example: a sweep started 25 s ago (by the sweeper's `TimeProvider`) gives 25.0.
- **FR-3.2 — Value when no sweep is in progress.** It reports 0 before the first sweep starts, between sweeps, after any sweep ends (completed, failed or lock_unavailable), and after the sweeper has stopped with no sweep in flight.
- **FR-3.3 — Registration.** The gauge is an observable gauge (the value is a current level, to be compared with `max`, not summed) registered by `AddBrighterInstrumentation`, by the same route as the publish-confirmation queue-depth instrument (#4562), which is an observable up-down counter. `AddBrighterInstrumentation` cannot see `Paramore.Brighter.Outbox.Hosting`, so the sweeper's state must reach it through a type visible to `Paramore.Brighter.Extensions.Diagnostics`; the ADR designs that type. When `AddBrighterInstrumentation` is not called, no gauge is published and the sweeper behaves as it does today.
- **FR-3.4 — Attributes.** The gauge has a fixed, small set of attributes (cardinality must not grow with time, messages or sweeps). The ADR decides which attributes, if any.

**FR-3A — Tripped-topics gauge.** When `AddBrighterInstrumentation` has been called, an observable gauge named `paramore.brighter.outbox_sweeper.tripped_topics` reports the number of tripped topics each time it is observed, read from the circuit breaker in use, while the sweeper is an active sweeper (FR-6A). When the sweeper is not active it reports 0, because a sweeper that is not sweeping is not skipping any topic.
- Example: an active sweeper with two topics tripped gives 2. The same sweeper reads 0 while its next sweep is still blocked acquiring the lock. None tripped, no circuit breaker registered, or a sweeper that is not active, gives 0.
- The gauge is registered by `AddBrighterInstrumentation` in the same way as the running-time gauge (FR-3.3), adds no member to `IAmABrighterSweeperMeter`, and is not published when `AddBrighterInstrumentation` is not called.
- It carries no per-topic attribute: topic names are reported by the investigate check and by the trip and recovery logs, spans and metric (ADR 0058). The ADR decides whether any attribute is added; cardinality must stay bounded (FR-3.4).
- Like the running-time gauge, it is pulled and keeps reporting while the sweeper's thread is blocked (NFR-1).

**FR-4 — Sweeper health checks (opt in).** Brighter provides two remedy checks for the sweeper and one call that registers both with `IHealthChecksBuilder`:
- **Restart check**: reports the hung-sweep condition (FR-5).
- **Investigate check**: reports the consecutive-failed-sweeps condition (FR-6), the tripped-topics condition (FR-6A) and the tripped-topics-unreadable condition (FR-13.2).

Neither is added unless the user opts in. Each check reports **Healthy** or **Degraded** and never Unhealthy. Each is registered with a tag naming its remedy kind (FR-10.3), so a host can route each to a different endpoint. Both read the same sweeper state (FR-1, FR-2).
- Example: a sweep has run 31 s with a 30 s threshold, and 3 consecutive sweeps had failed before it. The restart check reports Degraded and the investigate check reports Degraded, each with its own description and tag.

**FR-4A — Sweeper not found, or more than one.** The registration call (FR-4) does not require a sweeper to be registered yet, since the order of service registrations is the user's. The checks and gauges look for the sweeper when they run. A sweeper is registered when the user has called `UseOutboxSweeper`, which registers it as a hosted service (it is not resolvable as `TimedOutboxSweeper` today). How the checks and gauges find it is the ADR's decision. They must find a sweeper registered by an unchanged user call to `UseOutboxSweeper`; what `UseOutboxSweeper` registers internally may change (the ADR decides).
- **FR-4A.1 — No sweeper.** When no sweeper is registered (`UseOutboxSweeper` was not called), nothing throws. Both checks report Healthy, with a description that says no outbox sweeper is registered and `Data` holding the remedy kind and an empty conditions collection. Both gauges report 0.
- **FR-4A.2 — More than one sweeper.** One sweeper per service provider is a supported-configuration rule, not a behaviour. With more than one sweeper registered (for example a second hosted service registered by hand; `UseOutboxSweeper` called twice adds no second sweeper), what the checks and gauges report is undefined, and the docs say so (FR-11). No acceptance criterion tests it.

**FR-5 — Degraded while a sweep is hung.** The restart check reports Degraded when, at the moment it runs, the sweep in progress is a hung sweep (running time > hang threshold). Otherwise this condition does not apply.
- Example: TimerInterval = 10 s, default hang threshold 30 s. Running time 31 s gives Degraded. Running time exactly 30 s gives Healthy. Running time 29 s gives Healthy. No sweep in progress gives Healthy.
- Example: hang threshold overridden to 2 minutes, TimerInterval = 10 s. Running time 90 s gives Healthy; running time 121 s gives Degraded.
- **FR-5.1 — Recovery.** When the hung sweep ends, whatever its outcome, the next run of the check no longer reports this condition. If the hung sweep ends as failed, it counts towards FR-6.

**FR-6 — Degraded after N consecutive failed sweeps.** The investigate check reports Degraded when the consecutive-failed-sweep count is greater than or equal to N. This matches #4555, where reaching the threshold is Degraded.
- Example: N = 3 (default). After 2 consecutive failed sweeps the check is Healthy. After 3 it is Degraded. After 4 it is still Degraded.
- Example: N = 3, outcomes failed, failed, lock_unavailable, failed give Degraded, because lock-unavailable does not reset the count.
- **FR-6.1 — Recovery.** The first completed sweep resets the count to 0, so the check reports Healthy (unless FR-5 applies). Example: failed × 3 (Degraded), then completed, gives Healthy.

**FR-6A — Degraded while an active sweeper has a topic tripped.** The investigate check reports Degraded when, at the moment it runs, the sweeper is an active sweeper and the circuit breaker in use reports one or more tripped topics. It applies whether the active sweeper's recent sweeps completed or failed; a sweep that skips a tripped topic is still `completed`. When no circuit breaker is registered, `TrippedTopics` is empty, or the sweeper is not active, this condition does not apply.
- Reason for the restriction: any instance can trip a topic from its request path, but the cooldown advances only on a sweep that obtained the lock. A sweeper that does not obtain the lock (another instance holds it, or the lock store is failing) never cools its tripped topics down, and without the restriction would stay Degraded until it next obtained the lock.
- Example: the sweeper's last sweep completed, and topics `orders` and `payments` are tripped. The check reports Degraded and its description names both. After the circuit breaker cools `payments` down and removes it, the next run names only `orders`. After `orders` is removed too, the next run no longer reports this condition.
- **FR-6A.1 — Recovery.** A topic stops counting as soon as the circuit breaker no longer lists it. A topic that is re-tripped while still listed stays counted.
- **FR-6A.2 — No threshold.** A single tripped topic is enough. There is no duration or count threshold for this condition.
- **FR-6A.3 — Source of truth.** The check reads the circuit breaker's current `TrippedTopics`. It does not keep its own copy, so it agrees with what the sweeper is skipping.
- **FR-6A.4 — Circuit breaker registration.** The check and the gauge read the `IAmAnOutboxCircuitBreaker` registered in the service provider. It must be registered as a singleton shared with the outbox producer mediator, so that both see the same tripped topics. Brighter documents this requirement (FR-11). If no circuit breaker is registered, the investigate check does not report this condition and the gauge reports 0. If the registered lifetime is not singleton, the signals read the instance the service provider returns and are not guaranteed to match the mediator's. This is a documented limitation and has no acceptance criterion.
- **FR-6A.5 — Not active.** When the sweeper is not an active sweeper (including a stopped one, FR-1.2), tripped topics on it (for example, tripped by its request path) are not reported by the check or the gauge. They become reported when the sweeper obtains the lock again and the topics are still tripped.
- **FR-6A.6 — Lock handover.** The lock is taken and released on every sweep, so which instance obtains it can change from tick to tick. A tick that collides with another instance's sweep ends lock-unavailable and makes the sweeper not active until it next obtains the lock, usually one `TimerInterval` later. That one-interval gap in the tripped-topic signals is accepted. So is the shorter gap in every sweep: while a sweeper whose last sweep obtained the lock is still acquiring the lock for its next one it is not active, so a probe or gauge read that lands in that window sees no tripped topics, and with a slow lock (a database round trip) that window is longer. The docs say so and recommend an alert that tolerates it (FR-11). Tripped topics are always one instance's view: `InMemoryOutboxCircuitBreaker` is per instance, even with a durable outbox and a distributed lock.

**FR-7 — Threshold configuration and validation.**
- **FR-7.1 — Hang threshold (restart check).** The default is 3 × `TimerInterval` (example: TimerInterval = 10 s gives 30 s; TimerInterval = 1 s gives 3 s). An override must be a positive duration. Zero or negative is rejected with `ArgumentOutOfRangeException` thrown by the registration call itself (FR-4), before any health-check run. A health check registered through the host's lazy factory is not constructed until the first probe, so validation must not wait for that. An override smaller than `TimerInterval` is allowed.
- **FR-7.2 — Failure threshold (investigate check).** The default N is 3. An override must be a positive integer. 0 or negative is rejected with `ArgumentOutOfRangeException` thrown by the registration call itself, before any health-check run. N = 1 is allowed (a single failed sweep gives Degraded).
- **FR-7.3 — Direct construction.** A check constructed directly with an invalid value also throws `ArgumentOutOfRangeException`, so no check can exist with an invalid threshold. This applies to every remedy check with a threshold, including the consumer take-out-of-service check (FR-12.3).

**FR-8 — Health check description.** The description names the condition and gives the values an operator needs:
- Hung sweep: the words "running" or "hung", the running time, the hang threshold and `TimerInterval`. Illustrative text: "Outbox sweep has been running for 31s, longer than the 30s threshold (TimerInterval 10s)".
- Consecutive failures: the consecutive-failed-sweep count, N and `TimerInterval`. Illustrative text: "3 consecutive outbox sweeps have failed (threshold 3, TimerInterval 10s)".
- Tripped topics: the number of tripped topics and their names (RoutingKey values), and a statement that messages for those topics are not being swept until their cooldown ends. Illustrative text: "2 topics are circuit-broken and are not being swept: orders, payments".
  - If more than 10 topics are tripped, the description names the first 10 in ordinal order of name and gives the total; the full list is always in the result's `Data` (FR-10.5). The ADR may change the limit of 10.
- More than one condition at once on the same check (the investigate check can have consecutive failures and tripped topics together): its description names each, with the values of each. Conditions owned by different checks are never merged into one description; each check describes only its own.
- Healthy: each check's description says only that its own conditions are absent: the restart check that no sweep is hung, and the investigate check that none of its conditions applies (fewer than N consecutive failed sweeps, no reported tripped topic, tripped topics readable). Nothing more is required, except when no sweeper is registered (FR-4A.1), when the description says so.

The ADR fixes the exact wording. The ACs check that the values are present, not the exact text.

**FR-9 — Shared distributed lock across instances.** When several sweepers share one lock (two sweepers sharing an in-memory lock in tests), only the instance with a hung sweep reports Degraded for FR-5. Instances whose sweeps are lock-unavailable report running time 0 between attempts and stay Healthy, because lock-unavailable sweeps are neither failures nor hangs. Likewise a sweeper whose sweeps are lock-unavailable is not an active sweeper (FR-6A), so topics tripped on it by its request path are not reported by the investigate check or the tripped-topics gauge. `max` of the running-time gauge across instances therefore equals the hung holder's running time with no special handling. If lock acquisition itself blocks on an instance for longer than the hang threshold, that instance reports a hung sweep, because lock acquisition is part of the sweep (FR-1).

**FR-10 — Remedy kind for every remedy check.** Every condition reported by a Brighter remedy check (a health check registered by the registration calls this spec adds, or by any future Brighter registration call) belongs to a check whose tag and result data name its remedy kind (restart, take out of service, investigate), so an operator or orchestrator can tell the kind without parsing the free-text description. The existing consumer check is not a remedy check (FR-10.2). The one exception is a result the health-check service builds after an unexpected exception, which has no `Data` (FR-13.1). This applies to:
- **FR-10.1 — Sweeper check.** A hung sweep (FR-5) has remedy kind **restart**. Consecutive failed sweeps (FR-6) have remedy kind **investigate**. Tripped topics (FR-6A) and tripped topics unreadable (FR-13.2) have remedy kind **investigate**: a restart does not cure a failing topic, and taking the instance out of service would stop healthy topics from being swept. The hung-sweep condition is therefore reported by the restart check, and the others by the investigate check (FR-4). When several conditions apply, each is visible on its own check.
- **FR-10.2 — Consumer check from #4555 (`BrighterServiceActivatorHealthCheck`).** The existing consumer check keeps its behaviour, statuses and description exactly as today, carries no tag and no `Data`, and remains registered by the user with `AddCheck` (NFR-6). Brighter adds an opt-in registration that splits its conditions into the two consumer remedy checks (FR-12). Persistent channel failures have remedy kind **take out of service**, which keeps #4555's readiness guidance. Missing consumers have remedy kind **restart**. The existing consumer check is marked `[Obsolete]` (a compile warning, not an error) with a message that names the opt-in registration, and is retired in V11. Retirement is outside this spec.
- **FR-10.2.1 — Coexistence.** A host registers either the existing consumer check or the consumer remedy checks, not both, because the same conditions would be reported twice. Brighter does not enforce this; the docs state it.
- **FR-10.3 — Routing.** Each remedy check is registered with exactly one tag, which identifies its remedy kind (one tag per remedy kind, a mapping the ADR defines), and no other tag. Using only those tags and standard `Microsoft.Extensions.Diagnostics.HealthChecks` / ASP.NET Core health-check configuration (`HealthCheckOptions.Predicate`, and `ResultStatusCodes` where a Degraded result must fail a probe), an operator can expose the conditions so that a **restart** condition fails a liveness probe without failing readiness, a **take out of service** condition fails readiness without failing liveness, and an **investigate** condition fails neither probe but is still visible to monitoring. "Visible" means that the condition's description and `Data` are in the `HealthReport`, which any standard consumer can read: a `ResponseWriter` supplied by the user, or an `IHealthCheckPublisher` for hosts without HTTP. Brighter ships no response writer and ASP.NET Core provides no JSON one. The docs give a complete, copy-pasteable writer built on `System.Text.Json` that writes the overall status and, for each check, its name, status, tags, description and `Data` (FR-11), and mention the community `UIResponseWriter` as an alternative that adds a package dependency. No routing depends on the writer.
- **FR-10.4 — Convention.** One remedy check registration reports conditions of one remedy kind only. This is documented as Brighter's convention, which every future Brighter health check must follow. The existing consumer check, which is not a remedy check, is the single documented exception to this convention.
- **FR-10.5 — Remedy in the result data.** Each remedy check's `HealthCheckResult.Data` carries machine-readable detail for status pages and alert routing. Data supplements the tags and the description; no routing depends on it. Whenever the check runs and returns a result, whether Healthy or Degraded, `Data` holds:
  - the **remedy kind** of the check (restart, take out of service or investigate);
  - the **conditions** the check currently reports, as a collection of condition names. It is empty when the check is Healthy and holds every condition that applies when more than one does (AC-39);
  - for each reported condition, the **values** that condition's description is built from, with the complete data and not a shortened form:

  | Condition | Values in `Data` |
  |-----------|------------------|
  | Hung sweep | running time, hang threshold and `TimerInterval`, each in seconds |
  | Consecutive failed sweeps | the count, N and `TimerInterval` (in seconds) |
  | Tripped topics | the number of tripped topics and the names of **all** of them (RoutingKey values), in ordinal order |
  | Tripped topics unreadable | the exception type thrown by the circuit breaker |
  | Persistent channel failures | the channel-failure threshold and, for each consumer at or over it, its subscription name, consumer name and failure count |
  | Missing consumers | for each subscription that is not shut on purpose and whose running consumer count differs from the expected count, its name, the running count and the expected count (the condition itself applies only when the running total is below the expected total, FR-12.2) |

  The ADR decides the key names, the condition-name strings and the value types. Values are plain strings, numbers, or lists and dictionaries of them (nested if the table needs a record, such as a consumer's name and count), so that any serializer can write them.

> **Note (ADR decision)**: The ADR decides the mechanism behind FR-10.3 to FR-10.5: the tag names (for example `live`, `ready`, `operator`), the check and extension names, the exact data keys and the types that carry the state. Routing reads only tags and `HealthStatus`, never result data, status codes that differ per condition or a Brighter-specific response writer (NFR-7).

**FR-11 — Documentation and release notes.**

It explains why the first alert is preferred to alerting on the absence of `completed` sweeps, and that the second reports 0 on an instance that is not an active sweeper.
- The health-check page in BrighterCommand/Docs describes the sweeper checks, their four conditions (hung sweep, consecutive failures, tripped topics, tripped topics unreadable) and boundaries, the consumer remedy checks and their two conditions (persistent channel failures, missing consumers) with their remedy kinds, how to opt in, threshold validation, and the remedy-kind convention. It also warns that with the `InMemoryOutbox` a liveness restart discards every unsent message, and advises those deployments to route the restart check to monitoring instead, or to accept the loss. It states that one `TimedOutboxSweeper` per service provider is the supported configuration (FR-4A.2). It states that the tripped-topic signals read no topics during a sweep's lock acquisition and for one interval after a lock collision (FR-6A.6), and that the consumer restart check is Healthy unless the dispatcher is running and fewer consumers than expected are running, and ignores subscriptions shut on purpose (FR-12.2); it advises a liveness probe period and failure threshold that tolerate the window after a scale-up or reopen, and that an unexpected exception in a check reports Degraded, so on a liveness endpoint it restarts the process (FR-13.1). It states that `IAmAnOutboxCircuitBreaker` must be registered as a singleton shared with the mediator for the tripped-topic signals to match what the sweeper skips, and that a circuit breaker whose `TrippedTopics` blocks stalls the tripped-topic signals. It replaces or qualifies #4555's "map Degraded to 503 on readiness" advice.
- **Migration guidance.** The same page has a step-by-step migration from the existing consumer check and existing endpoints, so that an existing endpoint keeps its behaviour while new endpoints are added beside it:
  1. Give every existing endpoint a predicate that excludes the remedy-tagged checks, so it selects what it selected before and its status and output do not change. An endpoint with no predicate would select the restart check once the checks are registered, and a hung sweep would turn a readiness endpoint into a 503. The predicate excludes tags that no check carries yet, which does no harm, so it is safe to ship first.
  2. Register the sweeper checks. They are tagged by remedy kind. The consumer remedy checks are not registered yet, because the existing consumer check is still registered and the two are never used together (FR-10.2.1).
  3. Add new endpoints, each with a predicate on one remedy tag: liveness (restart tag, Degraded mapped to 503), readiness (take-out-of-service tag, Degraded mapped to 503) and operator (investigate tag, using the documented JSON writer). The conventional URLs `/health/live`, `/health/ready` and `/health/operator` are suggested as guidance only.
  4. Run the old and new endpoints side by side and compare the sweeper conditions. Consumer monitoring stays on the old endpoints, which still select the existing consumer check. The new readiness endpoint selects no check until step 5, so it must not be a probe target yet, and the new liveness endpoint covers only the hung sweep.
  5. Cut over consumer monitoring in one change: remove the existing consumer check, register the consumer remedy checks, and point probes and monitoring at the new endpoints, adding the user's own checks (database and so on) to the new predicates by name or tag so they are still covered, or keeping an old endpoint for them. The existing check is untagged, so a tag-filtered endpoint never selects it and its monitoring would silently stop; the two registrations are never used together (FR-10.2.1).
  6. Before V11, which retires the existing consumer check, remove any remaining old endpoints, first moving the user's own checks onto the new predicates.

**FR-12 — Consumer remedy checks (opt in).** Brighter provides two remedy checks that split the conditions of the existing consumer check (`BrighterServiceActivatorHealthCheck`), and one call that registers both with `IHealthChecksBuilder`. Neither is added unless the user opts in. Both read the `IDispatcher` registered in the service provider, with the same inputs as the existing check, plus the dispatcher's state, whether it has been started and whether `End` has been called since, and its shut subscriptions (FR-12.2): the dispatcher's subscriptions and expected consumers per subscription, its running consumers, and each consumer's consecutive channel-failure count. Each is registered with a tag naming its remedy kind (FR-10.3).
- **FR-12.1 — Consumer take-out-of-service check.** Reports the persistent-channel-failures condition. It is Degraded when at least one consumer in the dispatcher's consumers (every one, as in the existing check, whatever the dispatcher's state and including draining and shut-subscription consumers) has a consecutive channel-failure count greater than or equal to the channel-failure threshold, and Healthy otherwise. It is never Unhealthy. Remedy kind: **take out of service**.
  - Example: threshold 3. Consumers with counts 0, 2 and 2 give Healthy. Counts 0, 3 and 2 give Degraded, and the description names the subscription, the consumer and the count 3.
- **FR-12.2 — Consumer restart check.** Reports the missing-consumers condition. While the dispatcher is running, when the total number of running consumers is **less than** the total expected, the check is **Unhealthy** if no consumer is running, and **Degraded** if at least one is. Otherwise it is Healthy, including when no consumer is expected and when more consumers are running than expected, because a restart does not cure an excess consumer. When the dispatcher is not running it is Healthy and its description says so, so a probe that fires before the dispatcher has started, or during shutdown, does not restart the process. Remedy kind: **restart**, because Brighter does not recreate a consumer whose pump has stopped on its own (the dispatcher removes it). The terms:
  - **Dispatcher running.** The dispatcher has been started and `Dispatcher.End` has not been called since the last start. "Started" means any operation that moves the dispatcher to `DS_RUNNING` (`Receive`, `Open` or `SetActivePerformers`). A call to `End` counts even though it does nothing in a state other than `DS_RUNNING`, so a dispatcher whose pumps all died and whose host then calls `End` at shutdown is Healthy. A later start clears the call, since the dispatcher can be started again once its control loop has ended. The state `DS_STOPPED`, which the dispatcher reaches by itself when every pump has stopped (or every subscription is shut) without `End` being called, counts as running, so that "every consumer died" stays reportable. After `End` the dispatcher is not running for this purpose, even though its state stays `DS_RUNNING` while consumers drain.
  - **Shut on purpose.** A subscription is shut on purpose from a `Dispatcher.Shut` that took effect (it does nothing unless the dispatcher's state is `DS_RUNNING`) until at least one consumer is created for it again, by `Receive`, `Open` or `SetActivePerformers`. A `SetActivePerformers` call that creates none leaves it shut. A raise after a `Shut` creates only the extra consumers, so the subscription then shows fewer running than expected and the check is Degraded until `Open` is used; that is accepted.
  - **Running consumer.** Every consumer in `Dispatcher.Consumers` whose subscription is not shut on purpose, including a consumer that a scale-down has told to stop and that is still finishing its handler. The consumers of a shut subscription, including any still draining, do not count as running, and the subscription does not count as expected. It is left out of the description and `Data` of this check (FR-10.5), not shown with an expected count of 0.
  - **Totals.** The comparison is on totals across all subscriptions, as in the existing check, so a missing consumer on one subscription can be masked by an excess on another; that is accepted.
  - **Dispatcher members.** The dispatcher must make deliberately shut subscriptions, whether it has been started, and whether `End` has been called since the last start distinguishable; additive public members on `Dispatcher` are permitted (NFR-6) and the ADR designs them.
  - **Transients.** Deliberate scaling and reopening are accepted transients: after `SetActivePerformers` raises the count, or `Open` reopens a subscription, the check can be Degraded until the new consumers are created, and after a scale-down it stays Healthy while surplus consumers finish their in-flight handlers. The docs advise a liveness probe period and failure threshold that tolerate the scale-up window (FR-11).
  - Example: subscription `orders` expects 2 consumers, dispatcher running. 1 running gives Degraded and a description "orders has 1 of 2 expected consumers". 0 running gives Unhealthy. 2 running gives Healthy.
  - Example: the dispatcher is awaiting (not yet running), 0 consumers running, 2 expected: Healthy. `orders` shut on purpose with 0 running, no other subscription: Healthy.
- **FR-12.3 — Channel-failure threshold.** The default is 3 (as #4555). An override must be a positive integer. 0 or negative is rejected with `ArgumentOutOfRangeException` thrown by the registration call itself, before any health-check run (as FR-7.2). 1 is allowed. It applies to the take-out-of-service check only.
- **FR-12.4 — Statuses and descriptions match the existing check.** While the dispatcher is running, no subscription has been shut on purpose and no more consumers are running than expected, the worst status of the two consumer remedy checks equals the status the existing check reports (Healthy, Degraded or Unhealthy), and each condition's description text carries the same values as the existing check's (subscription name, consumer name, counts). Each check describes only its own condition. When Healthy, its description says its own conditions are absent, except as FR-12.2 (restart check only: dispatcher not running) and FR-12.7 (no dispatcher) state. The take-out-of-service check has no dispatcher-not-running mode (FR-12.1). The ADR fixes the exact wording. Outside that state the existing check keeps its behaviour (it reports Degraded or Unhealthy before the dispatcher starts and after a subscription is shut), which is a reason to move to the remedy checks.
- **FR-12.5 — Data.** Each check's `Data` follows FR-10.5.
- **FR-12.6 — Coexistence.** FR-10.2.1 applies: a host registers the existing consumer check or the consumer remedy checks, never both.
- **FR-12.7 — No dispatcher.** When no `IDispatcher` is registered in the service provider (for example a publisher-only service), nothing throws. Both consumer remedy checks report Healthy with a description that says no dispatcher is registered, and `Data` holding the remedy kind and an empty conditions collection.

**FR-13 — A failed read does not make a remedy check Unhealthy.**
- **FR-13.1 — Failure status.** Every remedy check Brighter registers (FR-4, FR-12) is registered with failure status Degraded, so an unexpected exception thrown from a check is reported by the health-check service as Degraded, never as Unhealthy by default. In that case the service builds the result, so `Data` is empty and only the tag names the remedy kind (an exception to FR-10.5). On a check mapped to a liveness probe the Degraded result becomes a 503, so an unexpected exception in a restart-tagged check restarts the process. This is accepted, and the docs say so (FR-11). The consumer restart check's Unhealthy for no running consumers (FR-12.2) is a reported condition, not a failure.
- **FR-13.2 — Tripped topics unreadable.** The circuit breaker is looked up in the service provider, and its `TrippedTopics` read, on each run of the check or gauge and only while the sweeper is an active sweeper (FR-6A), so this condition too arises only then. If reading the circuit breaker's `TrippedTopics` throws (for example a third-party `IAmAnOutboxCircuitBreaker`), or the lookup of the circuit breaker throws, the investigate check catches the exception, logs it, and reports Degraded for the tripped-topics-unreadable condition with a description saying the tripped topics could not be read, and `Data` holding the exception type. The check's other conditions are still evaluated and reported. In the same case the tripped-topics gauge reports 0 for that observation and logs the exception. A circuit breaker that is not registered is not an error (FR-6A.4). A `TrippedTopics` that blocks is not handled: NFR-1 assumes it does not, and this is a documented limitation (FR-11).
- **FR-13.3 — Gauge callbacks.** An exception inside a gauge callback is caught and logged, and that observation reports 0. It does not stop the sweeper or the meter provider (as NFR-9).
- **FR-13.4 — Dispatcher.** The consumer remedy checks, like the existing check, require the Brighter `Dispatcher` registered as `IDispatcher`. Any other implementation is not supported, and the failure is reported as FR-13.1 describes.

### Non-functional Requirements

**NFR-1 — Reports while the sweeper's thread is blocked.** Observing either gauge and running either health check never wait on the sweeper's thread, never wait on a lock held across sweep work (lock acquisition, outbox I/O) (a lock held only while state fields are written is permitted), and never need the sweep to make progress. While a test double blocks the sweep indefinitely, `MeterListener.RecordObservableInstruments()` returns the current running time and `CheckHealthAsync` completes. Each finishes within 1 second of wall-clock time in tests. This assumes that `IAmAnOutboxCircuitBreaker.TrippedTopics` does not block (FR-13.2).

**NFR-2 — Thread-safe, tear-free reads.** The sweep-start record, the failure count, and the lock state and last-sweep state behind "active sweeper" are written by the sweeper's thread and read from other threads. A read sees either the previous or the current value, never a torn or partial one. A gauge or check that runs at the moment a sweep starts or ends reports either the old state or the new state, never a negative running time and never a combination of the two (for example, active state from one sweep with the lock state of another).

**NFR-3 — Low overhead.** The state tracking this spec adds to each sweep (recording start, lock state and outcome, FR-1 and FR-2) is a constant number of field writes, and the tracking operations (the type that holds the state, FR-3.3) allocate nothing. The sweeper's per-sweep allocation does not grow with the number of sweeps, and reading a fixed state does not allocate more as sweeps accumulate. Reading the state is constant time and does not allocate in proportion to sweep count or outbox size. Sweeps run on the sweeper's dedicated thread, so a test cannot measure a whole sweep's allocations from its own thread. The requirement is therefore tested on the tracking operations, and on the sweeper's per-sweep allocation measured from the sweeper's own thread (AC-48).

**NFR-4 — Testable time.** Running time is measured with the sweeper's injected `TimeProvider`, so tests can use `FakeTimeProvider` to set exact running times, such as exactly 30 s and 31 s, without real delays.

**NFR-5 — No forced dependency for non-opted-in users.** A user who uses `Paramore.Brighter.Outbox.Hosting` but does not opt in to the sweeper health checks:
- needs no new package reference, and
- gets no new transitive dependency other than, at most, `Microsoft.Extensions.Diagnostics.HealthChecks` (the Microsoft package that holds `IHealthChecksBuilder`, which any registration call needs; it has no ASP.NET Core dependency) and the packages it brings with it.

The same holds for a user of `Paramore.Brighter.ServiceActivator.Extensions.Diagnostics` who does not opt in to the consumer remedy checks. That package references only `Microsoft.Extensions.Diagnostics.HealthChecks.Abstractions` today, and may gain `Microsoft.Extensions.Diagnostics.HealthChecks` and nothing else.

No user is forced to take a dependency on ASP.NET Core, OpenTelemetry or `Paramore.Brighter.ServiceActivator.Extensions.Diagnostics` to use the sweeper.

> **Note (ADR decision)**: Which package hosts the sweeper health check (for example, `Paramore.Brighter.Outbox.Hosting` with an `IHealthChecksBuilder` extension, or a new `Paramore.Brighter.Outbox.Hosting.Diagnostics` package) is decided in the ADR, within NFR-5.

**NFR-6 — Backward compatibility.**
- `IAmABrighterSweeperMeter`, `IAmAnOutboxCircuitBreaker` and `IDispatcher` get no new members; any addition on the dispatcher goes on the `Dispatcher` class. Third-party `IAmAnOutboxCircuitBreaker` implementations keep working: the signals use only the existing `TrippedTopics` property.
- `OutboxCircuitBreakerOptions` defaults and the circuit breaker's trip and cooldown behaviour do not change.
- No existing public constructor, method or option of `TimedOutboxSweeper`, `TimedOutboxSweeperOptions`, `BrighterServiceActivatorHealthCheck` or `Dispatcher` is removed or changes meaning. Public API additions are additive only.
- The existing sweeper instruments (`tick.lag`, `sweep.duration`, `sweeps`) keep their names, units, attributes and semantics.
- For an application that changes no configuration, `BrighterServiceActivatorHealthCheck` returns the same `HealthStatus` for the same conditions as before. The existing registration is not changed or removed. The sweeper checks are added beside it as an opt-in, and the consumer remedy checks are an opt-in replacement for it, never registered with it (FR-10.2.1, FR-12). Marking it `[Obsolete]` (compiler warning CS0618, not an error) is the one permitted change. Building the repository introduces no new warnings, so Brighter's own code and tests suppress the obsolete warning where they use it. A user who builds with warnings as errors must suppress CS0618 or move to the consumer remedy checks when upgrading; this is accepted and the release notes say so (FR-11).

**NFR-7 — Idiomatic for .NET health checks.** The remedy-kind convention uses only standard `Microsoft.Extensions.Diagnostics.HealthChecks` concepts that a host or orchestrator integration can read without Brighter-specific code. Non-HTTP hosts, such as a worker with a custom probe, can also read it.

**NFR-8 — Naming and cardinality.** Each new gauge's name follows ADR 0010 (the `paramore.brighter.*` prefix, alongside the existing `paramore.brighter.outbox_sweeper.*` instruments). Each gauge's attribute set is fixed and small (see FR-3.4, FR-3A).

**NFR-9 — Recording failures do not affect sweeping.** As for the existing instruments (ADR 0081 (sweeper metrics)), an exception from a metric recording call is caught and logged. It does not stop the sweeper or change a sweep's outcome.

### Constraints and Assumptions

- **Constraint**: Brighter does not cancel, abort or time out a sweep in flight (ADR 0081 (sweeper metrics)). Detection and reporting are the whole remedy Brighter offers.
- **Constraint**: Both signals are pulled. The metrics exporter or health-check host calls them on its own thread, never the sweeper's.
- **Constraint**: Signals based on "time since the last completed sweep" must not be used. On multi-instance deployments, instances that do not hold the lock never complete a sweep and would be Degraded permanently.
- **Constraint**: `IAmABrighterSweeperMeter` is a public role. Adding a member would break anyone who implements it, so the gauge is not added to it.
- **Constraint**: `InMemoryOutboxCircuitBreaker` is in-memory and per instance (ADR 0028), even with a durable outbox, and its cooldown advances only on a sweep that obtained the lock. Another `IAmAnOutboxCircuitBreaker` implementation reports whatever its `TrippedTopics` returns. Tripped topics are therefore reported per instance, and only while that instance is an active sweeper (FR-6A). `sum` or `max` across instances is the operator's choice. This work does not share or persist tripped-topic state.
- **Constraint**: The distributed lock is taken and released on every sweep (`TimedOutboxSweeper`), so there is no long-lived holder; the instance that obtains it can change from tick to tick (FR-6A.6).
- **Constraint**: `IAmAnOutboxCircuitBreaker` is not registered by Brighter itself; the user registers it. The tripped-topic signals depend on it being registered as a singleton shared with the mediator (FR-6A.4).
- **Constraint**: `TimerInterval` stays validated as at least 1 second (existing behaviour). So the default hang threshold is never below 3 s.
- **Constraint**: The work is red-first (TDD). Tests are written and fail before the implementation, per the Brighter test-first workflow.
- **Assumption**: At most one `TimedOutboxSweeper` runs per host / service provider (FR-4A). The health checks observe that sweeper. The host stops it at shutdown and never replaces it, so a stopped sweeper can be queried only while the process is still answering probes, such as during the shutdown drain or while an abandoned sweep keeps running.
- **Assumption**: The health checks and the gauges observe the same sweeper state (FR-1, FR-2), so they never disagree about whether a sweep is in progress, apart from the moment of observation.
- **Assumption**: Users who want HTTP probes configure their own endpoints. Brighter supplies the convention and documentation, not the endpoint mapping.
- **Assumption**: The hang threshold is compared against the running time of the *current* sweep only. A sweep that was long but has now ended is reported only through the existing `sweep.duration` histogram.

### Out of Scope

- Cancelling, aborting, killing or timing out a hung sweep, or the thread running it.
- Automatically restarting the process, the sweeper or its thread. Brighter reports a restart remedy; acting on it is the orchestrator's or operator's job.
- Changing the `IAmABrighterSweeperMeter` interface.
- Signals based on time since the last completed sweep.
- Detecting a sweeper that is registered but never started (for example, `StartAsync` is never called). It has recorded nothing, so it reports running time 0 and Healthy. A sweeper that is not registered at all is covered by FR-4A.1. A sweeper that has stopped is covered by FR-1.2.
- Counting messages found or cleared by a sweep (draft PR #4484, outbox metrics), and the outstanding-message check (#4554).
- Changing the sweeper's scheduling, the lock protocol or the existing sweep outcomes.
- Changing when a topic trips, the cooldown, or the circuit breaker's logging, tracing and trip/recovery metric (ADR 0028, ADR 0058).
- Stale tripped topics on an instance that stops obtaining the lock. Cooldown advances only on a sweep that obtained the lock, so such an instance keeps its trips and applies them to its own next sweeps, possibly after the broker has recovered. The signals here hide them while the sweeper is not active (FR-6A.5) but do not expire them. Expiring them by time, or sharing tripped state between instances, changes ADR 0028 and is a separate piece of work that follows this one (a separate issue and ADR).
- Per-topic lag or backlog measurement (outstanding-message counts are covered by #4554 and the outbox metrics work).
- The sync `Dispatch()` path never tripping the breaker (tracked separately in ADR 0058).
- Removing the existing consumer check (retirement in V11) and changing its behaviour.
- Mapping endpoints in ASP.NET Core applications. Brighter documents the mapping but does not add endpoints.
- Re-exporting runtime or thread-pool metrics.

## Acceptance Criteria

Unless stated otherwise: TimerInterval = 10 s; default hang threshold 30 s; default N = 3; time is driven by `FakeTimeProvider`; "blocking double" means a test double for `IDistributedLock` or `IAmAnOutboxProducerMediator` that blocks the sweep until the test releases it.

**AC-1 — Gauge reports running time while the sweep blocks in the outbox (FR-1, FR-3.1, NFR-1, NFR-4).** Given `AddBrighterInstrumentation` is configured, a `MeterListener` subscribed to `paramore.brighter.outbox_sweeper.sweep.running_time`, and a blocking outbox mediator double, when a sweep starts and the clock advances 25 s, then `RecordObservableInstruments()` returns within 1 s and records 25.0 with unit `s`.

**AC-2 — Gauge includes lock acquisition (FR-1, FR-3.1).** Given a blocking `IDistributedLock` double whose `ObtainLockAsync` does not return, when a sweep starts and the clock advances 40 s, then the gauge records 40.0.

**AC-3 — Gauge is 0 when no sweep is in progress (FR-3.2).** Given the gauge is registered, when it is observed (a) before the sweeper starts its first sweep, (b) after a completed sweep, (c) after a failed sweep, (d) after a lock-unavailable sweep, and (e) after the blocking double from AC-1 is released and the sweep ends, then each observation records 0.

**AC-4 — Gauge not published without instrumentation (FR-3.3).** Given `AddBrighterInstrumentation` is not called, when the sweeper runs a sweep, then no instrument named `paramore.brighter.outbox_sweeper.sweep.running_time` is published and the sweep completes as before.

**AC-5 — Public API unchanged (FR-3.3, NFR-6).** Given the public API of `IAmABrighterSweeperMeter`, `IAmAnOutboxCircuitBreaker`, `TimedOutboxSweeper`, `TimedOutboxSweeperOptions`, `BrighterServiceActivatorHealthCheck`, `Dispatcher` and `IDispatcher` before this change, when the change is applied, then every member each declared before still exists with the same signature and meaning (apart from the `[Obsolete]` attribute on `BrighterServiceActivatorHealthCheck`), `IAmABrighterSweeperMeter`, `IAmAnOutboxCircuitBreaker` and `IDispatcher` declare exactly the same members, additions to the other types (including `Dispatcher`) are allowed, and a class written against the old interfaces still compiles.

**AC-6 — Hung sweep boundary (FR-5).** Given the sweeper health checks are registered with the default threshold and a sweep is blocked by a blocking double, when the running time is 29 s, then the check reports Healthy. When it is exactly 30 s, Healthy. When it is 31 s, Degraded, and the description contains the running time (31 s), the threshold (30 s) and `TimerInterval` (10 s).

**AC-7 — Hang recovery (FR-5.1).** Given the check reports Degraded for a hung sweep at running time 31 s, when the blocking double is released and the sweep ends as completed, then the next check reports Healthy.

**AC-8 — Hang threshold override (FR-7.1).** Given the hang threshold is overridden to 2 minutes, when a sweep has run 90 s, then the check reports Healthy. When it has run 121 s, Degraded.

**AC-9 — Hang threshold validation (FR-7.1).** Given an override of `TimeSpan.Zero` or `TimeSpan.FromSeconds(-1)`, when the registration call is made, then it throws `ArgumentOutOfRangeException` before any health-check run and without the host's health-check service having been built. Constructing the check directly with the same value also throws (FR-7.3). Given an override of `TimeSpan.FromSeconds(5)` with TimerInterval = 10 s, no exception is thrown.

**AC-10 — Default hang threshold follows TimerInterval (FR-7.1).** Given TimerInterval = 1 s and no override, when a sweep has run 3 s, then Healthy. When it has run 3.001 s, Degraded.

**AC-11 — Consecutive failures boundary (FR-2, FR-6).** Given an outbox mediator double that throws on every sweep, when 2 sweeps have ended as failed, then the check reports Healthy. After the 3rd, Degraded, and the description contains the count (3), N (3) and `TimerInterval` (10 s). After the 4th, still Degraded.

**AC-12 — Lock-unavailable neither counts nor resets (FR-2, FR-6).** Given outcomes failed, failed, lock_unavailable, then failed, when the check runs after each, then it reports Healthy, Healthy, Healthy, Degraded.

**AC-13 — Completed sweep resets the count (FR-6.1).** Given 3 consecutive failed sweeps (Degraded), when the next sweep completes, then the check reports Healthy. After one more failed sweep it still reports Healthy (count 1).

**AC-14 — Failure threshold override and validation (FR-7.2).** Given N = 1, when one sweep fails, then Degraded. Given N = 0 or N = -1, when the registration call is made, then it throws `ArgumentOutOfRangeException` before any health-check run, and so does constructing the check directly (FR-7.3).

**AC-15 — Failures thrown by the lock count as failed (FR-2, definitions).** Given an `IDistributedLock` double whose `ObtainLockAsync` throws, when 3 sweeps run, then the check reports Degraded for consecutive failures.

**AC-16 — Conditions on different checks at once (FR-4, FR-5, FR-6, FR-8, FR-10.1).** Given 3 consecutive failed sweeps followed by a sweep blocked for 31 s, when both checks run, then the restart check reports Degraded with a description of the hung sweep (31 s, 30 s, 10 s) and the investigate check reports Degraded with a description of the failures (3, 3, 10 s). Neither description mentions the other's condition. Each result's data names its own remedy kind.

**AC-17 — Health check runs while the sweeper's thread is blocked (NFR-1).** Given a blocking double holds the sweep indefinitely, when `CheckHealthAsync` is called from a test thread, then it completes within 1 s of wall-clock time.

**AC-18 — Shared lock across instances (FR-9).** Given two sweepers A and B share one in-memory lock, A's sweep holds the lock and is blocked by a blocking mediator double, and B's sweeps are lock-unavailable, when the clock advances 31 s, then:
- A's check reports Degraded (hung) and A's gauge records 31.0.
- B's check reports Healthy and B's gauge records 0 between B's sweeps.
- The maximum of the two gauge values is 31.0.
