# Conformance Tests for a Box or Transport

Brighter does not enforce *how* you implement a Box (Inbox/Outbox) or a Transport (Messaging Gateway); it does require that your implementation honours the contract of the interfaces it fulfils. To check that, we maintain [`tools/Paramore.Brighter.Test.Generator`](../../../tools/Paramore.Brighter.Test.Generator/): a code generator that emits a standard conformance suite into your test project from a small JSON file.

The bargain is:

1. You declare, in `test-configuration.json`, which component you are testing and which optional features your middleware or database supports.
2. The generator emits a suite of xUnit tests, plus a **provider interface** that the tests depend on.
3. You implement that provider interface — the "wrapper" that teaches the generic tests how to construct *your* Outbox or Gateway.
4. A green suite is your evidence of conformance.

You write the provider. You do not write the tests, and you MUST NOT edit them — see [Never edit generated code](#never-edit-generated-code).

## Which Guide Do I Need?

- **[Generating an Outbox suite](./outbox.md)** — for `Paramore.Brighter.Outbox.X`.
- **[Generating a Transport suite](./transport.md)** — for `Paramore.Brighter.MessagingGateway.X`.

## Scope: What the Generator Does Not Cover

The generator emits suites for **Outboxes** and **Messaging Gateways** only:

- **Inbox templates do not exist yet**, so `tools/Paramore.Brighter.Test.Generator/Templates/` contains only `Outbox/` and `MessagingGateway/`. Inbox generation is in progress in [PR #4230](https://github.com/BrighterCommand/Brighter/pull/4230); until it lands you MUST hand-write an Inbox's tests. This page will be updated when it does.
- **There are no Locking or Archive templates.**

A generated suite is a *floor, not a ceiling*. It proves you honour the interface contract. It does not cover behaviour specific to your middleware, so you SHOULD add hand-written tests alongside it for anything the generic suite cannot know about.

## Running the Generator

The tool takes exactly one option, `--file`, which defaults to `test-configuration.json`:

```bash
dotnet run --project tools/Paramore.Brighter.Test.Generator -- --file <path>
```

### ⚠️ You MUST `cd` into your test project first

Output is written to `DestinationFolder`, and when that is not set in the config the tool falls back to **the current working directory**, *not* to the directory holding the config file ([`Program.cs`](../../../tools/Paramore.Brighter.Test.Generator/Program.cs)):

```csharp
if (string.IsNullOrEmpty(configuration.DestinationFolder))
{
    configuration.DestinationFolder = Directory.GetCurrentDirectory();
    logger.LogInformation("No destination folder specified, going to use {Folder}", configuration.DestinationFolder);
}
```

No checked-in `test-configuration.json` sets `DestinationFolder`. So run it like this:

```bash
cd tests/Paramore.Brighter.MyMiddleware.Tests
dotnet run --project ../../tools/Paramore.Brighter.Test.Generator
```

Running it from the repository root with `-- --file tests/MyProject/test-configuration.json` resolves the config correctly but **writes the generated tests into the repository root**. `CONTRIBUTING.md` currently recommends that form; it is wrong, and this page supersedes it.

### Regenerating everything

From the repository root, to regenerate every participating project:

```bash
./generate-test.sh      # or .\generate-test.ps1 on Windows
```

This walks every directory under `tests/`, `cd`s in, and runs the generator. A project without a `test-configuration.json` is skipped silently and successfully — the tool logs and returns `0` for a missing file, which is exactly what makes the sweep safe.

### If you change a template

Templates are read from `AppContext.BaseDirectory`, i.e. the generator's **build output**, not the source tree. After editing a `.liquid` file you MUST rebuild the generator before regenerating, or you will silently re-emit the old content:

```bash
dotnet build tools/Paramore.Brighter.Test.Generator
```

## Never Edit Generated Code

Every emitted file carries:

```csharp
// <auto-generated>
// This file is auto-generated by Paramore.Brighter.Test.Generator
// </auto-generated>
```

- You MUST NOT edit files under a `Generated/` folder. The next regeneration overwrites them.
- If a generated test is wrong for everyone, fix the template and regenerate all projects.
- If it is wrong only for your middleware, the answer is a feature flag in your config (see the per-component guides), not an edit.
- **The generator never deletes.** It only creates and overwrites. If you turn a feature flag from `true` to `false`, the previously generated test file remains on disk and keeps running (and failing). You MUST delete it by hand.

## The Shared Contracts

Regardless of component, the generator always emits four files into the root of your test project, from [`Templates/*.liquid`](../../../tools/Paramore.Brighter.Test.Generator/Templates/):

| File | Purpose |
|---|---|
| `IAmAMessageBuilder.cs` | Fluent builder interface used by the tests to construct a `Message`. |
| `DefaultMessageBuilder.cs` | The stock implementation. |
| `IAmAMessageAssertion.cs` | `void Assert(Message expected, Message actual)` — how the tests compare messages. |
| `DefaultMessageAssertion.cs` | The stock implementation. |

The defaults suit most implementations. Override them when your middleware cannot round-trip a `Message` faithfully — for example RabbitMQ, which sets root-level `"MessageAssertion": "RmqMessageAssertion"` in [its config](../../../tests/Paramore.Brighter.RMQ.Async.Tests/test-configuration.json) because some headers do not survive the broker. To override, implement the interface in your test project and name your type in the config:

```json
{
  "Namespace": "Paramore.Brighter.MyMiddleware.Tests",
  "MessageAssertion": "MyMiddlewareMessageAssertion",
  "MessageBuilder": "MyMiddlewareMessageBuilder"
}
```

Both default to `DefaultMessageBuilder` / `DefaultMessageAssertion` when omitted, and both are inherited by each component's config unless that component overrides them. Note that `MessageAssertion` applies to gateways only — outbox tests do not use assertions, and `OutboxConfiguration` has no such property.

## Root Configuration Schema

`test-configuration.json` deserialises to [`TestConfiguration`](../../../tools/Paramore.Brighter.Test.Generator/Configuration/TestConfiguration.cs). Use exact PascalCase for property names.

| Property | Type | Default | Notes |
|---|---|---|---|
| `Namespace` | string | `""` | Required in practice. Root namespace of your test project. |
| `DestinationFolder` | string | current working directory | Leave unset; `cd` instead. |
| `MessageBuilder` | string? | `DefaultMessageBuilder` | Inherited by components. |
| `MessageAssertion` | string? | `DefaultMessageAssertion` | Inherited by gateways. |
| `Outbox` | object? | `null` | Single outbox. See [outbox.md](./outbox.md). |
| `Outboxes` | map? | `null` | Named outbox variants. |
| `MessagingGateway` | object? | `null` | Single gateway. See [transport.md](./transport.md). |
| `MessagingGateways` | map? | `null` | Named gateway variants. |

The singular and plural forms are mutually exclusive: **if both are set, the singular wins and the plural is ignored entirely.**

## Running the Generated Tests

The suite is **xUnit**, and it talks to real infrastructure — there are no test doubles here by design. Bring the middleware up first with the relevant Compose file from the repository root (`docker-compose-rmq.yaml`, `-kafka`, `-mysql`, and so on), then:

```bash
dotnet test tests/Paramore.Brighter.MyMiddleware.Tests
```

`Category` in your config renders an xUnit `[Trait]`, so you can select a single implementation's suite:

```bash
dotnet test --filter "Category=RMQ"
```

`CollectionName` renders `[Collection(...)]`, which serialises tests that would otherwise contend over shared infrastructure.
